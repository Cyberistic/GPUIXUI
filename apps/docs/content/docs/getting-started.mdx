A GPUix application is a React tree rendered into a native window. The entry
file ends with `render()`, which creates the window, mounts React and starts the
frame loop. Wrap the tree in a `ThemeProvider` so every component below it reads
the same resolved theme.

```tsx title="app.tsx"
import { render } from "@gpuix/react";
import {
  Box,
  Button,
  Stack,
  Text,
  ThemeProvider,
} from "@gpuixui/primitives";
import { lightTheme } from "@gpuixui/tokens";

function App() {
  return (
    <ThemeProvider theme={lightTheme}>
      <Box tone="background" padding="lg">
        <Stack direction="column" gap="md">
          <Text role="h2">Hello from GPUIXUI</Text>
          <Button variant="primary">Save changes</Button>
        </Stack>
      </Box>
    </ThemeProvider>
  );
}

render(<App />, { title: "My app" });
```

```sh
nub app.tsx
```

`lightTheme` and `darkTheme` are plain values from `@gpuixui/tokens`. The
application owns the mode switch, because GPUix exposes no appearance query; see
[Theming](/docs/theming) for the roles and the extension mechanism, and
[Dark mode](/docs/dark-mode) for the switch itself.

## Providers

The two component packages read two different React contexts, so a mixed app
mounts two providers.

- `@gpuixui/primitives` owns its context. There is no default theme: a primitive
  rendered without `<ThemeProvider>` above it throws `MissingThemeProviderError`
  naming the provider.
- `@gpuixui/components` reads the token context from `@gpuixui/tokens/react`.
  That context **falls back to `lightTheme`** when no provider is above it, so a
  components-only tree paints light instead of failing.

An app that uses both packages nests the token provider outside the primitives
provider, with the same resolved theme:

```tsx
import { darkTheme } from "@gpuixui/tokens";
import { ThemeProvider as TokensThemeProvider } from "@gpuixui/tokens/react";
import { ThemeProvider } from "@gpuixui/primitives";

<TokensThemeProvider theme={darkTheme}>
  <ThemeProvider theme={darkTheme}>
    {/* primitives and components */}
  </ThemeProvider>
</TokensThemeProvider>;
```

A components-only app still imports the provider from `@gpuixui/tokens/react`; a
primitives-only app needs only the primitives provider. The
[Installation](/docs/installation) page declares `@gpuixui/tokens` directly for
that reason, rather than relying on a transitive install.

## Try the library in an example

[`examples/basic-app`](https://github.com/Cyberistic/GPUIXUI/tree/master/examples/basic-app)
composes the Tier 1 components into a settings workflow and is the one example
in the repository today:

```sh
nub install
nub run --filter @gpuixui/basic-app dev
```

Its `dev` script currently runs `bun src/main.tsx`, so it needs Bun, the GPUix
native binding and a desktop session; without that,
`nub run --filter @gpuixui/basic-app check-types` verifies the composition. See
[Examples](/docs/examples) for what that does and does not prove.

## The native playground

The companion playground (`apps/playground`) hosts the capability scenarios and
the theme gallery behind the repository's 20/20 native smoke suite:

```sh
nub run dev:playground
```

It needs the GPUix native binding and a desktop session. On Intel macOS the
pinned 0.10.0 binding is a local source build (ADR `0003`), so a clean checkout
must build it first.

The playground has no per-component screens yet. Each component page therefore
names the native suite that drives it, or carries a labelled browser
approximation for a static rest state; no page substitutes a browser imitation
for a runtime check.

## Native previews

The site runs GPUix in the browser only through an isolated, opt-in WebAssembly
document: a page with a scene shows the real component code there, labelled as
the browser renderer rather than the desktop window. Every page also carries its
native evidence — a capture, a playground screen, or the suite and command that
drives the component — and a static rest state may carry a labelled browser
approximation. The rules are summarised in [Architecture](/docs/architecture)
and recorded in full in `docs/preview-strategy.md`.
