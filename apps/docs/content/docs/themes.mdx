Edit the semantic tokens the library ships and watch them apply to a preview in
real time. The editor reads its defaults from `@gpuixui/tokens` — the base is
the platform style the sidebar switch selected — and emits the same
`createTheme` shape the library consumes; it invents no palette of its own.

## How it works

The editor edits the shadcn-core roles — `background`, `foreground`, `card`,
`popover`, `primary`, `secondary`, `muted`, `accent`, `destructive`, `border`,
`input` and `ring` — plus `radius.md` and the `sans` family. Light and dark are
independent; pick the mode, edit, and the preview follows. Only the roles you
touch are stored as your edits, so they persist to the URL (shareable) and to
`localStorage` while everything else keeps following the selected style;
**Reset** clears the edits back to that style.

## Starting from a platform

The editor is the copy-and-own contract in practice. Choose **Windows** in the
sidebar and the preview and inputs start from Windows's roles, radii and family;
change the accent and **Copy theme** prints the whole resolved theme, the
Windows values you kept and the ones you replaced. The code is an ordinary
`createTheme` module — the same shape [Theming](/docs/theming#take-one-and-make-it-yours)
describes — so it can ship as your own style. Switching the platform afterwards
re-bases the preview without discarding your edits, because an untouched role
was never pinned.

## The token bridge

`@gpuixui/tokens` ships TypeScript objects, not CSS variables, and the library
paints through GPUix. This preview is CSS, so the editor exposes each role as
the shadcn variable name (`--primary`, `--background`, …) on the preview
element, maps `radius.md` to `--radius`, and maps `.SystemUIFont` to a CSS
system stack because GPUI resolves that sentinel natively and the browser
cannot. The bridge exists only for this preview.

## The theme audit

The readout under the preview runs `auditTheme` on the theme the edits resolve to
— the same gate `@gpuixui/tokens` tells a theme author to run before shipping, so
an edit is measured against exactly the contract the library holds itself to. One
call reports ten independent failures:

- **Roles** the renderer cannot paint. GPUix ignores a colour string it cannot
  parse and keeps the previous value or paints black, so the editor names the role
  and the value instead of failing in silence, and calls an absent role
  **"missing from this theme"** — a theme restored from storage can predate a role
  the library added, which is not a typo in a value.
- **Elevation shadows** the renderer cannot paint. A level is normally a geometry
  plus a share of the `shadow` role, which the role check covers — but an
  `elevation` override replaces a level whole, colours and all.
  `invalidShadowColors` names the level and the value, because the runtime then
  paints no shadow at all and a raised card or dialog silently sits flat.
- **Numbers**: `invalidNumbers` reads every numeric token — spacing, radius,
  border width, icon size, type size and leading, density and the shadow
  geometry — against the rule the design gives it. A style batch crosses a JSON
  boundary on its way to native, so `NaN` and `Infinity` arrive as `null` and the
  property is dropped, while a negative or zero size is accepted and lays an
  element out at no height: a theme that is not the one the reader described,
  with nothing painted wrong enough to notice. A control height — and a list row,
  which a `dense` row builds at exactly `density.rowHeight` — is also the box a
  pointer presses, so both are held to the library's {targetSize.minimum}px target
  floor: a shorter one lays out, but a reader cannot reliably hit it. A type
  role's leading must also reach its own font size, because a shorter line height
  puts the next baseline inside this line's glyphs, and a control height must
  contain the leading of the tallest label a control paints (`label` or `body`),
  because the box is exactly that height and a shorter one clips the text it
  exists to show. A third pair sits inside the type scale: `bodyStrong` shares
  `body`'s size and leading by design, so its weight is the whole difference
  between reading and emphasis, and a brand that forwards one weight to every
  role paints the two identically. Those are the report's three rules about a
  pair of tokens, so each is measured on the pair.
- **Contrast**: `contrastFailures` checks {contrastPairs.length} role pairs — body
  text at 7:1, secondary text at 4.5:1, boundaries and focus rings at 3:1 — and
  the readout names every pair an edit breaks, with its measured ratio. A
  translucent value is reported as **unmeasurable** rather than counted as a pass,
  because its contrast depends on the surface behind it.
- **Decorative surfaces**: the {decorativeSurfaces.length} placements
  `decorativeFailures` measures carry no text, so WCAG gives them no floor at
  all. Ten kinds are measured, each where a component paints it: a `divider`
  rules a region, a `skeleton` stands in for content that has not loaded, a
  `scrim` is the veil under a modal, a `statusTint` is the soft fill behind a
  status message and a `statusEdge` bounds it, a `scrollbar` is the thumb a
  scroller tints, a `stateWash` is the tint behind a hovered, pressed, selected
  or accented row, a `filledAction` is the resting face of a `secondary` action
  (the one filled variant with no brand colour of its own and no border), a
  `disabledFace` is the fill a control wears while it is unavailable — measured
  face against face with the enabled action it replaces, because a disabled
  control wearing an enabled fill tells the reader it is available — and an
  `elevation` is the shadow a raised surface drops — measured at the scale's
  deepest level, because if the strongest step cannot differ from the strip the
  whole scale is flat there. Each is held to {decorativeFloor}:1 against the
  strip it sits on: editing `border` towards `background` is how a card loses
  its edge, a `hover` equal to `popover` is a row that never looks hovered, and
  neither is a contrast pair.
- **Data series**: `seriesFailures` measures the
  {seriesColors(themes.dark).length} categorical colours a chart paints against
  the {seriesSurfaces.length} surfaces a plot is drawn on (`background`, `card`,
  `popover`) at the {contrastFloors.boundary}:1 boundary floor, each pair against
  `seriesDistinctnessFloor` in OKLab — a blue and a violet of one lightness pass
  contrast and still read as one series — and each pair again through every
  `colorVisionDeficiencies` simulation (`protanopia`, `deuteranopia`,
  `tritanopia`) against `seriesDeficiencyFloor`, because contrast and distance
  both assume full colour vision and two hues can separate for one reader while
  collapsing for another.
  The editor does not edit the scale, so an edit cannot break it; the readout
  reports it because `auditTheme` does, and a line that only appears for some
  themes would make a passing readout mean less than it says.
- **Text selection**: `selectionFailures` composites the `selection` wash over
  the **{selectionPairs.length}** text pairs a reader can select from — each
  content surface at its own body role (`input`, `background`, `card`,
  `popover`, and the `muted` fill a message bubble paints, which is the fifth
  content surface) and a `mutedForeground` line on the three prose surfaces — and holds
  every result to two floors: visible against what it covers (1.05:1) and
  readable inside it, at the floor the unselected pair already meets
  ({contrastFloors.body}:1 for body text, {contrastFloors.secondary}:1 for the
  secondary line). `contrastRatio` refuses a translucent colour, so the wash and
  the text in it were measured nowhere before this report; the editor does not
  edit `selection`, but a change to a surface under it can still bury a selected
  run — including the caption or second line beneath a heading. A theme carrying
  no `selection` role (or no surface to blend it over) has no wash to measure, so
  the line says it **could not be composited** and the role check names what is
  missing.
- **Indicator marks**: `indicatorFailures` holds the roles a component paints
  when it *shows* rather than says something — a progress fill, a spinner's lit
  dot, a slider's filled span, a switch's on-state, a presence dot — to the 3:1
  non-text floor on all {indicatorSurfaces.length} strips `indicatorSurfaces`
  names (`background`, `card`, `popover`, `muted`, `hover`, `active`, `input`):
  the page, a card, a popover, a muted toolbar, the two washes a row tints under
  the pointer and a field's own fill, which carries its caret. A mark is neither
  text nor a boundary, so no contrast pair saw it: `primary` was only measured
  against its own on-colour, and a bar painted in a role that matches the page
  passed every other report. A status mark paints the tone's readable role
  (`statusTone(...).foreground`), never its solid fill — light `warning` is a
  pale amber designed to carry near-black text and disappears on the page as a
  dot. The editor does not edit a mark's role directly, but `primary` is one, so
  an action-fill edit can hide a bar.
- **The disabled fade**: a faded control paints a share of its fill over the
  surface and fades its label over *that* faded fill, which is the composite a
  hand calculation usually forgets. `disabledFadeFailures` holds each of those
  pairs to {contrastFloors.disabled}:1 — deliberately not a readability claim,
  because WCAG exempts an inactive component, but the reader still has to see one
  — and shows why a label that clears {contrastFloors.secondary}:1 enabled can
  fall to 1.04:1 disabled. The editor does not edit the disabled roles, but every
  filled action is one of these pairs, so an action-fill edit can erase a
  disabled label.
- **The keyboard dim**: while one control holds keyboard focus the runtime paints
  every other focusable at 40% of itself, so a filled action's label composites
  into its own dimmed fill — as low as 1.27:1 in a shipped palette — and a
  reader who tabs away loses the words of the control beside them.
  `keyboardDimFailures` holds each of those pairs to {decorativeFloor}:1, deliberately not a
  readability floor: the dim is the runtime's where-can-Tab-go cue, so the claim
  is only that the label is still a label. A control whose text must stay
  readable opts out with `keyboardFocusDim: false`, which the library's filled
  actions do. The editor does not edit the dim, but every filled action is one of
  these pairs, so an action-fill edit can erase one.

The same role check guards the URL and `localStorage`: a persisted state that
carries a value the renderer cannot paint is rejected, and the editor falls back
to the selected style instead of restoring an edit that would paint black in
silence. A theme that merely misses a contrast, decorative, series, selection,
disabled-fade or keyboard-dim floor is a design choice the readout reports, not
a malformed state.

## Copy theme

**Copy theme** emits a `createTheme` module — one theme per mode, with the values
the preview resolved — in the exact format `@gpuixui/tokens` consumes, plus a
one-line usage note. Running the same audit on the result is up to the consumer;
`auditTheme` and the reports it folds — `invalidColorRoles`, `invalidShadowColors`,
`invalidNumbers`, `contrastFailures`, `decorativeFailures`, `seriesFailures`,
`selectionFailures`, `indicatorFailures`, `disabledFadeFailures` and
`keyboardDimFailures` — are public for exactly that.
