import { colorRoles, contrastFloors, indicatorSurfaces, seriesColors, seriesSurfaces, themes } from "@gpuixui/tokens";
import { previewMode } from "@/lib/platform";

A GPUIxUI theme is plain data. Components never carry a colour literal; they read
a semantic role such as `colors.primary`, `spacing.md` or `radius.md` from the
nearest `ThemeProvider`. Switching the provider restyles the subtree without
touching component code.

```tsx
import { ThemeProvider } from "@gpuixui/tokens/react";
import { darkTheme } from "@gpuixui/tokens";

<ThemeProvider theme={darkTheme}>
  <App />
</ThemeProvider>;
```

<Callout type="info" title="No OS appearance query">
  GPUix 0.11.0 exposes no OS appearance query. The application owns the mode and
  passes a resolved theme; there is no hidden `prefers-color-scheme` in the
  library.
</Callout>

## Theme shape

Every theme has the same fields:

| Field | What it decides |
| ----- | --------------- |
| `colors` | {colorRoles.length} semantic roles: surfaces, text, actions, status, borders, focus |
| `typography` | display, headings, body, label, caption, code and the font families |
| `spacing` | the spacing scale components use for gaps and padding |
| `radius` | `sm` through `xl` and `full` |
| `density` | control heights and horizontal padding for `sm`, `md` and `lg` |
| `elevation` | the shadow steps (`sm`, `md`, `lg`) |
| `borderWidth` | thin and strong boundaries |
| `iconSize` | the icon sizes paired with each type role |

## Colour roles

Roles describe intent, not a ramp shade. There are {colorRoles.length} of them; the families that
matter most on a page are:

| Role | Light | Dark | Use |
| ---- | ----- | ---- | --- |
| `background` | {themes.light.colors.background} | {themes.dark.colors.background} | window and application canvas |
| `foreground` | {themes.light.colors.foreground} | {themes.dark.colors.foreground} | default text |
| `card` | {themes.light.colors.card} | {themes.dark.colors.card} | raised content surface |
| `popover` | {themes.light.colors.popover} | {themes.dark.colors.popover} | menus, popovers and dialogs |
| `primary` | {themes.light.colors.primary} | {themes.dark.colors.primary} | primary action |
| `primaryForeground` | {themes.light.colors.primaryForeground} | {themes.dark.colors.primaryForeground} | text and icons on `primary` |
| `secondary` | {themes.light.colors.secondary} | {themes.dark.colors.secondary} | secondary action |
| `mutedForeground` | {themes.light.colors.mutedForeground} | {themes.dark.colors.mutedForeground} | secondary text |
| `accent` | {themes.light.colors.accent} | {themes.dark.colors.accent} | tinted emphasis surface |
| `hover` | {themes.light.colors.hover} | {themes.dark.colors.hover} | wash under a pointer |
| `active` | {themes.light.colors.active} | {themes.dark.colors.active} | wash under a press |
| `selected` | {themes.light.colors.selected} | {themes.dark.colors.selected} | wash behind a chosen row |
| `destructive` | {themes.light.colors.destructive} | {themes.dark.colors.destructive} | destructive action |
| `border` | {themes.light.colors.border} | {themes.dark.colors.border} | decorative borders |
| `borderStrong` | {themes.light.colors.borderStrong} | {themes.dark.colors.borderStrong} | essential control boundaries |
| `ring` | {themes.light.colors.ring} | {themes.dark.colors.ring} | focus ring |

The full catalogue, including the four status families and their soft pairs, is
in [`docs/tokens.md`](https://github.com/Cyberistic/GPUIXUI/blob/master/docs/tokens.md).
`colorRoles` exports the ordered list, so a docs table or a theme editor can
enumerate it instead of copying names.

</Callout>

## Data series

A chart series, a legend swatch or a heat-map region needs colour that carries
**identity**, not status: reusing `destructive` for a revenue bar would read as a
warning, and a hex per chart is the scattered literal the system forbids. A theme
therefore owns one categorical scale of {seriesColors(themes.dark).length}
colours, `seriesColors(theme)`, designed per mode and contrast variant. Every
colour is measured against the {seriesSurfaces.length} surfaces a plot is drawn
on (`background`, `card`, `popover`) at the {contrastFloors.boundary}:1 non-text
floor, and no two are closer than
`seriesDistinctnessFloor` in OKLab — contrast alone cannot tell a blue from a
violet of the same lightness. Both of those contracts assume full colour vision,
so every pair is also simulated for each `colorVisionDeficiencies` entry
(`protanopia`, `deuteranopia`, `tritanopia`) and held to
`seriesDeficiencyFloor`: two hues can read apart to one reader and collapse for
another, and only the simulation sees it.

<SeriesSwatches />

A theme that carries `series` replaces the scale whole; every other theme —
including the platform styles and the authored looks — resolves the scale for its
mode and contrast. The browser bridge publishes one variable per swatch
(`--series-1`, `--series-2`, …), so a preview charts in the theme the switch is
showing.
`seriesFailures(theme)` reports a broken scale, and `auditTheme` runs it beside
the contrast and decorative reports.

## Indicator marks

A component that **shows** rather than says something — a progress fill, a
spinner's lit dot, a slider's filled span, a switch's on-state, an avatar's
presence dot — paints a mark. A mark is neither text nor a boundary, so no
contrast pair covers it: `primary` was only ever measured against its own
on-colour, and a bar painted in a role that matches the page passed every other
report. `indicatorRoles` is the closed set a mark may use, and
`indicatorFailures(theme)` holds every one of them to the 3:1 non-text floor
(`4.5:1` in a high-contrast theme) on the {indicatorSurfaces.length} strips
`indicatorSurfaces` names
(`background`, `card`, `popover`, `muted`, `hover`, `active`, `input`): the page,
a card, a popover, a muted toolbar, the two washes a row tints under the pointer
and a field's own fill, which carries its caret.

A **status** mark does not paint the tone's solid fill. That role is a surface
designed to carry text — light `warning` is a pale amber with near-black text and
measures 1.78:1 on the page — so a dot or bar painted in it would be the one mark
nobody can find. A status mark paints the tone's readable role instead,
`statusTone(theme, tone).foreground`, which is the role a soft status surface and
a field error already paint.

## Built-in themes

The built-in themes ship with the package, and `getTheme` selects one by mode
and contrast:

```tsx
import { getTheme } from "@gpuixui/tokens";

const theme = getTheme("dark"); // darkTheme
const accessible = getTheme("dark", "high"); // high-contrast dark
```

Each theme is also published by name:

| Theme | Export |
| ----- | ------ |
| Light | `lightTheme`, `themes.light` |
| Dark | `darkTheme`, `themes.dark` |
| High contrast light | `highContrastLightTheme`, `highContrastThemes.light` |
| High contrast dark | `highContrastDarkTheme`, `highContrastThemes.dark` |

## Override a theme

`extendTheme` merges overrides into a base theme without mutating it;
`createTheme` starts from a built-in mode.

```tsx
import { createTheme } from "@gpuixui/tokens";

export const acmeDark = createTheme({
  mode: "dark",
  name: "Acme",
  colors: {
    primary: "#B49CFF",
    primaryForeground: "#1C1547",
    ring: "#9B8CFF",
  },
  radius: { md: 8 },
  density: "compact",
});
```

```tsx
export const acmeLight = createTheme({
  mode: "light",
  name: "Acme Light",
  colors: {
    primary: "#6A45F0",
    primaryForeground: "#FFFFFF",
    ring: "#7C5CFF",
  },
});
```

Only what changes is written. Every other role is inherited, so a brand cannot
accidentally drop a role a component reads.

A brand that overrides a fill owns two things, and it owns them **per mode**
because two jobs pull in opposite directions. A `primary` is a surface that
carries text, and it is also the role a progress fill, a spinner's lit dot and a
slider's filled span paint, so `indicatorFailures` holds it to 3:1 on the page,
a card, a popover and a muted strip. The saturated violet carries a white label
at 5.6:1 and measures 2.66:1 as a mark on the dark card — readable, and
invisible. So the dark brand takes a lighter fill a reader can find, and pairs
it with the near-black iris that fill can carry; the light brand keeps the
saturated violet, which is dark enough for both jobs there. The base theme's
`primaryForeground` was chosen for the base fill, not yours.

`auditTheme(theme)` is how that is caught before it ships: one call reports the
label pair, every boundary and decorative surface, the series, the selection
wash, each mark and the dim the runtime casts while Tab is elsewhere.
`packages/tokens/src/brand-theme.example.ts` is both themes
as a working file, type-checked and audited by the package's suite.

## Density

Density changes control geometry, never type. `compact` is for toolbars and
data-dense desktop surfaces; `comfortable` is the default.

```tsx
const compact = createTheme({ mode: "dark", density: "compact" });
```

## Scales

The geometry is data too: spacing, radii, borders, icon sizes and the density
presets. These specimens read them from the theme the platform switch resolves,
so macOS, Linux and Windows show their own radii and control heights. Values are
pixels at the surface; a component names the token, never the number.

## Platform styles

GPUIxUI ships one theme per platform. `platformTheme` keeps the base theme's
mode and contrast, and applies the platform's own type families, radius, density
and colour roles:

```tsx
import { platformTheme, themes } from "@gpuixui/tokens";

const windows = platformTheme(themes.dark, "win32"); // "Dark · Windows"
```

A high-contrast base keeps its own colours — contrast wins over platform — and
takes only the geometry and families. The UI face stays GPUI's `.SystemUIFont`
sentinel, which the runtime resolves to the operating system's own font, while
the monospace family is the one the platform installs (`Menlo`,
`DejaVu Sans Mono`, `Consolas`). `default` is the library's own identity, for a
platform it does not name.

in the page URL, so a link carries it:

A preview renders the selected style's **{previewMode}** palette, whatever the
site's own light/dark switch says. A preview is a picture of the library's
identity, and that identity is its dark theme; the switch a reader came here to
compare is the platform. Both palettes are on this page — [Built-in

style's roles, radii and family, and switching re-bases its preview without
discarding what you edited — only the roles you touched are pinned. That is the
[copy-and-own contract](#take-one-and-make-it-yours) with a live output.

### The look picker

Beside it, **Look** applies one of the authored styles `@gpuixui/tokens` ships —
**Platform** (the platform's own style), **Windows XP (Luna)** or **Windows 7
(Aero)** — over whatever the platform switch resolved. A look is data of the
same shape as a platform style (`retroStyles`), applied with `applyStyle`, so
the preview paints the look's palette, radii, density and monospace family
rather than a docs-only skin. It is remembered the same way and written to the
URL as a second parameter:

```text
https://gpuixui.sudokw.com/docs/components/button?platform=win32&look=luna
```

A look is **not a fifth platform**: `platformNames` stays the persisted key for
the operating systems an application runs on, and the mission's toggle stays
macOS · Linux · Windows · Default. A look is the extension mechanism in
practice — the same table a consumer can edit to ship their own style.

Both axes resolve through one theme, and the surface a preview renders on
carries it as CSS variables from the same bridge the theme editor uses. Nothing
is a docs-only style sheet: the variables are `@gpuixui/tokens` values, and a
preview cannot paint a colour the library does not have (a test holds the
preview style sheets to that).

<Callout type="info" title="What a variant changes">
  The type families, the radii, the density and the platform's colour roles —
  `primary`, the surfaces, the borders and the focus ring. Switching this page
  from macOS to Windows changes the surface colours, the corner radius and the
  monospace face of every preview, because each variant is a real
  `@gpuixui/tokens` theme.
</Callout>

<Callout type="warn" title="Browser previews are illustrative">
  The library renders through GPUix, not the DOM. A preview shows the geometry,
  palette and states of the native component in a browser; it is not the native
  surface. The shipped component is the one in the Code tab.
</Callout>

### Take one and make it yours

A platform style is data, not a compiled preset: `platformStyles` holds each
platform's colour roles, radius scale, density preset and type families, and
`platformTheme` applies them to a base theme. A consumer who wants a platform's
geometry with their own brand edits the values it names and ships the result —
there is no hidden layer to fight.

```tsx
import { extendTheme, platformTheme, themes } from "@gpuixui/tokens";

// Windows' controls, your accent and corners.
export const house = extendTheme(platformTheme(themes.dark, "win32"), {
  name: "House",
  colors: {
    primary: "#B49CFF",
    primaryForeground: "#1C1547",
    ring: "#8A6EFF",
  },
  radius: { md: 6, lg: 10 },
});
```

Only what is written changes: every other role, the density and the type
families come from the platform style, and the base theme is untouched. Three
things a brand owns when it overrides a fill:

- **The on-colour.** A fill and the text on it are a pair; the base theme's
  `primaryForeground` was chosen for the base fill. The snippet sets both.
- **The mark.** The same `primary` is what a progress fill, a spinner's lit dot
  and a slider's filled span paint, and `indicatorFailures` holds it to 3:1 on
  the page, a card, a popover and a muted strip. A fill dark enough to carry
  white text is often too dark to be found on a dark card — the saturated
  violet measured 2.44:1 there — so a dark brand lightens the fill and takes the
  near-black label that fill can carry. The colour a platform you start from
  paints its own card changes the number, which is why the pairing is yours.
- **The measurement.** `auditTheme(theme)` runs every contract the package runs
  on its own themes — roles, shadows, text pairs, decorative surfaces, the
  series, the selection wash, the marks and the keyboard dim — and reports each
  failure by name, so the check a brand runs is the check the library runs on
  itself.

`packages/tokens/src/platforms.example.ts` is the working version of this
snippet (`resolveHouseTheme`), executed by the package's suite in both modes.
`src/lib/platform-page.test.ts` executes this page's snippet against the same
contract, so a copy from the page is a theme that passes.

## Read the theme

`useTheme` returns the nearest theme, or the light theme when no provider
exists. Components use it internally; an application can use it for its own
layout without duplicating a colour.

```tsx
import { useTheme } from "@gpuixui/tokens/react";

const theme = useTheme();
const muted = theme.colors.mutedForeground;
```
