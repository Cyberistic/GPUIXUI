---
title: Patterns
description: Realistic compositions, not isolated controls.
---

Patterns are where components meet real tasks: a settings page with validation,
a confirmation flow, a searchable command menu, a data table with filters. Each
page shows the composition, explains the state it owns, and says which parts are
verified in the native runtime.

## Settings form

The first pattern is the workspace settings screen from
[`examples/basic-app`](/docs/patterns/settings-form): labelled fields with live
validation, a select, three kinds of selection control, save progress, a loading
skeleton, a tooltip and a light/dark switch, all composed from the public
primitives. It is type-checked and its source is the real application file; it
has not been launched natively.

## Still to come

The confirmation flow and the command palette have every component they need —
`ConfirmDialog`, `CommandMenu`, `Dialog`, the form parts and the toast system
are implemented and native-tested. They wait on one **runnable composed example**
(`ConfirmDialog` + a form + `Toast`; `CommandMenu` + `Dialog`), because a pattern
page is never assembled from separate component demos.

An inspector workspace waits on `packages/docking`, which does not exist yet.

A pattern is never assembled from browser imitations and presented as working
native behaviour.
