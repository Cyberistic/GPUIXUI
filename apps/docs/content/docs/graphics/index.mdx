Everything the library draws lives here: the **charts** on the GPU, the
**icons** in the set, and the **diagrams** from a Mermaid source.

One category, because a reader looking for "the pictures this library makes"
should not have to know which package owns them.

## The three

| Page | What it is | Painted by |
| ---- | ---------- | ---------- |
| [Charts](/graphics/charts/charts) | bar, stacked bar, line, area, composed, pie, donut, radar, radial and sparkline charts | [TanStack Charts](https://github.com/TanStack/charts)' scene compiler |
| [Icons](/graphics/icons/icon) | the monochrome glyph set, its size scale and its two accessibility rules | the library's own set |
| [Diagrams](/graphics/diagrams) | a Mermaid source, drawn as a diagram | [Pele](https://pele.run) |

## One paint path

The charts and the diagrams reach the frame the **same way**: a scene — a
renderer-neutral list of shapes — compiles to **one SVG document**, and the
runtime's own renderer paints that document as **one image**.

That is why a chart can hold **two series' colours in one element** and a
diagram can hold a dozen shapes in one picture: the document carries each
shape's own fill, and the runtime's decoder honours it. The older route — an
`<svg source>` per series — paints **one tint** for the whole element, so a
chart drawn that way is one element per colour.

The cost of the route is the same for both: an image is a picture, so a shape
inside it is not an element of its own. The charts answer that with a **named
element per series**, which carries the series' name, its values and its
colour; the diagram's name rides the same element.
