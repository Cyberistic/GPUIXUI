The application owns the mode and passes a resolved theme to `ThemeProvider`.

```tsx
import { useState } from "react";
import { getTheme, type ThemeMode } from "@gpuixui/tokens";
import { ThemeProvider } from "@gpuixui/tokens/react";

export function Root() {
  const [mode, setMode] = useState<ThemeMode>("dark");
  const [contrast, setContrast] = useState<"default" | "high">("default");

  return (
    <ThemeProvider theme={getTheme(mode, contrast)}>
      <Workspace onToggleMode={() => setMode(mode === "dark" ? "light" : "dark")} />
    </ThemeProvider>
  );
}
```

## Follow the desktop's palette

A desktop hands over a small `SystemPalette` — a page, an ink, an accent, a quiet strip, a border, an error colour and a selection colour — not a `Theme`. `paletteToTokens(palette, base)` maps the roles the palette names and keeps the base's value for every role it does not, so two colours produce a page and an ink rather than a half-built theme. `paletteMode(palette)` returns the mode the palette states and otherwise reads it from the page's lightness — including a stated mode this release does not ship, such as the upper-cased `Dark` a consumer's decoder writes, an old release's name or a `null` a store kept, because the call site below hands the answer straight to `getTheme`, which refuses a name it does not know. A palette that names no page, or a page in a colour form this library cannot measure, has no mode, so the caller's own default stands.

```tsx
import {
  darkTheme,
  getTheme,
  paletteMode,
  watchSystemTheme,
} from "@gpuixui/tokens";

const stop = watchSystemTheme({
  read: () => readDesktopPalette(),
  base: darkTheme,
  baseFor: (palette) => getTheme(paletteMode(palette) ?? darkTheme.mode),
  onChange: setTheme,
  every: 2000,
});
```

The runtime pins no file watcher, so `watchSystemTheme` is a **poll**: `read` is called on every tick, `every` is the interval in milliseconds, `base` is the theme a palette is mapped onto and `baseFor` picks a different base when the desktop switches its light and dark themes. `onChange` receives the resolved theme; `timer` replaces the default `intervalTimer` when the application owns its scheduler, and the returned function cancels the poll. A tick re-applies only when the palette changed, and a change is recorded once `onChange` returns — a callback that throws reaches your boundary and the same palette is offered again on the next tick.

A palette's selection is a **fill** on the desktop and a translucent **wash** here, because the run inside it keeps its own text role. An opaque value is restated at the base theme's own share, so the hue is the platform's and the readability is the theme's.

On Linux, Omarchy's `colors.toml` decodes through `decodeOmarchyPalette(source)`. It reads the file's own names (`red` → `destructive`, `muted` and `color8` → both `muted` and `border`, `accent` and `color4` → `accent`) and answers `problems` for every line it could not use, so a file outside the flat format is a visible mix of the palette and the base instead of a silent one.

Run `auditTheme(theme)` on the result before shipping: a system palette is not a designed theme, and the reports name the pair, mark or wash it cannot serve.

## Restore a stored theme

A theme read back from storage is decoded, not assumed: `missingTokens(theme)` lists the numeric parts it lost — a whole `group`, a `step` inside one, or a `family` that names no face — before `auditTheme` refuses it, so a restore path can open the default instead of handling a thrown error.

```tsx
import { lightTheme, missingTokens } from "@gpuixui/tokens";

const stored = decodeStoredTheme(raw);
const theme = missingTokens(stored).length === 0 ? stored : lightTheme;
```
