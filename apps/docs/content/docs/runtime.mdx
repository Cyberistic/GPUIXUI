---
title: Runtime capabilities
description: What the pinned GPUix runtime provides, what it does not, and the honest workaround for each gap.
---

The library pins `@gpuix/react` / `@gpuix/native` at **0.11.0**. This page records
what that runtime provides, what it does not, and the strongest honest alternative
for each gap. `@gpuixui/runtime` encodes the same matrix in code — `capabilities`
and `unsupportedFeature` — and its compile-time guards fail the build the moment
the runtime adds a key the matrix claims is absent, so the table below cannot go
stale silently.

## The matrix

| Capability | Status | Workaround |
| ---------- | ------ | ---------- |
| Terminal rendering | Supported | `render(<App />, { terminal: true })`, or set `GPUIX_TERMINAL=1` |
| Headless `Dialog` | Supported | `@gpuix/react/dialog` owns the Escape layer and the Tab trap |
| Tab / Shift+Tab focus | Supported | Default; `preventDefault()` keeps one Tab |
| `transform` | Not supported | Animate motion with `@gpuixui/motion`; static rotation/scale is unsupported |
| Grid span | Not supported | Size the track with `gridTemplateColumns`/`gridTemplateRows` or an explicit width |
| Canvas drawing | Not supported | Render `svg` or compose `div`/`svg` primitives; no retained draw API — a `<canvas>` also tracks no painted bounds (`content-surfaces`) |
| IME composition | Not supported | Compose at the application layer from `onInput`/`onKeyDown` |
| Global shortcut | Not supported | Window-level `onKeyDown`; background hotkeys need a runtime change |
| Tray / menu bar | Not supported | Ship an in-window menu; a system tray needs a runtime change |
| Native view / webview | Not supported | Use `markdown`/`code`/`diff` surfaces |

## Measured in a window

Some limits are not in the matrix above, because the matrix is built from the
runtime's own typings and these were measured by a probe that paints: the type
does not say them, so a reader must not infer them from the table's silence.

| Gap | What a window measured | Use instead |
| --- | ---------------------- | ----------- |
| Sticky positioning | `position: "sticky"` paints nothing — a sticky sample inside its scroller moves by exactly the scroll amount, so it behaves like `relative` (`data-grid-fixed-header`) | put the header **outside** the row scroller as a sibling, and wrap header and rows in one `overflowX` scroller so both move together |
| Floating layer placement | `side="right"` paints the panel one 6px gap off the anchor's right edge and `side="left"` mirrors it; `align="start"` holds the panel's top on the anchor's top; but **`align="center"` ends the panel at the anchor's centre line** rather than centring it, so the panel starts half its height low (`floating-sides`). The headless `floating-placement` scenario drives the `TestRenderer`, and the two can differ | use `side` with `align="start"` when the box matters; for a genuinely centred panel, offset it yourself by half its measured height, as the overlay components do |
| Select option reveal | a list paints in its own layer one 6px gap below the trigger's start edge, takes the focus, opens on the selected row, moves the highlight with the arrows (wrapping past a disabled row), selects on `Enter`, and dismisses on `Escape` (focus returns) or an outside press (`select-lifecycle`). What a keyboard cannot do is **reveal** a row past the list's edge: the runtime sets no max height or overflow and its two scroll-button parts are empty in 0.11.0, so a 40-option list is a 320px scroller the **wheel** moves (`-200`) while twenty `ArrowDown`s leave the offset alone (`fields.runtime.test.tsx`) | cap the surface and make it a scroller (the shipped `Select` caps at 320px); keep a keyboard-critical list short, or use a `Combobox`/`SearchInput` composition where the query narrows it |
| Frozen column | no sticky, so a frozen first column is **composed**: its own vertical scroller beside the grid's, mirrored in both directions through `onScrollChange` → `scrollTo` (a 120px label pane and a 240px grid stay on the same `y` at `-300` and `-600`; the row under the reader keeps its `y`; a press on a frozen cell selects the row for the whole grid; a `deltaX` wheel pans the grid and leaves the column still; a `-10000` wheel clamps both at `-1440`) (`data-grid-frozen-column`), and in a window the mirror lands in the **same frame** as the wheel because `scrollTo` paints synchronously, the sideways pan stays the grid's alone, and a press on a frozen cell selects the row for the grid (`frozen-column-lifecycle`) | give each pane its own scroller, mirror offsets through `onScrollChange` and guard the echo with a **ref** (`scrollTo` paints synchronously); pan horizontally on the data pane alone — there is no single-scroller freeze |
| Dock keyboard navigation | the keyboard order across a dock's layers: one Tab stop for the whole rail (the selected trigger) between the sidebar's actions and the pane's first field, then the status bar. A closed sidebar paints 0 wide, yet its unguarded control keeps its tab stop, still reports its own 12px box inside the zero-width parent and still accepts `focusElement` — the pointer is clipped away but the keyboard is not; a control given `tabIndex={-1}` is skipped by the same traversal and returns when the pane reopens. A rail step moves the selection **and must move focus itself**, and the pane's field owns its arrows (`dock-focus-lifecycle`) | one stop per rail through a roving `tabIndex` and one per pane; `tabIndex={-1}` on a closed pane's controls, because the runtime does not skip a control whose parent paints nothing; call `renderer.focusElement` from the rail's key handler; give the dock its own rail chords, or leave the arrows to fields |
| Menu anchored in a scroller | a dropdown whose trigger sits in a horizontally scrolled header keeps its place: a −100 wheel moves the trigger and the panel **together in one read**, `Escape` returns the focus to the trigger, `Enter` opens it on the first item and a second `Enter` hides that column, and it still opens after the header shrinks (`header-menu-lifecycle`). Two measured rules: anchor arithmetic uses the **cell**, not the trigger element — the trigger paints 22px inside its cell, so a width read from the trigger's box is 22px out — and hiding a column **before** the anchor moves it while hiding one after it does not | anchor the panel from the header **cell**'s box and let the shipped dropdown place it; keep the trigger outside the columns a reader can hide, or re-place it as they do |
| Table sort and selection | a table is flex rows of fixed-width cells, and both interactions work with no table primitive: a press selects the record it hit **and that row holds the focus**, so the next key reaches that row's own handler; `down` roves focus and selection together; a header press sorts by the column it hit and a second press flips the direction while the selected **record** survives the sort; the header keeps its painted `y` while the rows scroll under it and a wheel over it scrolls nothing, because it is a sibling outside the row scroller; and one `overflowX` box pans header and cells together, staying aligned (`table-lifecycle`). The measured constraint: a sortable header whose painted centre is clipped by the horizontal viewport sorts nothing, because a press is aimed at the element's centre | key sort and selection by **record**, never by row index; give each row `tabIndex={0}` and move focus with `focusElement` from the row's own key handler; keep the header a **sibling above** the row scroller inside one `overflowX` box; keep a sortable column's centre inside the frame, or pan the header first |
| Dock reflow | a split is pointer capture over a caller-owned width: a divider keeps the drag 80px outside its 6px box and nested levels keep independent widths (`split-pane-lifecycle`, `docking-nested`). A dock's re-clamp signal exists: when a 120px sidebar takes 100px from a flexible centre, the centre's `onLayout` fires again and its settled payload is the painted box (`w=240`, equal to `bounds`) — but the reflow's **first** pass reports the box the pane still has (`w=340`, `reports=2`) and a pane whose box did **not** change is still reported to (`dock-reflow`) | subscribe to **both** `onMouseDown` and `onMouseMove` on the divider so capture arms; re-clamp from the width the payload carries and make the handler idempotent rather than treating every report as a change; a dock passes its own bounds, since a split's `max` is the caller's number |
| Window size | `getWindowSize()` is the box the layout fills, and `useWindowSize()` reports the same pair: a 900×520 window with a fixed 120px sidebar and a flexible centre reads 900×520 on both channels with the centre at 780, `zoomWindow()` takes it to 1680×923 with the centre reflowing to 1560 and `onLayout` reporting again, and a second call restores 900×520 (`window-resize-reflow`). The 800×600 constant fails that arithmetic. The app channel samples every 100ms, so it **lags** an animated zoom (`expected 1680, got 900`), and the binding publishes no `setSize` | read the size for arithmetic — a split's `max`, a dock's own width — and re-clamp on `onLayout`, which the resize runs again with the new box; wait for `useWindowSize()` after a programmatic zoom instead of reading it in the same tick |
| Window chrome | the runtime reserves **no** titlebar: `getWindowInsets()` and `useWindowInsets()` agree on the `safeArea`/`ime`/`effective` edges (the channel samples every 100ms, so poll it rather than reading it in the mount's tick), all `0,0,0,0` on this host while no keyboard is up, a bar at `top: effective.top` starts and paints there (±1), and the app's own bar is the capture's **first row** — so the layout starts at the window's top edge. A transparent titlebar changes neither the insets nor that origin (`window-chrome`). Two limits: whether the OS titlebar is hidden is not app-visible (no API reports it, and a capture is the app's own scene), and an IME inset cannot be measured because the window protocol cannot start an IME session | paint your own chrome — a titlebar-integrated toolbar keeps its own constant (28pt on macOS) and paints over the top edge, because `trafficLightX`/`trafficLightY` are **inputs** rather than a reported safe area; inset only by the reported `effective` edges, which carry what the OS knows and the app cannot (a notch's safe area, an on-screen keyboard) |
| Second window | a process gets **one** window: `init()` opens it and a second call fails with `A GPUI application already exists on this thread`, which is why each backdrop mode is its own CLI run (`window-backdrop`), and the renderer publishes only verbs on that window — activate, minimize, zoom, fullscreen, title | keep a detached tab, an inspector or a second document inside the one window — a pane, a layer, or a `createPortal` surface; no method opens another OS window |
| Window backdrop | `windowBackground` is honoured: an `opaque` window's unpainted surface carries alpha **255** while `transparent` and `blurred` both carry **0**, with the app's painted box identical in all three (`rgba(217, 67, 43, 255)`, a 900×520 window captured at 1800×1040 — the display's 2× scale) (`window-backdrop`). Two limits: the app's capture of `blurred` is **byte-identical** to `transparent`, because the vibrancy is composited behind the window, so no app frame proves the blur; and one window per process (`A GPUI application already exists on this thread`), so each mode is its own run. A translucent fill is composited against that surface — `#D9432B80` painted `rgba(109, 34, 22, 255)` on an opaque window | let the **unpainted** area carry the translucency and paint the content opaque; take `"blurred"` for the effect but confirm it by eye on the target OS rather than from a capture |
| Caret position, selection ranges and code decoration | the arrow keys move the native caret and `getSelectedText()` returns the selected text, but nothing reports *where* the caret is or what range is selected, and `<code>` takes `language`/`showLineNumbers` with no decoration layer (`editor-surface`) | edit in a `<textarea>`, display in `<code>`; a highlighted *editable* surface is not buildable |
| Window-level key events | `render({ onKeyDown })` is the app-level path: a `cmd-k` reached the app handler and opened a palette (`open=true last=cmd-k`) whose text painted, `Escape` closed it, and after a press on another element (`getFocusedElementId` named it, not the probe) `cmd-k` still opened the palette (`window-shortcut-lifecycle`). The element's own handler runs first and the window handler after it, with `event.modifiers` set (`window-key-shortcut`) | install one window handler at the root and route accelerators through it; a chord a field needs is the field's to consume. A background hotkey has no path — keys fire only while the window is focused |
| Keyboard focus events | a `Tab` traversal **does** run React's `onFocus`: the traversal reaches a tooltip's trigger and the tip opens, and `Tabs` counts `focuses=1` for the same traversal (`tooltip-lifecycle`, `tabs-lifecycle`). An earlier run read the frame before the event arrived and recorded the opposite | open a focus-only surface from `onFocus`; a key *move* that needs its origin reads the key event's own `elementId` or `getFocusedElementId`, because the first arrow after a traversal must move off the tab it reached |
| Scroll event payloads | `onScroll` reports the wheel **input**, not the travel — a `-100000` wheel reports `-100000` after the offset moved 200px and clamped — while `onScrollChange` reports the clamped absolute `scrollX`/`scrollY` pair `getScrollOffset` returns (`scroll-lifecycle`) | a scrollbar, a saved position or a follow-the-tail scroller reads `onScrollChange`; `onScroll` is the gesture's own delta |
| Nested scrollers | `scroll` does not stop at the innermost scroller: **one wheel moves every scrollable ancestor** on the hit path by the same delta. In a 320×140 list inside a 420×260 page, a `-100` wheel over the list moved the list to `-100` **and** the page to `-100` while the list still had 240px of travel; a wheel over a filler row below the list moved only the page; a `-100000` wheel clamped the list at `-340` and the page at `-360`, each against its own content; and the page's `onScroll` heard all three wheels, two of them aimed inside the list (`nested-scroll-lifecycle`). There is no wheel handler and no `preventDefault`, so a pane cannot stop the wheel reaching its page | keep the workspace itself **non-scrolling** and let each pane own its scroller — size the dock to the window instead of wrapping it in a scroll root. Read each scroller's own `onScrollChange` offset rather than an ancestor's `onScroll` event, which fires for wheels aimed inside its descendant |
| Horizontal scrollers | `overflowX: "scroll"` is a real horizontal scroller: in a 320px viewport holding 18 × 80px columns, a `deltaX = -160` wheel moves the strip left and leaves `y = 0`, `onScroll` reports the `deltaX`, and a `-4000` wheel clamps exactly at `-(18 × 80 − 320) = -1120` (`scroll-horizontal`) | put a wide table, tab rail or code block in its own `overflowX` scroller; a horizontal gesture moves one axis only, so a pane needing both axes sets both overflow values |
| Revealing a selection | the runtime does not scroll a selection into view: pressing `End` in an eight-tab, 320px rail selected tab 7 while the rail stayed at `x = 0` and the tab's box started past its right edge (`x ≥ 320`). The selected element's own `scrollIntoView()` moved the rail to `x = -320` and painted it wholly inside — but the call scrolls the nearest ancestor scroller to the **index of its direct child**, so a rail whose tabs sit in a wrapper row moved only `x = -1` (`tab-overflow`) | call `scrollIntoView()` on the selected element after the change and keep tabs or rows as direct children of the scroller — a wrapper row makes the selection unreachable, so a reveal is a layout fix, not a second call |
| Drag auto-scroll | the runtime does not scroll a pane because the pointer rests near its edge: an eight-move drag inside a rail's 24px band left the plain rail at `y = 0`, while a rail whose `onMouseMove` reads its own `getElementBounds` and calls `renderer.scrollTo(id, 0, offset - 16)` moved to `y = -128`. `scrollTo` paints synchronously, so state written after the call is not committed when the drag returns (`moves=0` while the offset reached `-128`) (`drag-autoscroll`) | own the band, the step and the clamp: read the pane's own bounds, hold the next offset in a **ref**, and increment before calling `scrollTo`; nothing scrolls on its own while a tree or list is dragged |
| Pointer capture | the runtime arms capture on a left press **only** for an element that listens to both `onMouseDown` and `onMouseMove`: the paired sample kept all eight moves and its release 120px outside its box, while a move-only sample got the pre-press move and the sibling received the eight, and the shipped `Slider` followed a drag off its track (`pointer-capture`) | a drag handle, splitter or slider subscribes to **both** `onMouseDown` and `onMouseMove`; a move-only element captures nothing and the element under the pointer resolves the drag |
| Text selection | a **pointer** drag over a selectable `Text` paints the wash and `getSelectedText()` reports the run, `Cmd+C` pastes that run into a field and `clearSelection()` clears it, while a default `Text` paints none (`selection-lifecycle`) | give a selectable line a box that hugs its glyphs (`alignSelf: "start"`) — a press past the last glyph selects nothing; a component may offer "select and copy", but an **initiated** copy has no API (`clipboard-lifecycle`) |
| Cross-pane drag | a drag across two panes is composed from the panes' listeners, and the whole gesture — press, eight moves, release — arrives **before** React commits the render the press scheduled: a handler that gated on a `dragging` **state** saw `false` for every move and the drag never started, while a synchronous press flag let each pane resolve the drop (`drag-between-panes`). The dragged item there listens to `onMouseDown` alone, so it captures nothing and the pane under the pointer receives the travel (the `pointer-capture` rule) | hold the press flag in a **ref** and state only for the readout; subscribe to `onMouseMove` on the element that must follow the pointer past its own box, or listen on the panes for a "drop on whatever is under the pointer" model |
| Drag reorder | a reorderable row that listens to both `onMouseDown` and `onMouseMove` captures the pointer, so **no other row hears the release** (`heard=0`): a press on `alpha` and a drag onto `delta`'s label reorders the list to `bravo,charlie,delta,alpha`, and the painted rows take each other's `y`, so it is a real move rather than a relabelled string. The hit test reports the label **above** the row first (`top=other`), so the drop is the first id `getElementsAt` reports that belongs to a row — reading only the topmost id gives `over=none misses=1` — while a release outside every row is a miss and leaves the order alone (`drag-reorder`). Without `onMouseMove` capture never arms: the target row hears the release (`heard=1`) and nothing reorders | subscribe to **both** listeners on the row being dragged, keep the press flag in a **ref**, and resolve the drop by scanning `getElementsAt` for a row id rather than trusting the topmost one. There is no drag host feature — no drag image, no cross-application payload and no drag between windows (one window per process); an OS file drop is `onFileDrop` |
| Keyboard focus dim | while one element has keyboard focus the runtime fades every other focusable to **40%** — fill and label — per element and on by default, and `keyboardFocusDim: false` opts one out (`keyboard-focus-dim`): the shipped filled actions keep all 66 008 fill pixels while a ghost's 611 label pixels go to 0 and a caller's `style` can put the cue back (`filled-action-dim`). **A focused text field casts no dim**: `renderer.rs`'s focus path returns nothing for an `input`/`textarea`, so nothing dims while a reader types | a filled action or a field's value declares `keyboardFocusDim: false` (the library's filled buttons do, through `paintsFilledSurface`); a control with no fill keeps the cue, because it is what tells a reader where Tab is — and a faded label can measure as low as 1.27:1, so text that must stay readable opts out |
| Inline SVG | `<svg source>` paints, but as **one tint** — the whole markup is masked in `style.color`, so a shape's own `fill` never reaches the frame; five stacked `<svg>` elements each paint their own tint while `<text>` inside the markup paints (`content-surfaces`) | stack one `<svg>` per colour, so a multi-series chart is one element per series; labels can live in the markup |
| Image bytes | `<img>` paints a path, an http(s) URL and a data-URL PNG; a pixel buffer set through `ref.setImagePixels` paints **only from a layout effect** — a passive `useEffect` leaves the element's `img: no src` fallback (`content-surfaces`) | upload pixels before the frame paints (the waveform example's `useLayoutEffect` pattern); a data URL needs no timing |
| Chart surfaces | a chart has no host element and no drawing surface, so it is composed: a `setImagePixels` buffer keeps each pixel's own colour — three series paint `#2ECC71`/`#3498DB`/`#E74C3C` inside **one** element, which a tinted `<svg source>` cannot do — its transparent margin composites onto the card behind it, a second buffer replaces the frame whole on a data change with no re-mount, and `setImage` decoding SVG **bytes** paints every `fill` its own colour (`chart-raster`). Two limits: a translucent bar over another bar is unmeasured, and the element scales its buffer to its box | raster a multi-colour plot through `setImagePixels` from a **layout effect** and re-push it on new data; take `setImage` with SVG bytes for a vector plot; compose axes and legends as `<text>` beside the image, since the raster carries only the marks. `<svg source>` is one tint, so it is never the multi-colour route |
| Virtualized list | **Two modes.** The children form retains every row and skips only the off-screen build and paint. The **`itemCount`** form (`itemCount` + `estimatedItemHeight` + `windowStart`) mounts only the slice the app renders: 100 000 logical rows with a 60-row window retain just the window (`wrow-60` absent), the estimate positions mounted rows the paint never reached, `onVisibleRange` reports **absolute** indices (`20..27`) but lags the paint by one gesture (the paint had reached `40..46`), a press reports the row's absolute index, and `scrollToItem(90000)` paints `File 90000` at `-90000 × 28` after the app moved its window (`virtual-list-windowed`). In the children form `scrollToItem` reveals a row that was never mounted and fires **no** `onVisibleRange`; changing the row count reports ranges computed against the spliced child list (`1..2`, `0..1`), not the painted rows; and roving focus moves through `renderer.focusElement` (`virtual-tree-lifecycle`). Either way `onVisibleRange` describes the **previous** scroll — rows 13–21 paint while its report still reads `first=0 last=9` (`virtual-list-lifecycle`). Rows **may differ in height**: 400 rows cycling 24 / 48 / 72px each paint their own height and start where the previous ended, `scrollToItem(150)` lands the row at the viewport's top edge from estimates, and growing row 0 by 40px while the reader sits at row 150 leaves the painted rows and the offset untouched — a row outside the window is not remeasured until it paints again (`virtual-list-rows`) | reveal with `scrollToItem`; in `itemCount` mode move the app's `windowStart` **first** and scroll after that commit, since the window is app state native cannot infer. Size the window wider than the viewport plus overdraw (60 rows against 280px) so the one-gesture lag cannot expose empty estimate boxes. Measure an expandable or streamed row while it is **on screen** — one that grows outside the window keeps its old height until it paints again. Read the painted rows or the anchor, not the index; never paginate from `onVisibleRange` across a row-count change; a tree keeps one focus and moves it with `focusElement` |
| Expandable rows | a painted row that grows is re-measured on the **next frame** with no scroll and no offset change, and the rows above do not move; the rows below shift by the growth (row 4 paints at `row 3 + 120` after one wheel, and a press lands on it, so the shift is not a stale hit test); a growth that leaves less than one 32px row of the 240px viewport **drops the following row out of the painted window** until a scroll, because the list paints whole rows; the opened row keeps its 120px after leaving and re-entering the window; and the grown height joins `scrollToItem`'s estimate (`virtual-list-expand`) | an expansion needs no remount or forced re-layout — but size an expandable table's viewport (or overdraw) against the **open** row height, and measure a row while it is on screen: one that grows outside the window is not remeasured until it paints again (`virtual-list-rows`) |
| Loading-row restore | a paginated history's **loading void** is the list's anchor, so a splice replaces the screen the reader was reading: a prepend left to the runtime painted the arriving page at the pixel the reader's message held (`y=80`) and the message left the screen, while an app that read `getListScrollTop` before the commit and re-anchored kept that message at `y=80` with the page filling `0..80` (`loading-row-correction`). At the at-end sentinel (`itemIndex == row count`) the page painted at `y=0` unless the app pinned its first row on the void's old top edge (`y=80`), where the message above kept `y=40`; a second prepend page needed **no** correction because the anchor was then a message row, and the append rule fired again after wheeling back to the end (`corrected=2`). The read names the row at the viewport top **after** layout, not the request | read the anchor before the commit and re-anchor after it — `scrollToItem(voidRow + 1 + pageRows, offset - edgeHeight)` under a top void, and `edgeHeight - viewportHeight` at the end sentinel — correcting only while the void is the anchor; `flushSync` the splice before the scroll, because a `scrollToItem` beside the state update resolves against the old list |
| Portals (`createPortal`) | a portalled card paints inside its **target's** box and outside an ancestor's clip, keeps the provider context above the caller, receives a pointer press and keys typed in its field, and unpaints when detached (`portal-layer`); `getPaintedText` still lists a clipped sibling's glyphs, and a clip only holds when the clipping box is the child's containing block | prove a clip with a capture rather than the paint report, and give the clipping box `position: "relative"`; a portal moves content within the one window — the binding opens one window per process, so a tab cannot detach into its own |
| Animated geometry | `motion` tweens painted geometry and lands exactly on a numeric target: a 120×40 box with a 3s `easeInOut` transition painted `40, 43, 117, 123, 221, 240, 240, 240` across eight presses and settled at 240×240, `onMotionComplete` fired once per run, and the reverse run tweened too (`motion-geometry`). The animated box **clips** its content instead of reflowing it — a fixed 320×200 child kept its size while the box was 120×40 and while it was 240×240 | animate an **outer** box with `overflow: "hidden"` for a collapsing sidebar or a growing row, since the content inside stands still; read `onMotionComplete` to unmount or unlock after a run; `duration: 0` paints the two target sizes with no frame between them, which is the negative control |
| Clipboard | the binding has no clipboard read or write, and the keys do not cross the window seam: `cmd-a`/`cmd-c`/`cmd-v`/`cmd-x` reach a focused field's `onChange` — select-all, copy, paste and cut all work — but never reach the app's window handler, while `cmd-k` from the same control does (`clipboard-lifecycle`) | an app-level "copy" action is not buildable; offer the text in a read-only field the user can select and copy from |

## Measured offscreen

One measurement is not a window fact: the accessibility tree is read from the
offscreen `TestRenderer`, because a window's automation protocol has no a11y
verb. It is listed apart so the section above stays a record of paints.

| Capability | What the test renderer reported | Use instead |
| --- | ------------------------------ | ----------- |
| Accessibility tree | the role reaches the platform under its **own** name — `button` is `Button`, `option` is `ListBoxOption`, `heading` is `Heading`, `progressbar` is `ProgressIndicator` — while `aria-label`/`aria-description`/`aria-id` land on `label`/`description`/`author_id`, `aria-selected`/`aria-expanded`/`aria-level`/`aria-valuetext` on `selected`/`expanded`/`level`/`value`, and `onClick` + `tabIndex` surface as `Click` and `Focus` (`a11y-tree`). A `<text>` is a `Label`. **A node needs a role to exist**: a `div` with only an `aria-label` paints no node and `role="none"` is dropped | give an element that must be announced both a `role` and its label, and assert the platform's role name rather than the token you passed; carry a state in `aria-valuetext`, since there is no `aria-checked`/`aria-valuenow` and no live region to announce a change |

## Not in the typings

The matrix above is built from `@gpuixui/runtime`'s own keys. These seven are
different: the pinned typings declare neither the host nor the prop — or no
public method takes one — so there is nothing to pass and no probe to run — a
component composes the alternative instead. `COMPONENTS.md`'s rows rely on each
of them.

| Capability | What the pinned typings have instead | Use instead |
| --- | --- | --- |
| Links (`href`) | `ElementType` has no `a`, and `HostProps` declares no `href`; the Breadcrumb, Navigation Menu and Lists inventory rows record the same absence | render a pressable `<text>` (the link-styled button) and show the destination in the copy; there is no visited state, middle-click or pointer cursor |
| Form grouping (`fieldset` / `legend`) | `ElementType` has no `fieldset`; the shipped `Fieldset` is a `role="group"` div with a legend-styled text | compose it from a div and a text; a group-level disabled state is not announced either, because there is no `aria-disabled` |
| Context-menu event (`onContextMenu`) | `HostProps` declares no `onContextMenu`; a right press arrives as `onAuxClick`, which `isRightClick` distinguishes — the shipped `ContextMenu` uses that path, and `context-menu-lifecycle` measured a right press opening the surface at the press point | handle `onAuxClick` and place your own surface at the pointer |
| Paste event (`onPaste`) | `HostProps` declares no `onPaste`; a paste runs inside a focused field and reaches `onChange` with the new value (`clipboard-lifecycle`) | read the pasted text from the new value in `onChange`; there is no paste payload, caret or insert-at-selection API |
| Accessibility attributes | the closed set is `role`, `aria-label`, `aria-description`, `aria-id`, `aria-expanded`, `aria-selected`, `aria-valuetext` and `aria-level` — no checked or pressed state, no `aria-labelledby`, and no `aria-live` | name the control itself, put a numeric value in `aria-valuetext`, and do not present a toast or a countdown as announced |
| Application menu | the typings expose only `WindowOptions.appName`, which names the Hide and Quit items. The macOS bar the runtime installs is **fixed** — Apple (Services, Hide, Hide Others, Show All, Quit) and Window (Minimize, Zoom, Close), with no Edit menu so ⌘C/⌘V reach the window's text handling — and no public method takes a menu (`app_menu::init` is `pub(crate)`) | draw the menu **inside** the window with the dropdown parts; a native item's callback cannot be attached, and a Linux or Windows menu bar is the app's own |
| Reduced-motion preference | no preference query exists: `@gpuix/native` 0.11.0 publishes no `appearance`, `prefers*` or `reduce*` export, and `WindowOptions` carries no such option — so there is no value to read. `@gpuixui/motion` takes the policy from the caller instead: `MotionValue.sample(elapsedMs, reducedMotion)` and the hooks' `options.reducedMotion` | the app owns the policy — detect it in your own layer and pass it with `MotionValue.sample(elapsedMs, reducedMotion)` or the hooks' `options.reducedMotion` ([Motion](/docs/motion)); keep motion optional and short rather than the carrier of meaning |

## What to do instead

The unsupported rows are not decorative placeholders — each has a named gap and a
working alternative.

### `transform`

`StyleDesc` has no `transform`, nor `transformOrigin`, `rotate`, `scale`,
`translate` or `skew`. You cannot statically rotate or scale an element.

```tsx
import { motion } from "@gpuix/react";
import { layoutSpring } from "@gpuixui/motion";
import { useSpring } from "@gpuixui/motion/react";

function Grow({ open }: { open: boolean }) {
  const { value } = useSpring(open ? 100 : 0, layoutSpring);
  return <motion.div animate={{ width: value }} transition={{ duration: 0 }} />;
}
```

`@gpuixui/motion` drives the numeric `MotionStyle` fields the runtime *does* have
— `width`, `height`, `top`, `right`, `bottom`, `left`, `opacity`, `borderRadius`.
Static rotation/scale stays unsupported until the runtime grows a `transform` key.
The physics behind those fields — springs, retargeting, keyframes, inertia and
the app-supplied reduced-motion policy — is [Motion](/docs/motion).

### Grid span

The grid exposes only `gridColumnMin`/`gridRowMin` and integer
`gridTemplateColumns`/`gridTemplateRows`. `col-span-*` / `row-span-*` /
`grid-area-*` are unrepresentable — `@gpuixui/tw` refuses them by name rather than
dropping them.

Size the track to do the spanning instead of asking an item to cross tracks:

```tsx
<div style={{ display: "grid", gridTemplateColumns: 2, gridTemplateRows: 1 }} />
```

### Canvas drawing

`canvas` is a blank host element — it appears in `ElementType` but has no
2D-context or draw props. Compose the shape from `svg` / `div` primitives, which
are first-class. A multi-colour plot is the exception: see the chart surface in
*Measured in a window* (`setImagePixels` for a raster, `setImage` with SVG bytes
for a vector plot).

### IME composition

No composition events reach the React surface. Compose at the application layer
from `onInput`/`onKeyDown`; live IME preview needs a runtime change.

### Global shortcut

Key events fire only while the window is focused; there is no system-wide hotkey
registration. Bind window-level `onKeyDown` via `render`'s key handlers.
Background hotkeys need a runtime change.

### Tray / menu bar

There is no tray, menu-bar or status-item host. Ship the menu inside the window;
a system tray needs a runtime change.

### Native view / webview

There is no webview or native child-view host. Use the `markdown`/`code`/`diff`
surfaces for rich content; embedded web content needs a runtime change.

## `isTerminal()`

`isTerminal()` is re-exported from `@gpuixui/runtime`. It is `false` until
`init()` runs, so read it while rendering, not at module scope:

```tsx
import { isTerminal } from "@gpuixui/runtime";

// A terminal has no titlebar: drop the macOS traffic-light space.
if (isTerminal()) {
  // …render without the window chrome…
}
```

## Read the matrix from code

```ts
import { capabilities, unsupportedFeature } from "@gpuixui/runtime";

capabilities.transform.supported; // false
capabilities.transform.workaround; // "Animate motion with @gpuixui/motion; …"

const refusal = unsupportedFeature("gridSpan");
// UnsupportedRuntimeFeature { feature: "gridSpan", reason, workaround }
```
