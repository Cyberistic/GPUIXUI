---
title: Runtime capabilities
description: What the pinned GPUix runtime provides, what it does not, and the honest workaround for each gap.
---

The library pins `@gpuix/react` / `@gpuix/native` at **0.11.0**. This page records
what that runtime provides, what it does not, and the strongest honest alternative
for each gap. `@gpuixui/runtime` encodes the same matrix in code — `capabilities`
and `unsupportedFeature` — and its compile-time guards fail the build the moment
the runtime adds a key the matrix claims is absent, so the table below cannot go
stale silently.

## The matrix

| Capability | Status | Workaround |
| ---------- | ------ | ---------- |
| Terminal rendering | Supported | `render(<App />, { terminal: true })`, or set `GPUIX_TERMINAL=1` |
| Headless `Dialog` | Supported | `@gpuix/react/dialog` owns the Escape layer and the Tab trap |
| Tab / Shift+Tab focus | Supported | Default; `preventDefault()` keeps one Tab |
| `transform` | Not supported | Animate motion with `@gpuixui/motion`; static rotation/scale is unsupported |
| Grid span | Not supported | Size the track with `gridTemplateColumns`/`gridTemplateRows` or an explicit width |
| Canvas drawing | Not supported | Render `svg` or compose `div`/`svg` primitives; no retained draw API — a `<canvas>` also tracks no painted bounds (`content-surfaces`) |
| IME composition | Not supported | Compose at the application layer from `onInput`/`onKeyDown` |
| Global shortcut | Not supported | Window-level `onKeyDown`; background hotkeys need a runtime change |
| Tray / menu bar | Not supported | Ship an in-window menu; a system tray needs a runtime change |
| Native view / webview | Not supported | Use `markdown`/`code`/`diff` surfaces |

## Measured in a window

Some limits are not in the matrix above, because the matrix is built from the
runtime's own typings and these were measured by a probe that paints: the type
does not say them, so a reader must not infer them from the table's silence.

| Gap | What a window measured | Use instead |
| --- | ---------------------- | ----------- |
| Render root | the window's render root must be **one element**: a root that is a fragment paints only **one** of its children. `ToastProvider` mounted as the root — its children are the panel and the viewport — painted the viewport in the automation tree while `getPaintedText()` was empty for the panel; the same provider inside one wrapper element paints both, and siblings **inside** a host element paint normally (`toast-lifecycle`) | return one element from the app root and mount a multi-child provider inside it; a fragment at the window's root loses a child with no error |
| Sticky positioning | `position: "sticky"` paints nothing — a sticky sample inside its scroller moves by exactly the scroll amount, so it behaves like `relative` (`data-grid-fixed-header`) | put the header **outside** the row scroller as a sibling, and wrap header and rows in one `overflowX` scroller so both move together |
| Floating layer placement | `side="right"` paints the panel one 6px gap off the anchor's right edge and `side="left"` mirrors it; `align="start"` holds the panel's top on the anchor's top; but **`align="center"` ends the panel at the anchor's centre line** rather than centring it, so the panel starts half its height low (`floating-sides`). The headless `floating-placement` scenario drives the `TestRenderer`, and the two can differ | use `side` with `align="start"` when the box matters; for a genuinely centred panel, offset it yourself by half its measured height, as the overlay components do |
| Nested overlays | a dialog holding a popover holding a menu is composed from the shipped surfaces, and the window measured the dismissal order: the first `Escape` leaves the menu (`dismissed=menu`) and returns the focus to its trigger, the second leaves the popover (`dismissed=menu,popover`), the third the dialog (`dismissed=menu,popover,dialog`), each enclosing surface surviving the one inside it. A press outside both floating surfaces is **one gesture** that closes one layer (`closes=1,1,2`); the next press closes the popover and the dialog stays (`closes=1,2,2`), and a third closes the last (`closes=2,2,2`) with the focus at the app's opener. A pointer-opened menu nested in a popover takes the popover surface's focus, so one arrow reaches its first row (`nested-overlay-lifecycle`, 41 checks) | compose the shipped `Dialog`/`Popover`/`DropdownMenu` so they share one dismiss layer per surface; a custom overlay consumes a dismissal only while no deeper layer is open, and identifies one pointer gesture by the fields its handlers share |
| Aspect ratio | `aspectRatio` fills whichever axis is left open: a definite **160** width at ratio **2** paints **160×80**, a definite **60** height paints **120×60**, two definite dimensions (**160×60**) keep both, and a **100**-wide box at ratio **0.5** paints **100×200** — a portrait box, not a smaller one. A container's stretch makes only the axis it stretches definite: a child in a **240**-wide column paints **240×120**, while a child in an **80**-tall row paints **0×80**, because the row supplies the height and the ratio derives no width from it (`aspect-ratio-paint`, 14 checks) | leave one axis open for the ratio, and give a row child its height so the ratio derives its width; two definite dimensions leave the ratio unconsulted |
| Flex sizing | a `flex-1` column is not an equal split: `@gpuixui/tw` compiles it to `{ flexGrow: 1, flexShrink: 1, flexBasis: 0 }`, and a window measured what the four fields paint (`flex-sizing`) in 27 checks, while the headless `layout-flex-sizing` asserts the same arithmetic. In a 400px row a 120px item beside a `flexBasis: 0` grower gives the grower **280**; two `flexBasis: 0` growers whose content fits split it **140/140**, while the same contents with no basis paint **70/210**; a grower holding **200** keeps its content and the other takes the **80** left, so **`flexBasis: 0` does not override the automatic content minimum**; a 320px item shrinks to **180** in a 300px row while `flexShrink: 0` keeps **320**, painted 20 past the row; 300px of content floors an item at **300** in a 200px row until `minWidth: 0` lifts it to **200**; `maxWidth: 120` stops a grower at **120** and leaves the row short; and `alignSelf` places 60px of content at **0/120/240** in a 300px column whose `stretch` item is **300** | give a fixed pane or a frozen column `shrink-0`; declare `minWidth: 0` on a column that must truncate, because the automatic minimum is its content; do not cap a grower with `maxWidth` when it must fill its row |
| Select option reveal | a list paints in its own layer one 6px gap below the trigger's start edge, takes the focus, opens on the selected row, moves the highlight with the arrows (wrapping past a disabled row), selects on `Enter`, and dismisses on `Escape` (focus returns) or an outside press (`select-lifecycle`). What a keyboard cannot do is **reveal** a row past the list's edge: the runtime sets no max height or overflow and its two scroll-button parts are empty in 0.11.0, so a 40-option list is a 320px scroller the **wheel** moves (`-200`) while twenty `ArrowDown`s leave the offset alone (`fields.runtime.test.tsx`) | cap the surface and make it a scroller (the shipped `Select` caps at 320px); keep a keyboard-critical list short, or use a `Combobox`/`SearchInput` composition where the query narrows it |
| Frozen column | no sticky, so a frozen first column is **composed**: its own vertical scroller beside the grid's, mirrored in both directions through `onScrollChange` → `scrollTo` (a 120px label pane and a 240px grid stay on the same `y` at `-300` and `-600`; the row under the reader keeps its `y`; a press on a frozen cell selects the row for the whole grid; a `deltaX` wheel pans the grid and leaves the column still; a `-10000` wheel clamps both at `-1440`) (`data-grid-frozen-column`), and in a window the mirror lands in the **same frame** as the wheel because `scrollTo` paints synchronously, the sideways pan stays the grid's alone, and a press on a frozen cell selects the row for the grid (`frozen-column-lifecycle`) | give each pane its own scroller, mirror offsets through `onScrollChange` and guard the echo with a **ref** (`scrollTo` paints synchronously); pan horizontally on the data pane alone — there is no single-scroller freeze |
| Dock keyboard navigation | the keyboard order across a dock's layers: one Tab stop for the whole rail (the selected trigger) between the sidebar's actions and the pane's first field, then the status bar. A closed sidebar paints 0 wide, yet its unguarded control keeps its tab stop, still reports its own 12px box inside the zero-width parent and still accepts `focusElement` — the pointer is clipped away but the keyboard is not; a control given `tabIndex={-1}` leaves the **forward** chain while nothing inside it holds focus, but the runtime treats a negative index as a sort key and orders it **before** the zero stops: `focusElement` can reach an excluded cell, and the next Tab leaves to the control before the widget (`grid-focus-lifecycle`) — so a closed pane sets the attribute **and** moves focus out as it closes. Tab from the remembered `0` cell leaves the widget in one press. A rail step moves the selection **and must move focus itself**, and the pane's field owns its arrows (`dock-focus-lifecycle`) | one stop per rail through a roving `tabIndex` and one per pane; `tabIndex={-1}` on a closed pane's controls **and** move focus out as the pane closes, because the runtime neither skips a control whose parent paints nothing nor removes a negative index — it orders it before the zero stops; call `renderer.focusElement` from the rail's key handler; give the dock its own rail chords, or leave the arrows to fields |
| Menu anchored in a scroller | a dropdown whose trigger sits in a horizontally scrolled header keeps its place: a −100 wheel moves the trigger and the panel **together in one read**, `Escape` returns the focus to the trigger, `Enter` opens it on the first item and a second `Enter` hides that column, and it still opens after the header shrinks (`header-menu-lifecycle`). Two measured rules: anchor arithmetic uses the **cell**, not the trigger element — the trigger paints 22px inside its cell, so a width read from the trigger's box is 22px out — and hiding a column **before** the anchor moves it while hiding one after it does not | anchor the panel from the header **cell**'s box and let the shipped dropdown place it; keep the trigger outside the columns a reader can hide, or re-place it as they do |
| Table sort and selection | a table is flex rows of fixed-width cells, and both interactions work with no table primitive: a press selects the record it hit **and that row holds the focus**, so the next key reaches that row's own handler; `down` roves focus and selection together; a header press sorts by the column it hit and a second press flips the direction while the selected **record** survives the sort; the header keeps its painted `y` while the rows scroll under it and a wheel over it scrolls nothing, because it is a sibling outside the row scroller; and one `overflowX` box pans header and cells together, staying aligned (`table-lifecycle`). The measured constraint: a sortable header whose painted centre is clipped by the horizontal viewport sorts nothing, because a press is aimed at the element's centre | key sort and selection by **record**, never by row index; give each row `tabIndex={0}` and move focus with `focusElement` from the row's own key handler; keep the header a **sibling above** the row scroller inside one `overflowX` box; keep a sortable column's centre inside the frame, or pan the header first |
| Composite-row press routing | a press runs its handlers from the topmost hitbox down to the first child that **paints a fill** — the fill is the boundary, not the depth — so a press on an unfilled `<text>` label reaches the row (`text-unfilled → hits=row-click`) while the same label filled runs nothing (`text-filled → hits=none`), a filled control runs its own handler alone (`control-filled → hits=cell-click`), an unfilled one runs both (`control-unfilled → hits=cell-click,row-click`), and `pointerEvents: "none"` on a filled control still runs both, because only the drawing that paints nothing lets the press through (the inert-control case). A reorder row that captures through `onMouseDown` never hears a press its cell takes (the drag-row case), and a row's `onAuxClick` does not hear a right press on a filled child (the aux-row case). A key is the other path: it travels the **focus path**, so a row's `onKeyDown` hears a key typed in a field inside it (`field-cell → hits=row-key`) while the field keeps the key and the focus, and a press on that field also runs the row's click (the field-in-row case). The ten cases are `PRESS_CASES` in `apps/playground/src/live/press-routing.ts`, measured by `press-routing-lifecycle` (15 checks) | make the cell that paints take the press itself, or paint nothing there, when the row is the selection — a row's `onClick` cannot be the only path; fill a cell or guard the row before putting a pressable chip in a selectable row, since an unfilled child runs both handlers; make a reorder handle the element the press lands on; put a context menu on the cell that paints, because a row's `onAuxClick` does not hear a right press on a filled child; read the key event's own `elementId` before acting on an arrow, because a field inside the row keeps the key |
| Composite-row hover routing | a row's pointer feedback is the runtime's native `style.hover` refinement, and the hovered set comes from the **same hit test** the press takes, so a fill between the pointer and the row can take the feedback without taking the press (`hover-routing-lifecycle`, 56 checks on four 460×56 rows whose `hover` fill is the `accent` role over `card`): an unfilled `<text>` label leaves the row its enter and its fill (`text-unfilled → row-enter=1 child-enter=1 paint=yes`); a `<text>` or a `<div>` that paints a fill takes both (`text-filled → row-enter=0 child-enter=1 paint=no`, `div-filled → row-enter=0 child-enter=1 paint=no`); and a filled child declaring `pointerEvents: "none"` gives the row back both while it still hears its own listener (`inert-div → row-enter=1 child-enter=1 paint=yes`), because opting out removes the fill's hitbox, not the handler. The four cases are `HOVER_CASES` in `apps/playground/src/live/hover-routing.ts` | give a decorative child `pointerEvents: "none"` — a status pill, a badge, a metric inside a selectable row — or paint the row's `hover` on the child when it must answer the pointer itself; a row that waits for `onMouseEnter` hears nothing behind a fill |
| Modifier press | a click carries the held modifier set, so a list selects by chord: a plain press on row 3 reports `selected=3 anchor=3` with all four flags `false` and the pressed row holding the focus; `shift` row 6 reports `selected=3,4,5,6 anchor=3` and `shift` row 1 re-ranges backwards from the same anchor; `cmd` row 5 reports `flags=cmd:true,ctrl:false,alt:false,shift:false` and `selected=1,2,3,5 anchor=5`, and pressing it again removes it; `cmd-shift` row 2 joins the span to the set; a plain press replaces the set and moves the anchor, so the next `shift` ranges from that press rather than the last toggle; and the chosen rows paint the theme's `selected` fill (`modifier-select-lifecycle`). One measured limit: **a double press cannot be synthesized** — `simulateClick` and the locator both dispatch `click_count: 1`, so two presses on the same row report `click=1` even in a row that listens for a double click | read the payload's four flags rather than deriving the chord from `shift` alone, and keep the anchor as state — a **plain** press moves it, `shift` **keeps** it and a `cmd` toggle **moves** it; give a control that opens on a double press a keyboard path or an explicit control, because no window probe can send a count |
| Filtering controls | a filter is a field above the rows, so the runtime refuses nothing — the rules around it are the app's, and a window measured the four decisions a grid owns by typing a literal, case-insensitive query over 120 rows (`table-filter-lifecycle`): `1` narrows the painted set to **39** while the field keeps the text session and the visible selection survives; `12` narrows to two and **clears** the selection it hid, rather than acting on a record nobody can see; `12z` paints the empty state and no row; clearing restores every row and parks the session back in the filter field; a −200 wheel and then a filter opens the new set at **0**, read from `scrollOffset` because the readout alone would have passed while the list stayed put; `Down` from `Item 1` lands on `Item 10` — the filtered order, not the numeric one — and moves the real focus with the selection; and a clear keeps the row it still holds | keep the selection by **record** and clear it when that record leaves the set; leave the text session in the filter field while rows come and go; reset the scroller to the top on a filter change; step the filtered array on arrow keys and move the focus with the selection |
| Dock reflow | a split is pointer capture over a caller-owned width: a divider keeps the drag 80px outside its 6px box and nested levels keep independent widths (`split-pane-lifecycle`, `docking-nested`). A dock's re-clamp signal exists: when a 120px sidebar takes 100px from a flexible centre, the centre's `onLayout` fires again and its settled payload is the painted box (`w=240`, equal to `bounds`) — but the reflow's **first** pass reports the box the pane still has (`w=340`, `reports=2`) and a pane whose box did **not** change is still reported to (`dock-reflow`) | subscribe to **both** `onMouseDown` and `onMouseMove` on the divider so capture arms; re-clamp from the width the payload carries and make the handler idempotent rather than treating every report as a change; a dock passes its own bounds, since a split's `max` is the caller's number |
| Resizable column drag | a column's divider is pointer capture over a caller-owned width, and a window measured it: a 6px divider keeps **8 of 8** moves past its own box and widens the column 160 → 220 on a +60 drag, the release ends the gesture, a −150 drag clamps at **120** with the header painting the floor, a second +30 drag measures from **150** (the width its own press found), the widened grid pans to **−20** with header and cells on one offset, `right` on the focused divider steps it to **166**, and a move-only divider hears **1 of 8** moves while its column stays **90**. The headless `table-column-resize` scenario synthesises the pointer, so only a window proves the press arm (`column-resize-lifecycle`, 29 checks) | subscribe to **both** `onMouseDown` and `onMouseMove` on the divider, or the press never arms the capture and the element under the pointer resolves the drag; read the width at **each press** and apply the delta to that snapshot; clamp through the split pane's own arithmetic, since a column and a pane are one drag against one pair of bounds; keep header and cells in one `overflowX` scroller so a pan moves them together |
| Property inspector | one object read by four views: a preview, 30 key-value rows, a metric and an editing field repaint in the frame the edit lands — typing `ab` reaches all of them, and the preview and inspector share one row with a **6px** divider as their whole gap (`inspector-lifecycle`). The preview paints **120×80** and the metric **9600**; **Wide** takes them to **240×80** and **19200**, **Reset size** returns the width and keeps the typed tag; a **−200** wheel scrolls only the inspector's 30 rows while its pane and the preview caption hold their `y` | make the inspector a **pane that owns its `overflow`** — it scrolls its rows inside the split while the preview holds still; paint every view from the one object in the frame the edit lands, with no reconciliation step; derive one value column from the label column; a toolbar is a row in the pane, not a host the runtime provides |
| Workspace restore | the runtime publishes no storage, so a saved arrangement is the app's data — and a window measured the **restore**: a re-mounted workspace paints the saved string (`sidebar=0 document=360 tab=output scroll=-120`), its layout pass reports `360`, and the saved scroll paints at **−120** while a corrupt `not a workspace` opens the default (160 / 240 / explorer / 0) rather than a partial layout and a stored `sidebar:-5 document:9999 scroll:-30` clamps to **0 / 360 / 0**. Both negative controls were measured: restoring the default instead of the saved layout, and skipping the saved scroll (`got 0`) (`workspace-restore`) | decode the persisted string at the app's boundary into a typed layout and restore from it on mount; open the default on a decode failure; clamp every restored width and scroll to the pane's bounds; apply the saved scroll on the first layout pass |
| Window size | `getWindowSize()` is the box the layout fills, and `useWindowSize()` reports the same pair: a 900×520 window with a fixed 120px sidebar and a flexible centre reads 900×520 on both channels with the centre at 780, `zoomWindow()` takes it to 1680×923 with the centre reflowing to 1560 and `onLayout` reporting again, and a second call restores 900×520 (`window-resize-reflow`). The 800×600 constant fails that arithmetic. The app channel samples every 100ms, so it **lags** an animated zoom (`expected 1680, got 900`), and the binding publishes no `setSize` | read the size for arithmetic — a split's `max`, a dock's own width — and re-clamp on `onLayout`, which the resize runs again with the new box; wait for `useWindowSize()` after a programmatic zoom instead of reading it in the same tick |
| Layout reports | `onLayout` arrives after the first paint and again on a **size** change, not on a move: a 240×60 surface under a panel that opens still reported `originY=88` after the panel moved it **120** points down, while it painted at **208**, so a box stored from the last report is the box it used to occupy. A 1px probe at the surface's origin, its width alternated on each pointer read, is laid out again (`probe=3`) and reports the fresh `originY=208`; the same pointer read against that origin is the local point it had at rest (`120,30`), where the stale box reads `120,150` (`surface-origin`, 15 checks). **Inside a clipped parent**: a `defaultOpen` section settles its clipping box on the body's **80** with no press, a pressed one on **120**, a body grown to **200** while the section was closed is measured again on the next open rather than the retired **120**, a closed section keeps neither the box nor the body mounted, and the content recipe's padding is part of the measurement (**94** for an **80** body), so a reveal needs no caller-supplied height (`collapsible-lifecycle`, 31 checks) | measure a **size** from `onLayout`, never a position; a surface that can be moved reads a fresh origin from a nudged 1px probe or a payload carrying the current box, and does not trust a stored report across a layout change above it |
| Hiding a subtree | `display: "none"` is **ignored**: the renderer matches `display` against `"flex"` and `"grid"` only, so the wrapper's control still reports its **200×32** box, paints its own fill and stays in the Tab walk (`hidden-subtree-lifecycle`). `visibility: "hidden"` is the hiding word — the control reports no box, the **32**-point row it held paints the page and the traversal skips it — and a code focus on it reports the id yet delivers no key (`invisibleKeys=0`) | hide with `visibility: "hidden"` when the row must stay, or unmount the subtree; never `display: "none"`. Move focus off a hidden surface before expecting a keystroke |
| Window chrome | the runtime reserves **no** titlebar: `getWindowInsets()` and `useWindowInsets()` agree on the `safeArea`/`ime`/`effective` edges (the channel samples every 100ms, so poll it rather than reading it in the mount's tick), all `0,0,0,0` on this host while no keyboard is up, a bar at `top: effective.top` starts and paints there (±1), and the app's own bar is the capture's **first row** — so the layout starts at the window's top edge. A transparent titlebar changes neither the insets nor that origin (`window-chrome`). Two limits: whether the OS titlebar is hidden is not app-visible (no API reports it, and a capture is the app's own scene), and an IME inset cannot be measured because the window protocol cannot start an IME session | paint your own chrome — a titlebar-integrated toolbar keeps its own constant (28pt on macOS) and paints over the top edge, because `trafficLightX`/`trafficLightY` are **inputs** rather than a reported safe area; inset only by the reported `effective` edges, which carry what the OS knows and the app cannot (a notch's safe area, an on-screen keyboard) |
| Fenced code block | a `<markdown>` fence is a surface of its own, not a region of the page: the runtime lays **3.5%** of a neutral ink over the fill **behind the host** and **2%** more under the language strip, and the token seam derives both, so a palette is read on the composite. A window painted them: the base dark block `#191C22` with a `#1E2126` strip, the macOS dark look `#242426`/`#28282A` on its own `#1C1C1E` page, each theme's keyword (`#A7A9FF`, `#B0B2FF`) on its own fence and clearing the body floor there, neither block painting the other's keyword, and a host handed no theme the runtime's own `#8F96ED`. The strip is a second wash (1.057:1 over the base body, 1.053:1 over the look's) carried by the runtime's rule, and the unthemed control keeps the runtime's own code metrics (`markdown-fence`, 50 checks) | derive the two washes from the fill that actually sits behind the document (`nativeFenceFill` / `nativeFenceHeaderFill`) — a fence composites over the host's fill, not the theme's `bg`, so a document on a card derives from the card — and read the palette's `keyword` on the fence rather than on the page, because the first run's platform block composited to the base page's fence |
| Second window | a process gets **one** window: `init()` opens it and a second call fails with `A GPUI application already exists on this thread`, which is why each backdrop mode is its own CLI run (`window-backdrop`), and the renderer publishes only verbs on that window — activate, minimize, zoom, fullscreen, title | keep a detached tab, an inspector or a second document inside the one window — a pane, a layer, or a `createPortal` surface; no method opens another OS window |
| Window backdrop | `windowBackground` is honoured: an `opaque` window's unpainted surface carries alpha **255** while `transparent` and `blurred` both carry **0**, with the app's painted box identical in all three (`rgba(217, 67, 43, 255)`, a 900×520 window captured at 1800×1040 — the display's 2× scale) (`window-backdrop`). Two limits: the app's capture of `blurred` is **byte-identical** to `transparent`, because the vibrancy is composited behind the window, so no app frame proves the blur; and one window per process (`A GPUI application already exists on this thread`), so each mode is its own run. A translucent fill is composited against that surface — `#D9432B80` painted `rgba(109, 34, 22, 255)` on an opaque window | let the **unpainted** area carry the translucency and paint the content opaque; take `"blurred"` for the effect but confirm it by eye on the target OS rather than from a capture |
| Theme and density switch | a provider value change lands in the frame the switch commits, and a window measured the two axes separately: the **palette** cycle repaints the page and card (dark `#11141A` / `#191D25`, light `#F6F8FA` / `#FFFFFF`, high contrast `#000000` / `#0D0D0D`) while the `md` control stays **32**, so a palette press does not reflow; the **platform** cycle re-lays the control out (macOS **28**, Linux **36**, Windows **32**, Default **32**) and the page stays `#000000` with a high-contrast palette, because `applyStyle` reserves that palette while it takes the look's density; both cycles close on the opening frame (`theme-switch-lifecycle`, 73 checks) | switch the palette and the platform through the provider's value rather than a remount; a reflow comes from a density change alone, and a high-contrast theme keeps its palette while a look changes its metrics |
| Dialog focus containment | the runtime moves native focus from code and offers `focusNextWithin`/`focusPreviousWithin`, but it does **not** trap Tab: the surface's own key handler cancels it and drives the wrap (`modal-focus-trap` — focus enters the content, four Tab presses stay inside and wrap back to it, Shift-Tab is the reverse, `Escape` returns the focus to the trigger, and a popover opened inside takes the first `Escape` and returns its focus before a second closes the modal). The restore target is the opener recorded in the render that opens the surface, before its children exist, so a child's `autoFocus` cannot steal it: a surface with nothing focusable, an `initialFocus` field and an `autoFocus` field all return the opener (`modal-focus-restore`, 6 checks) | cancel Tab in the surface's `onKeyDown` and drive `focusNextWithin`/`focusPreviousWithin`; save the focused id when the surface opens and restore it from a layout-effect cleanup guarded by `getElementBounds`; push nested layers onto one dismiss stack, because a keystroke reaches only the focused layer — there is no trap, focus sentinel or `inert` |
| Confirmation flow | a confirmation is the shipped `ConfirmDialog` **plus the caller's close** — the component reports `onConfirm` and never closes itself, so a failed save stays visible. A press opens the surface with the focus on **Cancel**, not the destructive action, and the untouched dialog dismisses on `Enter` reporting nothing (`confirms=0 closes=1`); Delete reports **once** (`confirms=1 closes=2`) and the surface goes because the caller closed it; Cancel and `Escape` report nothing and every path returns the focus to the opener (`confirm-dialog-lifecycle`). Two negative controls were measured: a duplicated confirm reports twice, and a close path wired to the confirm event makes `Enter` confirm | open from your own action and close from `onConfirm` after the work succeeds; give Cancel `initialFocus` and let `onOpenChange(false)` — the event Cancel and `Escape` both send — report nothing. A component that closed itself would hide the failure it exists to report |
| Validation flow | `Field` paints the message its caller hands it and never validates a keystroke, so the schema runs at the submit boundary: a valid value paints its description and **no** destructive pixel, submitting empty paints the pattern's own wording **in place of** the description plus the destructive role on the message and the invalid edge while the focus stays in the field, typing `design` and pressing `Enter` clears both, and a value with a trailing space fails the next submit because the value the field kept is what was validated (`validation-lifecycle`) | run the schema in the submit handler (`onSubmit`, the `Enter` path) and hand its message to the field; keep the value on screen so the next submit validates it; the focus stays where the reader left it. The message is not announced — there is no `aria-describedby` ([Accessibility](/docs/accessibility)) |
| Field edit correction | a controlled field applies its `value` **only when that value changes**: an owner clamping five characters reports `abcde` and pushes it back, the native box keeps the sixth and seventh characters, and the next edits arrive as `abcdef` and `abcdefg` — so an edit that leaves the owner's value where it was cannot be taken back. | Expandable rows | a painted row that grows is re-measured on the **next frame** with no scroll and no offset change, and the rows above do not move; the rows below shift by the growth (row 4 paints at `row 3 + 120` after one wheel, and a press lands on it, so the shift is not a stale hit test); a growth that leaves less than one 32px row of the 240px viewport **drops the following row out of the painted window** until a scroll, because the list paints whole rows; the opened row keeps its 120px after leaving and re-entering the window; and the grown height joins `scrollToItem`'s estimate (`virtual-list-expand`) | an expansion needs no remount or forced re-layout — but size an expandable table's viewport (or overdraw) against the **open** row height, and measure a row while it is on screen: one that grows outside the window is not remeasured until it paints again (`virtual-list-rows`) |
| Loading-row restore | a paginated history's **loading void** is the list's anchor, so a splice replaces the screen the reader was reading: a prepend left to the runtime painted the arriving page at the pixel the reader's message held (`y=80`) and the message left the screen, while an app that read `getListScrollTop` before the commit and re-anchored kept that message at `y=80` with the page filling `0..80` (`loading-row-correction`). At the at-end sentinel (`itemIndex == row count`) the page painted at `y=0` unless the app pinned its first row on the void's old top edge (`y=80`), where the message above kept `y=40`; a second prepend page needed **no** correction because the anchor was then a message row, and the append rule fired again after wheeling back to the end (`corrected=2`). The read names the row at the viewport top **after** layout, not the request | read the anchor before the commit and re-anchor after it — `scrollToItem(voidRow + 1 + pageRows, offset - edgeHeight)` under a top void, and `edgeHeight - viewportHeight` at the end sentinel — correcting only while the void is the anchor; `flushSync` the splice before the scroll, because a `scrollToItem` beside the state update resolves against the old list |
| Portals (`createPortal`) | a portalled card paints inside its **target's** box and outside an ancestor's clip, keeps the provider context above the caller, receives a pointer press and keys typed in its field, and unpaints when detached (`portal-layer`); `getPaintedText` still lists a clipped sibling's glyphs, and a clip only holds when the clipping box is the child's containing block | prove a clip with a capture rather than the paint report, and give the clipping box `position: "relative"`; a portal moves content within the one window — the binding opens one window per process, so a tab cannot detach into its own |
| Stacking order (`zIndex`) | the published runtime has **no** stacking field — paint order is tree order — and the only level a window has measured is the repository's **local** extension: red/green/blue absolute boxes mounted at levels 3/1/2 hit-test `stack=high,mid,low` and paint `#FF3B30` on top, the same boxes with no level keep tree order (`plain=plain-mid,plain-low,plain-high`), and a level 9 on an in-flow child is ignored under a positioned cover (`flow=flow-cover,flow-base`). Three limits: only positioned siblings are ordered, there are no stacking contexts, and a level of `0` reads like no level (`z-index-lifecycle`, 16 checks on 0.11.0) | render the surface last in the tree: a dialog, toast or menu mounts after what it covers, and a nested surface mounts inside its parent. The local patch is not a library API — never write a level in a component, because the published binding drops it and a rebuild without the patch leaves every surface in its resting order |
| Animated geometry | `motion` tweens painted geometry and lands exactly on a numeric target: a 120×40 box with a 3s `easeInOut` transition painted `40, 43, 117, 123, 221, 240, 240, 240` across eight presses and settled at 240×240, `onMotionComplete` fired once per run, and the reverse run tweened too (`motion-geometry`). The animated box **clips** its content instead of reflowing it — a fixed 320×200 child kept its size while the box was 120×40 and while it was 240×240 | animate an **outer** box with `overflow: "hidden"` for a collapsing sidebar or a growing row, since the content inside stands still; read `onMotionComplete` to unmount or unlock after a run; `duration: 0` paints the two target sizes with no frame between them, which is the negative control |
| Clipboard | the binding has no clipboard read or write, and the keys do not cross the window seam: `cmd-a`/`cmd-c`/`cmd-v`/`cmd-x` reach a focused field's `onChange` — select-all, copy, paste and cut all work — but never reach the app's window handler, while `cmd-k` from the same control does (`clipboard-lifecycle`) | an app-level "copy" action is not buildable; offer the text in a read-only field the user can select and copy from |
| Pasted code in a field | a one-time code is the one value a reader almost never types, and there is no paste event, so the shipped `OTPField` distributes one multi-character `onChange` **forward from the cell that took it** (`otp-paste-lifecycle`): a marker copied from a shipped `Input` with `cmd-a`/`cmd-c` and pasted into the first of six cells reports the whole code with one character per cell, `completes=1 edits=1`, and the focus in the sixth; a nine-character paste over a finished code truncates at six and is **not** a second completion (`completes=1 edits=2`); and a paste over the third cell keeps the first two (`edits=3`). A paste cannot be told from fast typing | let the field distribute the code — the app cannot read a paste, because there is no payload and no caret. Keep `onComplete` on the transition into a full code; normalisation (`123-456` → `123456`), the forward fill and the focus advance are the field's own rules |
| Text input ink | two inks inside a field are the runtime's, and a window measured both (`field-ink`): an empty `<input>`'s hint is a fixed `#8F8F8F`, so a host given `nativeTextTheme` paints **none** of the theme's `placeholder` role, while a host with no `placeholder` carrying a themed `<text>` over it paints the role and none of the grey; and a **value** paints the element's `color`, not the theme object's `text` — a value typed into a host given only the seam paints **darker than its fill**, its brightest pixel under the probe's `INK_PEAK_FLOOR` (120), while the same value with `color: inputForeground` peaks within `INK_PEAK_TOLERANCE` (12) of the ink. The shipped `Input` paints the role when empty and the seam's ink once typed | give the host `color: theme.colors.inputForeground` and paint the hint yourself in the `placeholder` role with the host's `placeholder` unset — the seam's `text`/`textMuted` reach `<code>`/`<diff>`/`<markdown>`, not a field's value or hint |
| Custom fonts | a face registered before the first paint paints its own advances: GPUix's square test face paints **80**px at 20px where the theme's `.SystemUIFont` paints **42**px and a family nothing installs paints **44**px, so naming a family changes nothing on its own (`register-font`). The order is a frame, not a verdict: a face installed after its text first laid out painted **44**px, then **81**px on the next re-layout, while a never-installed control stayed **44**px (`font-registration-late`, 4 checks) | register every face before the first paint — that frame is the one a reader sees — and treat a missing file as a silent fallback, because no API reports which family painted; a late install re-shapes on the next layout, but the fallback frame it skipped is already painted |
| Terminal frame (pty) | the same app painted into a **100×40-cell pty** instead of a window: the stream enters the alternate screen, hides the cursor and enables mouse, the kitty keyboard, bracketed paste and in-band resize, then sends an **800×640** frame (the grid at the fallback 8×16 cell) as one zlib RGBA transfer inside a synchronized-update batch; **510 864 of 512 000** pixels (99.78%) are the app's terminal page and **0** are the native-window page, so `isTerminal()` reads true in the app; **508** exact-white ink pixels form the centred word; a left SGR press at the frame's centre (`ESC[<0;400;320M`) reaches the app's `onClick` and turns that ink `#FFF200` while the page stays; the terminal's in-band resize (`ESC[48;20;50;0;0t`) repaints the app at **400×320**; a kitty key event (`ESC[116u`) reaches the app handler and repaints the whole page with **0** rest pixels left; and ctrl-c exits `0` and restores the terminal — alternate screen left, the four protocols disabled, the keyboard flags popped and the image deleted (`terminal-render`, `terminal-resize`, `terminal-pointer`, `terminal-input`) | target **kitty or Ghostty**, the terminals that speak the kitty graphics protocol; a terminal that does not speak it paints none of that stream. The resize is the terminal's own in-band message — re-`stty`ing the pty keeps the old frame, because the platform answers its terminal rather than a pty ioctl. Confirm a frame by looking at the terminal, because there is no automation protocol to read a pty back and no PTY **host element**, so an embedded terminal stays unavailable. The probe's harness is macOS-only (`script` + `stty`), which limits the evidence rather than the API |

The durable record — every host element, every limit, its verdict, its evidence

## Measured offscreen

One measurement is not a window fact: the accessibility tree is read from the
offscreen `TestRenderer`, because a window's automation protocol has no a11y
verb. It is listed apart so the section above stays a record of paints.

| Capability | What the test renderer reported | Use instead |
| --- | ------------------------------ | ----------- |
| Accessibility tree | the role reaches the platform under its **own** name — `button` is `Button`, `option` is `ListBoxOption`, `heading` is `Heading`, `progressbar` is `ProgressIndicator` — while `aria-label`/`aria-description`/`aria-id` land on `label`/`description`/`author_id`, `aria-selected`/`aria-expanded`/`aria-level`/`aria-valuetext` on `selected`/`expanded`/`level`/`value`, and `onClick` + `tabIndex` surface as `Click` and `Focus` (`a11y-tree`). A `<text>` is a `Label`. **A node needs a role to exist**: a `div` with only an `aria-label` paints no node and `role="none"` is dropped | give an element that must be announced both a `role` and its label, and assert the platform's role name rather than the token you passed; carry a state in `aria-valuetext`, since there is no `aria-checked`/`aria-valuenow` and no live region to announce a change |

The consumer half of the same budget — naming a control, the states no attribute
can carry, focus and the dim, and proving the tree — is on
[Accessibility](/docs/accessibility).

## Not in the typings

The matrix above is built from `@gpuixui/runtime`'s own keys. The rows below are
different: the pinned typings declare neither the host nor the prop — or no
public method takes one — so there is nothing to pass and no probe to run — a
component composes the alternative instead. `COMPONENTS.md`'s rows rely on each
of them.

| Capability | What the pinned typings have instead | Use instead |
| --- | --- | --- |
| Links (`href`) | `ElementType` has no `a`, and `HostProps` declares no `href`; the Breadcrumb, Navigation Menu and Lists inventory rows record the same absence | render a pressable `<text>` (the link-styled button) and show the destination in the copy; there is no visited state, middle-click or pointer cursor |
| Form grouping (`fieldset` / `legend`) | `ElementType` has no `fieldset`; the shipped `Fieldset` is a `role="group"` div with a legend-styled text | compose it from a div and a text; a group-level disabled state is not announced either, because there is no `aria-disabled` |
| Context-menu event (`onContextMenu`) | `HostProps` declares no `onContextMenu`; a right press arrives as `onAuxClick`, which `isRightClick` distinguishes — the shipped `ContextMenu` uses that path, and `context-menu-lifecycle` measured a right press opening the surface at the press point | handle `onAuxClick` and place your own surface at the pointer |
| Paste event (`onPaste`) | `HostProps` declares no `onPaste`; a paste runs inside a focused field and reaches `onChange` with the new value (`clipboard-lifecycle`) | read the pasted text from the new value in `onChange`; there is no paste payload, caret or insert-at-selection API |
| Accessibility attributes | the closed set is `role`, `aria-label`, `aria-description`, `aria-id`, `aria-expanded`, `aria-selected`, `aria-valuetext` and `aria-level` — no checked or pressed state, no `aria-labelledby`, and no `aria-live` | name the control itself, put a numeric value in `aria-valuetext`, and do not present a toast or a countdown as announced |
| Right-to-left layout | `StyleDesc` has no `direction`/`writingDirection` field; every edge is physical (`paddingLeft`/`Right`, `marginLeft`/`Right`, `borderLeftWidth`/`RightWidth`, `left`/`right`) and `AnchoredProps` places a surface by a physical `side`/`anchor`. There is nothing to pass that mirrors a tree. The **string** half is measured by `rtl-text` (19 checks): a capital `T` at the end of a sample lands **left** in `ייT` (**92/0** ink in the end bands) and **right** in `nnT` and `aייT` (**0/92**), so the platform reads the first strong character and lays the Hebrew run out right-to-left rather than right-aligning a box; and `سلام` measures **58 pt** against **79 pt** for the same letters with zero-width non-joiners, so the shaper joins the run. What is missing is *expressing* a direction, not reading one | keep one direction-aware helper that turns a logical inset or alignment into the physical value the app's direction needs, place overlays by a physical side, and mirror only directional glyphs (chevrons, arrows, back/forward) — a component stays physical in both directions |
| Application menu | the typings expose only `WindowOptions.appName`, which names the Hide and Quit items. The macOS bar the runtime installs is **fixed** — Apple (Services, Hide, Hide Others, Show All, Quit) and Window (Minimize, Zoom, Close), with no Edit menu so ⌘C/⌘V reach the window's text handling — and no public method takes a menu (`app_menu::init` is `pub(crate)`) | draw the menu **inside** the window with the dropdown parts; a native item's callback cannot be attached, and a Linux or Windows menu bar is the app's own |
| Reduced-motion preference | no preference query exists: `@gpuix/native` 0.11.0 publishes no `appearance`, `prefers*` or `reduce*` export, and `WindowOptions` carries no such option — so there is no value to read. `@gpuixui/motion` takes the policy from the caller instead: `MotionValue.sample(elapsedMs, reducedMotion)` and the hooks' `options.reducedMotion` | the app owns the policy — detect it in your own layer and pass it with `MotionValue.sample(elapsedMs, reducedMotion)` or the hooks' `options.reducedMotion` ([Motion](/docs/motion)); keep motion optional and short rather than the carrier of meaning |

## What to do instead

The unsupported rows are not decorative placeholders — each has a named gap and a
working alternative.

### `transform`

`StyleDesc` has no `transform`, nor `transformOrigin`, `rotate`, `scale`,
`translate` or `skew`. You cannot statically rotate or scale an element.

```tsx
import { motion } from "@gpuix/react";
import { layoutSpring } from "@gpuixui/motion";
import { useSpring } from "@gpuixui/motion/react";

function Grow({ open }: { open: boolean }) {
  const { value } = useSpring(open ? 100 : 0, layoutSpring);
  return <motion.div animate={{ width: value }} transition={{ duration: 0 }} />;
}
```

`@gpuixui/motion` drives the numeric `MotionStyle` fields the runtime *does* have
— `width`, `height`, `top`, `right`, `bottom`, `left`, `opacity`, `borderRadius`.
Static rotation/scale stays unsupported until the runtime grows a `transform` key.
The physics behind those fields — springs, retargeting, keyframes, inertia and
the app-supplied reduced-motion policy — is [Motion](/docs/motion).

### Grid span

The grid exposes only `gridColumnMin`/`gridRowMin` and integer
`gridTemplateColumns`/`gridTemplateRows`. `col-span-*` / `row-span-*` /
`grid-area-*` are unrepresentable — `@gpuixui/tw` refuses them by name rather than
dropping them.

Size the track to do the spanning instead of asking an item to cross tracks:

```tsx
<div style={{ display: "grid", gridTemplateColumns: 2, gridTemplateRows: 1 }} />
```

### Canvas drawing

`canvas` is a blank host element — it appears in `ElementType` but has no
2D-context or draw props. Compose the shape from `svg` / `div` primitives, which
are first-class. A multi-colour plot is the exception: see the chart surface in
*Measured in a window* (`setImagePixels` for a raster, `setImage` with SVG bytes
for a vector plot).

### IME composition

No composition events reach the React surface. Compose at the application layer
from `onInput`/`onKeyDown`; live IME preview needs a runtime change.

### Global shortcut

Key events fire only while the window is focused; there is no system-wide hotkey
registration. Bind window-level `onKeyDown` via `render`'s key handlers.
Background hotkeys need a runtime change.

### Tray / menu bar

There is no tray, menu-bar or status-item host. Ship the menu inside the window;
a system tray needs a runtime change.

### Native view / webview

There is no webview or native child-view host. Use the `markdown`/`code`/`diff`
surfaces for rich content; embedded web content needs a runtime change.

## `isTerminal()`

`isTerminal()` is re-exported from `@gpuixui/runtime`. It is `false` until
`init()` runs, so read it while rendering, not at module scope:

```tsx
import { isTerminal } from "@gpuixui/runtime";

// A terminal has no titlebar: drop the macOS traffic-light space.
if (isTerminal()) {
  // …render without the window chrome…
}
```

## Read the matrix from code

```ts
import { capabilities, unsupportedFeature } from "@gpuixui/runtime";

capabilities.transform.supported; // false
capabilities.transform.workaround; // "Animate motion with @gpuixui/motion; …"

const refusal = unsupportedFeature("gridSpan");
// UnsupportedRuntimeFeature { feature: "gridSpan", reason, workaround }
```
