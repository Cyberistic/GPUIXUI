A data surface is rows, columns, a header that sorts them and a selection that
survives a scroll. GPUix 0.11.0 has **no table host element**, so this lane is a
composition of layout primitives, the shipped list and a pure row model — not a
widget the runtime hands over. None of the Tier 3 rows is shipped yet; this page
records what exists, what a missing row will be built from, and the evidence for
each gap, so the first table does not start by re-discovering them.

## The lane

## What ships today

Most of a data surface is already here, one tier down. These are the pieces the
first table will compose:

| Piece | Page | What it gives the lane | Its limit |
| ----- | ---- | ---------------------- | --------- |
| List / ListItem | [List](/docs/components/list) | A roving tab stop, single and multiple selection, Shift ranges, `Cmd`/`Ctrl`+A, type-ahead, activation | Rows are compound children, so a list mounts all of them; a windowed list is `<virtual-list>`'s `itemCount` mode |
| Pagination | [Pagination](/docs/components/pagination) | A derived page window with stable width | No page-size control |
| Empty state | [Empty state](/docs/components/empty-state) | The no-rows state a table shows | No illustration slot |
| Cards, badges, progress | [Components](/docs/components) | Statistic cards and metric rows today | No chart component |
| Message scroller | [Message scroller](/docs/components/message-scroller) | Append-follow, unread count, jump-to-latest | Every row renders: a compound-children list, where the windowed `itemCount` mode renders rows from data instead |
| Command menu | [Command menu](/docs/components/command-menu) | Ranked filtering over a list | Per-group ranking, no column model |

A composed example is the [Dashboard](/docs/blocks/dashboard) block: statistic
cards, `Progress` rows and a hand-drawn SVG chart. The chart is labelled a gap
in its own source, because there is no chart component.

## A data surface you can build now

Two shipped primitives carry most of the lane: `Grid` for equal tracks and
`List` for interacting rows. A statistic card is a `Card` with `Text` and
`Badge`; a key/value panel is a two-column `Grid`.

```tsx
import { Grid, Text } from "@gpuixui/primitives";

<Grid columns={2} gap="sm">
  <Text role="caption" tone="muted">Rows</Text>
  <Text role="code">12,480</Text>
  <Text role="caption" tone="muted">Columns</Text>
  <Text role="code">7</Text>
  <Text role="caption" tone="muted">Last import</Text>
  <Text role="code">2 min ago</Text>
</Grid>;
```

This is the honest ceiling today: you own the row model, the sort and the
selection, and you draw the header yourself. What is missing is the reusable
part — a header that sorts, a selection that survives sorting, and column
configuration.

## A property panel is one object, read four ways

A property inspector is the lane's most common composition, and it is **not** a form.
The playground's `inspector-lifecycle` mounted the shipped `SplitPane` beside a
preview and measured one object read by four views at once:

- **One row, not a float.** The preview and the inspector share one row with the
  **6px** divider as their whole gap and one starting `y`; the group's right edge
  is the inspector pane's own.
- **One object, every view.** Typing `ab` reached the readout, the preview
  caption and the `tag` key-value row in the frame it landed, while the field kept
  the platform text session — there is no reconciliation step between them.
- **The table scans down.** Every label cell holds one `x`, and every value
  starts at its label's right edge. The value column is derived from the label
  column, so one widened row broke it (measured: the column moved to 649 from
  641).
- **A toolbar is a row in the pane.** Its actions paint on one row above the
  first property row; the runtime provides no toolbar host and needs none.
- **The inspector is a scroller.** It owns its `overflow`: a **−200** wheel moved
  the 30-row inspector to −200 while its pane and the preview caption kept their
  exact `y`, and the preview reported no offset — it is not a scroller. A pane
  that clips its rows instead reports no scroll handle at all, so the wheel check
  cannot pass on a box that merely hides its overflow.

The area and the metric follow the object rather than each other: **Wide** took
the width to 240, the area to 19200 and the preview to 240×80 in that frame, and
**Reset size** returned the width while the typed tag stayed — a reset is a size
action, not a new object.

## The table row comes first

The other twelve rows depend on it, so `Tables` is the row that unblocks the
lane. The shape the inventory names is a grid of `div` rows, not a `<table>`:

- **Rows and columns** — `Grid` for equal tracks; a whole row is one child, so
  the header and body share one column count.
- **Sort** — a pure module over the row array, like `menu/logic.ts` and
  `calendar/logic.ts`: `sortRows(rows, key, direction)` with the column
  definition owning the comparison. A component never sorts in render.
- **Selection** — a set of row ids, not indices, so it survives a sort; Range
  and `Cmd`/`Ctrl` semantics are the ones [List](/docs/components/list) already
  proves.
- **Keyboard** — a roving tab stop over rows and a header that is reachable, or
  a grid composite; the runtime has real focus but no `aria-colindex`, so a
  screen reader gets the row name and its selected state, not a cell address.
- **Virtualization** — `<virtual-list>` has two modes, and a table needs the
  second. The **children** form retains every row and skips only the off-screen
  build and paint; the **`itemCount`** form (`itemCount` +
  `estimatedItemHeight` + `windowStart`) mounts the slice the app renders, so a
  table of 100 000 rows keeps a 60-row window (`virtual-list-windowed`). Two
  rules make that mode work: size the window wider than the viewport plus
  **overdraw**, because `onVisibleRange` reports **absolute** indices
  one gesture behind the paint (`20..27` while the paint reached `40..46`); and
  on a reveal move the app's `windowStart` first and call
  `renderer.scrollToItem` after that commit, since the window is app state
  native cannot infer. A reveal is **index-addressed**: `scrollToItem` moves to
  a row that was never mounted and a programmatic reveal fires no
  `onVisibleRange` — read the painted rows or the list's anchor, and never
  paginate from that event across a row-count change
  (`virtual-tree-lifecycle`).
- **A find bar offsets by matches, not rows** — a search over a virtualized
  table searches a document the runtime never holds, and `getPaintedHighlights()`
  reports only the mounted window, so a row index cannot place the cursor.
  `matchIndexOffset` is a **match** count above the window: sum `findRanges` over
  the rows before `windowStart`. The document's count and the paint are different
  numbers — 676 matches across 400 rows, of which only the mounted rows wash —
  the row index `320` marks no match against a match numbered `541`, an
  off-by-one marks the match before the named one, and a negative offset drops
  the whole spec. A replace-all runs across the document, not the window
  (`search-virtual-document`).
- **An arriving page owes a re-anchor while a loading void is the anchor** — a
  paginated table, log or feed paints a void row at the edge a page arrives
  from, and `<virtual-list>` anchors on that row, so the splice replaces the
  screen the reader was reading. Read `getListScrollTop` before the commit and
  re-anchor after it: under a top void
  `scrollToItem(voidRow + 1 + pageRows, offset - edgeHeight)`, and at the
  at-end sentinel (`itemIndex == row count`) the page's first row takes the
  void's index at `edgeHeight - viewportHeight`. Correct only while the void is
  the anchor — a message anchor's index moves across the splice on its own — and
  `flushSync` the splice before the scroll (`loading-row-correction`).
- **A fixed header is a sibling, not a sticky row** — the runtime paints no
  `position: "sticky"`: a sticky child scrolls with its scroller, measured by
  `data-grid-fixed-header`. The header sits outside the row scroller, and both
  share one horizontal scroller so they move together; otherwise it scrolls
  away.
- **A frozen column is that rule on the other axis** — its own vertical scroller
  beside the grid's, with the app mirroring `onScrollChange` into `scrollTo` in
  **both** directions (`data-grid-frozen-column`). The mirror needs a **ref**
  guard, because `scrollTo` paints synchronously and the target's own change
  would otherwise mirror back. Both panes clamp together (`-1440` for 60 × 28px
  rows in a 240px pane), the row under the reader keeps its `y` across panes, a
  press on a frozen cell selects the row for the whole grid, and a horizontal
  wheel pans the data pane alone — a frozen column does not pan. In a window the
  mirror lands in the **same frame** as the wheel, for that synchronous reason
  (`frozen-column-lifecycle`).
- **A table's pane owns the wheel, not the page** — a wheel moves **every**
  scrollable ancestor on its hit path by the same delta, measured by
  `nested-scroll-lifecycle`: a `-100` wheel over an inner list moved the list to
  `-100` **and the page to `-100`** while the list still had 240px of travel,
  and each scroller clamps against its own content (`-340` inside, `-360`
  outside). The host props publish no wheel handler and no `preventDefault`, so
  a pane cannot keep a wheel from its page. Size the table's container to the
  height it has and give **it** the overflow, keep the page around it out of the
  scroll path, and read the table's own `onScrollChange` — an ancestor's
  `onScroll` fires for a wheel aimed inside the table. It holds for a
  `<virtual-list>` pane too: the rule is the scroll host's, not the
  `overflow` box's.
- **Sort and selection are keyed by record, and a window measured both** — a
  press selects the record it hit **and that row holds the focus**, so the next
  key reaches that row's own handler with no synthetic focus; `down` roves focus
  and selection together; a header press sorts by the column it hit and a second
  press flips the direction while the selected **record** survives the sort. The
  header is a sibling above the row scroller, and one `overflowX` box around
  both keeps a header cell and its column aligned after a pan. One measured
  constraint: a press is aimed at the element's painted **centre**, so a
  sortable header whose centre is clipped by the horizontal viewport sorts
  nothing — keep sortable columns inside the frame, or pan the header before
  expecting a press to land (`table-lifecycle`). The selection a desktop reader
  expects is a **chord**, and `modifier-select-lifecycle` measured it: `shift`
  extends from the anchor (`selected=3,4,5,6`), `cmd` toggles one record
  (`selected=1,2,3,5`) and `cmd-shift` joins the span to the set, while a plain
  press replaces the set and **moves** the anchor — so a `shift` after a `cmd`
  toggle ranges from the row the reader toggled, not the row last clicked
  plainly. Read the payload's four flags, because a handler that tests only
  `shift` cannot see a `cmd` the runtime sent. One limit: a double press cannot
  be synthesized (`click_count: 1`), so a table that opens a record on a double
  press needs a keyboard path or a control (`modifier-select-lifecycle`).
- **A cell that paints owns the press, and a key takes the focus path** — a
  table's checkbox cell, sort arrow, expander or trailing menu sits inside the
  row that also selects it, and the route is a painted surface rather than
  depth: `press-routing-lifecycle` measured that a press on a cell that paints
  runs the cell's handler alone (`control-filled → hits=cell-click`), while an
  unfilled child runs both (`control-unfilled → hits=cell-click,row-click`), and
  `pointerEvents: "none"` on a filled control still runs both — only a drawing
  that paints nothing lets the press through. A row whose cell paints cannot
  therefore rely on its own `onClick` for selection; a chip inside a selectable
  row needs the cell filled or the row guarded, or one press becomes two
  actions. A reorder row that captures through `onMouseDown` never hears a press
  its cell takes, and a row's `onAuxClick` never hears a right press on a
  filled child, so a context menu belongs to the cell. Keys are the other path:
  a key typed in an editable cell reaches the row's `onKeyDown`
  (`field-cell → hits=row-key`) while the field keeps it, so the row reads the
  event's own `elementId` before acting on an arrow (`press-routing-lifecycle`).
- **A column's divider arms the capture, and its width is read at each press** —
  a desktop resize is the split pane's drag rotated, and a window measured the
  reader's path (`column-resize-lifecycle`): a 6px divider that listens to both
  `onMouseDown` and `onMouseMove` arms the runtime's pointer capture, so it kept
  **8 of 8** moves past its own box and widened the column 160 → 220, with the
  header painting the new width and every later column shifting by the same 60.
  The release ends the gesture, a −150 drag clamps at the **120** floor and
  paints it, and a second +30 drag measures from the **150** its own press found
  rather than the earlier gesture's start — so read the width when the press
  lands and apply the pointer's delta to that snapshot, exactly as `SplitPane`
  holds its press. `right` on the focused divider steps it by 16 to **166**, so
  a pointer-only resize is half a control, and a divider shipped with only the
  move half hears **1 of 8** moves and never resizes, which is the control.
  Clamp through the split pane's own `nextSize` arithmetic — a column and a pane
  are one drag against one pair of bounds — and keep header and rows in one
  `overflowX` scroller so a pan moves them together.
- **A filter's rules are the app's, and a window measured them** — a filter is
  an `<input>` above the rows, so nothing in the runtime can make the four
  decisions a grid owns. `table-filter-lifecycle` typed a literal,
  case-insensitive query over 120 rows: `1` narrowed the painted set to **39**
  while the field kept the text session and the visible selection `item-1`
  survived; `12` narrowed to two and **cleared** the selection it hid, because an
  invisible selection would act on a record the reader cannot see; `12z` painted
  the empty state with no rows at all; clearing restored every row and parked the
  session back in the filter field; a −200 wheel and then a filter reopened the
  set at offset **0** — read from `scrollOffset`, since the readout alone would
  have passed while the list stayed put; `Down` from `Item 1` landed on
  `Item 10`, the next **filtered** row rather than the numeric one, with the real
  focus; and clearing the filter kept `item-10`, which the full set still holds.
  So keep the selection by **record** and clear it when the record leaves the
  set, leave the text session in the field while rows come and go, reset the
  scroller on a filter change, and walk the filtered array on arrow keys.
- **A column menu is app state, and a window measured what hiding or moving one
  costs** — the runtime has no table element, so the visible columns are one
  ordered list the header and every row read; the runtime still owns the
  geometry. `table-columns-lifecycle` opened six columns
  (120/80/160/100/140/90 = **690px**) in a 360px scroller: hiding `status` took
  the content to **610px**, unpainted that column's header and cells, and shifted
  every later column by exactly its **80px** while the header and its cells kept
  one `x`, the vertical offset stayed `-200` and the selection survived; a press
  on row 9's `owner` cell selected `r9`, the column that had moved into the gap;
  panning to the end reached `-250` (360 − 610); hiding `owner` while panned made
  the renderer **clamp its own offset** to `-90` (360 − 450) and report it
  through `onScrollChange`, so the grid calls no `scrollTo` and paints no blank
  space past the last column; and moving `owner` after `updated` changed the
  order and not the width, with the cells following the header. So derive every
  width and offset from the visible list, and read `onScrollChange` as the
  clamp's report rather than a value to set (`table-columns-lifecycle`).
- **A selection toolbar is told, and told when it empties** — the runtime has
  one app-level selection event, `render(<App/>, { onSelectionChange })`, and a
  window measured the contract (`window-selection-lifecycle`): a pointer drag
  over a selectable line reports the run `getSelectedText()` returns,
  `clearSelection()` reports **again** with no run (`last=none`), and a line
  that opted out of selection reports nothing. So a toolbar hides on the empty
  change instead of timing out, and it is installed once at the app root —
  there is no per-component hook. The payload carries the joined text only: no
  pane identity, no offsets, so a "comment on this line" action is a line
  press rather than a selection range.

## Gaps, with the evidence

| Gap | Evidence |
| --- | -------- |
| No table element | GPUix 0.11.0's element set has `div`, `text`, `img`, `svg`, `canvas`, `input`, `textarea`, `anchored`, `code`, `diff`, `markdown`, `virtual-list` — no table |
| No cell-level accessibility | `role`, `aria-label`, `aria-selected` and `aria-level` exist; `aria-colindex`, `aria-rowindex` and `aria-describedby` do not |
| Charts | No chart component; every drawing route is measured. `<svg source>` paints its markup as **one tint**, so a multi-series chart is one stacked `<svg>` per colour, and `<text>` inside the markup paints; a `setImagePixels` buffer keeps each pixel's own colour — three series inside one element — and its transparent margin composites onto the card behind it, uploaded from a layout effect; `setImage` decoding SVG **bytes** keeps every `fill`, which `<svg source>` cannot; `<canvas>` is measured **blank**, so the fill behind it shows through. Two limits: a translucent bar over another bar is unmeasured, and a buffer scales to its element's box, so a chart is drawn at its layout size |
| Hierarchical data | A tree view needs a `<virtual-list>` plus our own flattening; hierarchical virtualization is ours. `virtual-tree-lifecycle` measured the shape: one `<virtual-list>` child per visible node, 4 000 rows from 40 open directories, arrows moving native focus through `renderer.focusElement`, and a reveal by index |
| Resizable columns | Pointer events and `col-resize`/`row-resize` cursors exist; no column model, so the resize is application state. A window measured the drag (`column-resize-lifecycle`): a divider that listens to both `onMouseDown` and `onMouseMove` keeps **8 of 8** moves past its own box (160 → 220, a −150 drag clamping at **120**, the next +30 measuring from **150**, `right` stepping to **166** with header and cells on one offset), while a move-only divider hears **1 of 8** and resizes nothing |

The full runtime table is on [Runtime](/docs/runtime).

## Where a data change goes

- A **row primitive** (selection, sorting, filtering) → a pure module with a
  unit suite first; a component consumes it.
- **Table, tree and toolbar components** → `@gpuixui/components`, each with a
  native behaviour suite and a page under `packages/components/docs`.
- A **statistic card or a chart** → a Block until the behaviour is reusable; a
  chart composes a measured route — one tinted `<svg>` layer per series, a
  `setImagePixels` buffer uploaded from a layout effect, or SVG bytes through
  `setImage` — so it waits on a reusable chart component, not on a drawing
  surface.
- A **column layout in one app** → the app, or a Block, not a library prop.
