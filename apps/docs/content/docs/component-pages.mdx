A component page is not written from memory. It is one half of a record that also
feeds the component index, the sidebar, search and the API reference; the guards
below fail a page that loses a section, a source or a props table. This page is
the template to follow and the reason each piece exists.

## Two files

| Path | What it owns |
| ---- | ------------ |
| `apps/docs/content/docs/components/<slug>.mdx` | the page: prose, previews, sections |
| `apps/docs/src/component-meta/entries.ts` | the record: status, source, props types, runtime suite, limitations |

The page's frontmatter `title` and `description` must equal the record's `title`
and `summary`; `src/component-pages.test.ts` compares the pair for every
delivered component, so a rename is a two-file change.

## The record

Use `delivered(slug, title, tier, summary, options)` once the component exists.
`planned(...)` records have no page: they are shown in the index with their
status and wait for code.

| Field | What it must say | Guard |
| ----- | ---------------- | ----- |
| `sourcePath` | the repo-relative component file the page includes | `src/content-references.test.ts` resolves it |
| `api` | every exported props type the page generates | `src/content-references.test.ts` compares the set in both directions |
| `runtime` | the native suite: its command and its test file | `src/component-meta/native-coverage.test.ts` resolves both |
| `status` | the `COMPONENTS.md` row's status, not a guess | `src/component-meta/registry.test.ts` fails on drift |
| `limitations` | what the suite does not prove; required when a `done` row is partial | `src/component-meta/registry.test.ts` |
| `dependencies` | the package and workspace imports the entry file really has | `src/component-meta/dependencies.test.ts` re-derives them |

A compound component also declares `parts` (name and source path) and
`pattern: "stateful"`; a workspace component declares `pattern: "workspace"`,
its `persistence` and a `playgroundScreen`. Those rules live in
`src/component-meta/contract.ts` and are enforced before a page is written.

### Search vocabulary

Some components are never named the way a reader names them: `Text inputs` is
not `textbox`, and `OTP Field` never contains "one time password". Those terms
live in `apps/docs/src/lib/component-aliases.ts`, keyed by slug, and feed the
registry search document, the ranker and the index filter. Add a term only when
a reader would type it and the record's own fields cannot match it; an alias
that names another component is rejected, because it would misroute the query.

| Check | What it proves |
| ----- | -------------- |
| `src/lib/component-aliases.test.ts` | every key is a record, no term is shared or shadows a title or symbol, and the record's search document carries it |
| `src/lib/search.test.ts` | every alias reaches its component first, and a plain word keeps its own page |
| `apps/docs/scripts/smoke-build.ts` | two recovered terms reach their page in the production index |

## The sections

The section list is a function of the record's `pattern`. It is generated from
`src/component-meta/contract.ts`, so this table and the guard cannot disagree.

<PageTemplateSections />

A page missing a section fails `component-pages.test.ts` with the component and
the section name. The list is ordered: composition comes before the API
reference, and the API reference before keyboard notes.

Every page also starts with the status block and the native preview; a tier-A
approximation, where the record declares one, follows them:

```mdx
<ComponentState slug="button" />

<NativePreview slug="button" />

<ComponentPreview slug="button" />
```

## The blocks

| Block | What it does | Rule |
| ----- | ------------ | ---- |
| `<ComponentState slug>` | the status, GPUix-support line and limitations | mirrors `COMPONENTS.md`; never hand-written |
| `<NativePreview slug>` | the strongest honest native evidence tier | never falls back to a browser approximation |
| `<ComponentPreview slug>` | the labelled tier-A approximation | optional; only rendered through the approximation banner |
| `auto-type-table` (MDX tag) | the generated props table | one per type in `api`; the name must be a real export |
| `include` (MDX tag) | the real source file, read at build time | never a pasted copy; one per declared part |
| `<ComponentDependencies slug>` | the dependency list, derived from the entry file | nothing hand-maintained |
| `<RelatedComponents slug>` | cross-links declared in the record | a link to a planned component is a real page, never a 404 |

Two traps are worth naming: a self-closing `include` tag is silently skipped by
Fumadocs, so the page renders without source and no build error; and an
`auto-type-table` whose `name` is a typo renders an empty table. Both are
caught: `src/content-references.test.ts` compares the page's type names with
the record, and `src/component-api-tables.test.ts` resolves each table against
the file it names and requires at least one row.

## The preview

`<NativePreview>` reads the record and the capture sidecars and picks one tier:
a live GPUix scene, a real capture, the playground screen, or the native suite
coverage. The labels are mandated by `docs/preview-strategy.md`, and a page never
chooses a tier by hand.

- A browser approximation is allowed only through `<ComponentPreview>`, and it
  is always labelled "Illustrative approximation — not GPUix".
- A live scene appears only when the record declares `liveScene`; the scene must
  exist in `preview/scenes.ts`.
- A component with no suite is not given a tier V badge; `<NativePreview>`
  reports it as unverified instead.

## Live scenes

A live scene is a real GPUix surface: the component's own source, on the
published WebAssembly renderer, inside the isolated preview document. It is the
only tier a reader can interact with on the page, and it never replaces the
native evidence beneath it. A scene is expected when the record is `stateful`
(plan 508) — an exception is a written, test-pinned reason — or when the state
the page documents is one a still cannot prove; a static page uses a labelled
tier-A illustration instead. A scene is never a browser reimplementation of the
component — it mounts the package.

The build ships 49 scenes today. Every component scene comes from a record
that declares `liveScene`; the Showcase page and the three pattern pages add one
composition each. These files own the mechanism:

| Path | What it owns |
| ---- | ------------ |
| `src/component-meta/entries.ts` | the record field `liveScene`, which opts a page in |
| `preview/scene-contract.ts` | `LIVE_SCENES`, `SCENE_GESTURE`, `SCENE_INTERACTION`, `SCENE_LABEL`, `SCENE_PAGE` and the `SceneStep` union; dependency-free, so the search document can read it |
| `preview/scenes.ts` | `SCENE_TEXT` and `SCENE_STEP_TEXT`; re-exports the contract so every importer keeps one entry point |
| `preview/scene-views.tsx` | `LIVE_SCENE_VIEWS`: one real composition per scene |
| `preview/patterns/confirmation-flow.tsx` | a composed page's scene, kept out of `scene-views.tsx` so its source stays readable on the page |
| `preview/patterns/command-palette.tsx` | the second composed scene: the real palette opens from a control |
| `preview/patterns/project-browser.tsx` | the third composed scene: a query filters a real list, then a row opens |
| `preview/main.tsx` | the isolated document, both theme providers and the readiness contract |

The expectation table is the contract, not decoration:

| Export | What it decides |
| ------ | --------------- |
| `LIVE_SCENES` | every scene key the build ships; a record's `liveScene` must be one of them |
| `SCENE_TEXT` | the text the smoke looks for in GPUI's tree |
| `SCENE_GESTURE` | the steps that produce a state the component does not start in |
| `SCENE_INTERACTION` | the sentence shown above the surface, and the searchable instruction |
| `SCENE_PAGE` | the page that mounts a composition scene |
| `SCENE_LABEL` | the reader-facing name of a composition scene |
| `SCENE_TEXT_IS_SCENE_PROSE` | the measured exception for a component that paints no text |

### The gesture vocabulary

A scene that needs an interaction declares steps instead of mounting the state
directly. The smoke runs them through the renderer's own automation API, asserts
the expectation is **absent before** the steps and **present after** them, and
fails naming the scene when either half is wrong.

| Kind | Drives | Fields |
| ---- | ------ | ------ |
| `hover` | a tooltip or preview card opening | `testId` |
| `click` | a press, including a right click | `testId`, optional `button: 2` |
| `click-text` | an option that owns no test id | `text`, `within` (the control's test id) |
| `press` | a key on a focused control | `testId`, `keys` |
| `fill` | typing through the renderer's keyboard path | `testId`, `text` |
| `wheel` | a real scroll away from a tail | `testId`, `deltaY` (positive scrolls up) |

### The readiness contract

`preview/renderer-ready.ts` asks the renderer for its window handle.
`render()` returning and the DOM canvas both happen before asynchronous
graphics init, so neither is a readiness signal; a scene that focuses on mount
fails without the handle. The smoke waits for a canvas larger than 1×1, forces
the colour scheme and the platform, and proves the whole page follows them.
A scene mounts inside both theme providers with the same resolved theme:
`@gpuixui/primitives` owns its context and `@gpuixui/components` reads
`@gpuixui/tokens/react`, so one provider leaves half the composition light on a
dark page (plan 457 §9).

| Check | What it proves |

| `src/components/preview/preview-gaps.test.ts` | `docs/preview-strategy.md` names the same gaps as the code |

### Adding a scene

1. Add `liveScene: "<key>"` to the record and the page's previews; the key is
   the component's slug by convention.
2. Add the key to `LIVE_SCENES`, its expectation to `SCENE_TEXT`, and — when
   the state needs an interaction — the steps to `SCENE_GESTURE` and the
   reader's sentence to `SCENE_INTERACTION`.
3. Compose the real component in `LIVE_SCENE_VIEWS`, importing Tier 2 parts by
   subpath (the package root pulls the Toast provider's Effect runtime into a
   20 MB browser bundle).
4. Give every gesture target a `testId` the composition really paints, and keep
   the expectation out of the scene's own heading: it must be text the component
   paints.
5. Run `nub run --filter docs test` and
   `nub run --filter docs smoke:preview`; update
   `docs/preview-strategy.md` only when a tier claim changes.

## Checklist

1. Add the `delivered(...)` record with its source, props types, runtime suite
   and limitations.
2. Create `content/docs/components/<slug>.mdx` with the frontmatter matching the
   record.
3. Add the status block, the previews and the sections in the order above.
4. Include the real source and generate every declared props type.
5. Add the page to `content/docs/components/meta.json` and its tier separator if
   it opens a new group.
6. Run `nub run --filter docs test`, then `nub run check` and `nub run lint`.

A page that cannot pass these guards is not finished, and its inventory row is
not `done`.
