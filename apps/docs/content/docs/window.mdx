The library paints inside one native window. `@gpuix/react` opens it with
`render()`, `@gpuix/native` owns its `WindowOptions`, and everything on this
page is the host application's side of that boundary: none of it is a component,
a token or a preview.

## Opening the window

`render()` takes the React tree and the window options in one call:

```tsx title="main.tsx"
import { render } from "@gpuix/react";
import { App } from "./app";

render(<App />, {
  title: "Notes",
  width: 1100,
  height: 720,
  minWidth: 720,
  minHeight: 480,
});
```

That call also starts the frame loop; the process exits when the last window
closes. The pace, the platform's tick rule and the exit are
[Frame loop](/docs/frame-loop)'s subject. Calling `render()` again in the same
process is a **remount**, not an error: the previous tree is unmounted and the
new one mounts into the same window and loop, which is the hot-reload path. A
custom root — a different renderer, or window-level error handling — uses
`createRoot(renderer, handlers)` from the same package instead.

## Window methods

The renderer exposes the window operations a custom title bar or window control
needs. Read it with `useGpuixRequired()`; the methods are optional on the
renderer type, so an application calls them optionally.

```tsx
import { useGpuixRequired } from "@gpuix/react";
import { Button } from "@gpuixui/primitives";

export function WindowActions() {
  const renderer = useGpuixRequired();

  return (
    <Button onClick={() => renderer.toggleFullscreen?.()}>Fullscreen</Button>
  );
}
```

<WindowMethodsTable />

`getWindowSize()` is the size layout sees: the paintable content, excluding the
platform title bar. `setWindowTitle()` changes the OS title after the window is
open; it is not in-app text.

## Size and insets

`useWindowSize()` and `useWindowInsets()` poll the renderer every 100 ms by
default. Pass `{ intervalMs: false }` for one read, or a number to change the
sampling interval. Insets matter on a notched display and when a soft keyboard
is open.

```tsx
import type { ReactNode } from "react";
import { useWindowInsets } from "@gpuix/react";
import { Box } from "@gpuixui/primitives";

export function Shell({ children }: { readonly children: ReactNode }) {
  const insets = useWindowInsets();

  return (
    <Box style={{ paddingBottom: insets.effective.bottom }}>{children}</Box>
  );
}
```

`useWindowInsets()` returns the renderer's three regions plus the observer's
three keyboard numbers; the table above is that full shape.

## Display scale and pixel density

Every number this page takes is a **logical pixel**: `WindowOptions` sizes,
`getWindowSize()` and a `style` dimension all describe the same layout unit, so
a layout is written without a scale multiplier.

The runtime exposes no way to read the display's backing scale. There is no
`devicePixelRatio`, `scaleFactor`, pixel-ratio or OS-zoom query in the installed
declarations, so a component cannot branch on 1× versus 2× from JavaScript. The
row is one of the [absences](#what-the-window-does-not-provide) below.

Two consequences follow for assets:

- **Icons stay sharp.** An [icon](/docs/components/icon) paints `SvgProps.source`
  — vector markup sized by `iconPixels` — so there is no 1×/2× icon file to
  choose.
- **A raster image is one file.** [`img`](/docs/native-elements) takes `src`,
  `objectFit` and `alt`; there is no `srcSet` or density descriptor, so the file
  is painted into its layout box and `objectFit` decides the fit. If the target
  displays are dense, pass a larger asset; nothing selects one automatically.

Whether the compositor rasterises at 1× or 2× is the platform's decision, and no
probe in this repository has measured a painted frame at either scale. The
[Performance](/docs/performance) page owns that measurement rule, and
[Typography](/docs/typography) owns the typeface side of the same question.

## Custom window chrome

A desktop application that draws its own title bar sets
`titlebarTransparent: true` and positions its chrome around the native traffic
lights with `trafficLightX` / `trafficLightY`. On macOS the traffic lights
themselves stay native — there is no API to draw or hide them. `windowBackground`
chooses between an opaque, a transparent and a blurred window behind the tree;
`transparent: true` is the plain alpha form.

The [App shell pattern](/docs/patterns/app-shell) composes the in-content frame:
a title bar, a navigation rail, a scrolling content region and a status bar. It
is a composition of layout primitives, not a window API — this page is the
window, that page is what to paint inside it.

## Wayland layer shell

On Wayland, `layerShell` opens a compositor-anchored surface instead of a
floating window: a top bar, a dock, a notification overlay or a wallpaper. The
window has no native titlebar in that mode.

```tsx
// `StatusBar` is your application's root; any React tree works here.
render(<StatusBar />, {
  appId: "dev.gpuixui.bar",
  layerShell: {
    layer: "top",
    anchor: ["top", "left", "right"],
    exclusiveZone: 32,
    keyboardInteractivity: "none",
  },
});
```

Set `appId`: a compositor matches its window rules by it. The surface namespace
cannot change after creation. Other platforms ignore the option.

## Native file picker

`promptForPaths()` opens the operating system's picker — the same dialog the
platform uses for any application — and resolves `null` when the user cancels.
It is not a component and has no browser equivalent.

```tsx
import { useGpuixRequired } from "@gpuix/react";

export function usePathPicker() {
  const renderer = useGpuixRequired();

  return async (): Promise<string | null> => {
    const paths = await renderer.promptForPaths?.({ prompt: "Open note" });
    return paths?.[0] ?? null;
  };
}
```

## The frame overlay

The runtime ships its own frame overlay, painted into the scene after layout. It
is the tool for "is this frame slow?", and it is not a browser element
inspector.

```tsx
import { useGpuixRequired } from "@gpuix/react";

export function useFrameOverlay() {
  const renderer = useGpuixRequired();

  return (mode: "hidden" | "minimal" | "full") =>
    renderer.setDebugFrameOverlay?.(mode);
}
```

`cycleDebugFrameOverlay()` steps hidden → minimal → full → hidden.
`getDebugFrameOverlayStats()` returns the same numbers the overlay paints —
current, p90, p99, max, frames and samples — and
`resetDebugFrameOverlayStats()` clears the last 1 000 draw samples without
resetting the frame count. The same overlay can be requested at mount time with
`render(node, { debugFrameOverlay: "minimal" })`.

[Performance](/docs/performance) records which measurements exist; the overlay
is how a consumer takes their own.
