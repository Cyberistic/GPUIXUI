GPUIXUI is a TypeScript-first monorepo. The library packages point one way:

```
tokens → icons → primitives → components → data-grid · docking · editor
```

## Library packages

- `@gpuixui/tokens` — colour, spacing, typography, radii and density roles. It
  depends on nothing else in the repository.
- `@gpuixui/icons` — the monochrome SVG icon set, sized from the token scale.
- `@gpuixui/primitives` — foundational parts: layout, text, buttons, inputs and
  the value controls. It depends on tokens and icons. Its `core/` entry point
  holds the pure decisions behind those components; [Extending](/docs/extending)
  documents the layer and the rule for adding to it.
- `@gpuixui/components` — composition and feedback components. It reads tokens
  directly and wraps GPUix's headless `select`, `combobox` and `tooltip` where
  those exist.

`@gpuixui/data-grid`, `@gpuixui/docking` and `@gpuixui/editor` are planned and
have no package yet; the [component index](/docs/components) records what exists
and what is still planned.

## State and Effect

Effect is part of the architecture, not of the component API. Two rules hold
across the packages:

- **Decisions are plain functions, and failure or absence is data.** The
  `core/` layer under `@gpuixui/primitives` is written in Effect's data modules
  (`Option`, `Array`, `Order`), so a decision has no nullable return and no
  thrown error to forget. [Extending](/docs/extending) documents that layer.
- **A runtime exists only where a component owns ongoing work.** `ToastProvider`
  is the package's only `ManagedRuntime`: it creates one over the toast store's
  `layer`, and `useToast()` sends commands to it.
- **A single synchronous effect runs at the boundary that needs it, with no
  provider.** `Form`'s submit runs `validateAll` with `Effect.runSync`, and the
  type-ahead window reads a monotonic clock the same way. The exported
  `validate` and `validateAll` return `Effect`s, so a caller outside `Form`
  decides when to run them.

What stays with the application: time. `Countdown` owns no timer and renders the
`remainingMs` your clock passes. Using the components does not require writing
Effect code — `@gpuixui/components` declares `effect` as a dependency because its
toast runtime and those boundaries need it, and `@gpuixui/tokens` declares no
dependencies.

## Tooling

- `@gpuixui/config` — the shared TypeScript configuration.
- `@gpuixui/testing` — the platform-free smoke harness; [Native smoke
  suite](/docs/native-testing) explains it and its playground adapter.
- `@gpuixui/deploy` — the Alchemy stack declarations; [Deployment and
  hosting](/docs/deployment) reads them.

No library package is published to a registry yet.

## What runs where

| Surface | Renderer | What it proves |
| ------- | -------- | -------------- |
| A desktop app using the library | GPUix's native renderer (`@gpuix/native`) | the target the components are built and tested against |
| The live previews on this site | the published GPUix **WebAssembly** renderer, in an isolated document under `/gpuix-preview/` | the real component code paints; it is not a DOM imitation |
| This site's own chrome | React in the browser, server-rendered by TanStack Start and then hydrated | documentation only — its shell never imports the native runtime |

The library is not a DOM component set: every component renders GPUix host
elements, so the same code paints under the desktop binary and — through the
published wasm build — inside a browser. That is the only browser story the
project has; there is no HTML/CSS build of the components, and a browser
approximation on this site is labelled as one.

This site is server-rendered and then hydrated. The previews take their mode and
platform from what the providers publish on `<html>` — `data-platform` and the
`dark` class — through one `useSyncExternalStore` snapshot, so a preview cannot
disagree with the chrome around it and a shared `?platform=` link paints the
right surface after hydration.

## Preview strategy

Rather than fake a native surface, every preview is one of:

1. a **live GPUix surface** — the real component code on the published
   WebAssembly renderer, in an isolated document that loads on request;
2. a **real native run** in the playground, named per component when a screen
   exists;
3. a **real screenshot** captured from the GPUix runtime;
4. **native coverage** by an automated suite, naming the suite and its command;
5. a **browser approximation**, always labelled "not GPUix";
6. **source and a limitation notice** when the runtime cannot do something.

Which tier a page gets, the exact labels and the rules for a capture are on
[Previews](/docs/previews), with the maintainer specification in
`docs/preview-strategy.md` in the repository. What the pinned runtime can and
cannot do — measured, with the scenario that proves each row — is on
[GPUix capabilities](/docs/capabilities). No per-component playground screen
exists yet, so most delivered pages name their native coverage or show the live
surface, and the static ones carry a labelled approximation.
