title: Motion
description: Springs, easing, keyframes, inertia and reduced motion — the physics a GPUix motion target does not compute, sampled from a clock the caller owns.

GPUix tweens a numeric style field on its own clock: `motion.div` walks
`initial` → `animate` → `exit` and reports `onMotionComplete`. `@gpuixui/motion`
is the layer above that — closed-form springs, retargeting that keeps velocity,
keyframes and stagger, inertial decay, and reduced motion as a policy. It is
pure: no timers, no observers, no GPUix import. Every function samples at an
elapsed time you pass in, so a movement is a value in a test rather than a wait.

## What the package owns

| Module | Responsibility |
| ------ | -------------- |
| spring | `springPhysics`, three presets, `sampleSpring`, `atRest` and `retarget` — under-, critical- and over-damped integration |
| easing | `linear`, `easeIn` / `easeOut` / `easeInOut`, `circIn` / `circOut` / `circInOut`, `backIn` / `backOut` / `backInOut`, `anticipate` and `bezier` |
| timeline | `keyframe` + `sampleKeyframes`, `stagger` and the keyed `Sequence` driver |
| inertia | `inertia`, `project` and `sampleInertia` — exponential decay with optional hard bounds |
| value | `MotionValue` and its transitions: `instant`, `tween`, `springTransition`, `transitionEquals` |
| React | `useSpring`, `useTransition`, `useInertia` and `useMotion` from `@gpuixui/motion/react` |
| timing | `motionLevels`, `motionEasings` and `motionTiming` — the house durations and per-phase easing, in the runtime's seconds |

The primitives paint their one moving piece — a switch's thumb, a busy
spinner — with the **runtime's** declarative `motion.div` and a plain duration,
and the library's surfaces do the same: `motionTiming` names the house levels and
the per-phase easing below, and
`packages/components/src/internal/presence.tsx` composes them into a fade plus an
inset offset. The physics a surface does not need (a spring retargeted
mid-flight, a stagger, a momentum coast) stay here for the components that
scrub, count or follow a gesture. The reduced-motion preference is the
application's, since the runtime exposes none: `MotionProvider` from
`@gpuixui/components` carries it and a reduced run is a zero-duration
assignment. Per-surface table: `/docs/components` pages and
`docs/component-api.md` §11.

## The clock is yours

Every function takes an elapsed time in milliseconds and returns a sample.
Nothing schedules, sleeps or watches: `sampleSpring(layoutSpring, 0, 1, 0, 2000)`
settles because the maths says it has, not because a timer fired. A caller can
therefore drive motion from a gesture, a scroll offset or a test's frozen clock.

The hooks are the only place a clock is read. Each keeps one `performance.now()`
origin for the life of the component and samples every 16 ms, clearing its timer
on unmount. A hook is an app-boundary convenience; the pure functions are the
contract.

## House timing

`motionTiming(level, options)` turns one house level into the object the runtime's
`transition` prop reads: a duration in **seconds**, because the runtime reads
seconds while the levels are authored in milliseconds, and the easing for the
phase.

| Level | Milliseconds | For |
| ----- | ------------ | --- |
| `step` | 120 | a step indicator's tick |
| `fast` | 160 | a small affordance: a tooltip, an indicator |
| `normal` | 200 | a surface arriving: a popover, a menu, an accordion panel, a tab pill |
| `slow` | 320 | a surface that owns the window: a dialog, a drawer |
| `notice` | 500 | a notice that may be read while it leaves: a toast |

The phase chooses the easing, never the duration — `phase` defaults to
`standard`:

| Phase | Easing | Why |
| ----- | ------ | --- |
| `enter` | `easeOut` | a surface arrives decelerating |
| `exit` | `easeIn` | it leaves accelerating |
| `standard` | `easeInOut` | a movement between two resting states eases at both ends |

```ts
import { motionTiming } from "@gpuixui/motion";

const enter = motionTiming("normal", { phase: "enter" });
// { duration: 0.2, ease: "easeOut" }

const still = motionTiming("slow", { preference: "reduced" });
// { duration: 0 } — the target is assigned, not tweened
```

Under `preference: "reduced"` the duration is `0` and no easing is named. The
caller keeps the frames — an opacity, an offset — so the resting appearance never
depends on the preference.

## Springs

| Preset | Stiffness | Damping | For |
| ------ | --------- | ------- | --- |
| `affordanceSpring` | 320 | 34 | short, subtle feedback — a press or a toggle |
| `layoutSpring` | 260 | 28 | committed layout motion: collapse, expand, insert, remove |
| `continuitySpring` | 190 | 23 | a target that changes mid-flight: a pane, a divider, a zoom |

`springPhysics(params)` is the sanitising constructor. A non-finite or
non-positive mass, stiffness, rest delta or rest speed falls back to its
default; damping may be **zero** (a spring with no resistance) and is otherwise
non-negative; every value is clamped, so a spring built from user input cannot
produce `NaN` or blow up. Whatever comes out can be sampled.

```ts
import { layoutSpring, retarget, sampleSpring } from "@gpuixui/motion";

// 80 ms into a run from 0 → 1 — value and velocity live.
const mid = sampleSpring(layoutSpring, 0, 1, 0, 80);

// Retargeting keeps both, so a change of mind continues the movement
// instead of starting a second one.
const next = retarget(mid, 2);

export const at = sampleSpring(
  layoutSpring,
  next.value,
  next.target,
  next.velocity,
  1_000,
).value;
```

`sampleSpring` returns `{ value, velocity, target, settled }`, and `settled` is
the rest test `atRest` performs: within `restDelta` of the target and within
`restSpeed` of a standstill. A caller can stop sampling on that flag rather than
guessing a duration.

**The repair belongs to the sampler, not the constructor.** `SpringPhysics` is an
exported **structural** interface, so a caller may write one by hand and skip
`springPhysics()` entirely — `{ mass: 1, stiffness: 260, damping: NaN }`
type-checks. `sampleSpring` and `atRest` therefore repair what they are handed:
a mass, stiffness, damping or rest threshold that cannot be read takes the
house default, so a hand-built spring samples as the built one does. Without
that repair a `NaN` damping made every formula answer `NaN` and the spring
jumped to its target in a single frame, while a `NaN` rest threshold meant the
run never settled at all — a driver waiting for rest sampled it forever.

## One retained value

`MotionValue` holds a scalar across samples, which is what a gesture needs
between releases.

```ts
import { MotionValue, layoutSpring, springTransition } from "@gpuixui/motion";

const width = new MotionValue(120);
width.animate(240, springTransition(layoutSpring));

// Sample at elapsed times the caller owns. `complete` is a one-shot edge.
const first = width.sample(16);
const last = width.sample(500);

export const [moving, settled] = [first.active, last.complete];
```

- `set` assigns a value and cancels any run without momentum;
  `animate(target, transition)` retargets from the current presentation;
  `coast(inertia, velocity?)` starts a decay from the last value.
- An `animate` call that repeats the current target **and** an equal transition
  is a no-op, so re-declaring `springTransition(layoutSpring)` on a render does
  not restart the run.
- A `coast` is compared by its declaration the same way: re-declaring the
  inertia already in flight with the same release velocity is a no-op, so a
  render that builds `inertia()` again does not relaunch the run at full speed
  from the sample on screen (which would overshoot its rest and never settle).
  Another release velocity, a changed time constant or a different bound is a
  new gesture and starts from the presentation — and so is a coast after `set`
  or `animate`, because each retires the run it cancelled.
- `sample` clamps a non-monotonic time to the last sample, so a clock that steps
  backwards cannot rewind the paint.
- `complete` is true only on the sample that finishes the run; `active` says
  whether another sample will move the value.
- A transition is `instant`, `tween()` — `DEFAULT_TWEEN_MS` of 300 ms, easing
  with `easeOut` — or `springTransition(physics)`, and `transitionEquals`
  compares two declarations structurally rather than by identity.

## Keyframes, stagger and sequences

A keyframe list is normalised progress, not milliseconds, so the same timeline
scales to any duration:

```ts
import { easeOut, sampleKeyframes, stagger } from "@gpuixui/motion";

const offsets = [
  { at: 0, value: 0 },
  { at: 0.6, value: 120, easing: easeOut },
  { at: 1, value: 100 },
];

export const halfway = sampleKeyframes(offsets, 0.5);
export const delayAt = (index: number) => stagger(20, index, 3, "center");
```

Frames must be sorted ascending by `at`. `t <= first.at` returns the first value
and `t >= last.at` the last, so the ends do not extrapolate; between two frames
the **upper** frame's easing shapes the segment that ends at it. `stagger(stepMs,
index, count, from?)` returns a delay from `start`, `end` or `center`.

A frame whose `at` or `value` cannot be read **is not a stop**: `sampleKeyframes`
drops it before sampling, so the segment spans its readable neighbours instead
of interpolating to `NaN`, and a list with no readable frame samples `0`. That
repair sits in the sample rather than in `keyframe()`, so a hand-built list is
treated the same as one built with the helper — a `NaN` value from a measurement
removes a stop instead of erasing the animation.

The curve is repaired the same way. The progress a curve is handed is clamped
into `[0, 1]`, and a curve that answers `NaN` (or an infinity) is **not a
curve**: the run falls back to the linear progress, so it still starts, ends and
completes exactly instead of painting nothing for its whole journey. A caller's
own easing — `tween(300, myEasing)` — and a keyframe's `easing` both go through
it.

`Sequence` positions keyed steps in absolute elapsed time and samples all of
them at once — `at`, `append`, `stagger`, `duration`, `sample` and `complete`.
Each sample is `{ key, state, value }` with `state` one of `pending`, `active`
or `completed`. It is a driver, not a scheduler: nothing advances without a
sample, so a sequence can be scrubbed, frozen in a test, or driven by a gesture.
It repairs a hand-built step too: a start that cannot be read is placed at `0`,
and a duration the step cannot **run** — one that is not a number, or one that
is not positive — is no duration at all, so a step with no readable duration is
**completed on the first sample** and `duration()` stays a number.

The sequence's own **end** follows the step it still has to run: a duration the
step cannot run ends at its start, so `duration()` never lands before a step the
sequence still owes and `complete()` cannot answer `true` while a step is
pending.

The two stagger entry points answer alike. A step that is not a wait — one that
is non-finite or negative — is no wait rather than a `NaN` delay for the
standalone `stagger()` **and** for `Sequence.stagger`, so a caller cannot get
two answers for the same input, and no member of a group starts before the
sequence does: the group's members all sit at the group's start.

## Inertia

```ts
import { inertia, project, sampleInertia } from "@gpuixui/motion";

const scroll = inertia(350, { min: 0, max: 2_400 });

export const rest = project(scroll, 100, 900);
export const frame = sampleInertia(scroll, 100, 900, 120);
```

`inertia(tauMs, bounds?)` builds the decay constant and its hard bounds; the
time constant defaults to 350 ms, a non-finite or non-positive value falls back
to it, and inverted bounds are swapped rather than refused. `project` answers where a release would settle — position
plus velocity times the time constant, clamped — and `sampleInertia` decays
toward it exponentially, clamps at a bound with **zero** velocity, and reports
`settled` once the remaining speed is at or below the rest threshold. There is
no boundary spring: a bounce at the edge is not modelled.

**The repair belongs to the sample, not the constructor.** `Inertia` is an
exported **structural** interface, so a caller may write one by hand and skip
`inertia()` entirely — `{ tau: NaN, min: null, max: 10 }` type-checks. Both
samplers therefore repair what they are handed: an unreadable time constant
takes the house constant (`DEFAULT_TAU_MS`), an unreadable bound is dropped on
its own while the bound beside it still clamps, an inverted pair is read as the
range it describes, and a position or velocity that is not a number reads as a
standstill. `project({ tau: NaN, min: null, max: 10 }, 0, 100)` is `10`, and
`sampleInertia` on the same value settles. Before that, a hand-built inertia
answered `NaN` from both, so a `MotionValue` coasting on one painted `NaN` into
its target and never reported `complete`.

## In React

```tsx
import { motion } from "@gpuix/react";
import { layoutSpring } from "@gpuixui/motion";
import { useSpring } from "@gpuixui/motion/react";

export const Grow = ({ open }: { readonly open: boolean }) => {
  const { value } = useSpring(open ? 240 : 120, layoutSpring);
  return <motion.div animate={{ width: value }} transition={{ duration: 0 }} />;
};
```

Each hook returns `{ value, velocity, complete }` and accepts
`{ reducedMotion, initial }`. `initial` is the value the **first** run starts
from — the default is the target, so a hook mounted at rest paints without an
entry run. It is read once at mount: a later change is ignored, because the
current presentation is the truth after it. An `initial` the hook cannot read is
**no** initial — the run starts at the target — and an unreadable target starts
at `0`, so the first frame is always a number the runtime paints rather than the
`NaN` it draws as nothing. `useSpring` and `useTransition`
build their transition from primitive arguments, so passing a physics preset or
a tween inline is safe; `useMotion(target, transition)` takes the transition
itself and compares structurally, but its effect re-runs on the reference — pass
a module constant or a memoized value.

The `transition={{ duration: 0 }}` is deliberate: the hook has already sampled
the physics, so the runtime assigns the number instead of tweening it a second
time. The package drives the numeric fields a GPUix `MotionStyle` has — `width`,
`height`, `top`, `right`, `bottom`, `left`, `opacity` (0–1) and `borderRadius`.
There is no `transform` key, so scale, rotate and translate cannot be painted or
animated; motion on those axes waits on a runtime change.

## Reduced motion is a policy, not a capability

The pinned runtime exposes no reduced-motion preference — the capability record
calls detection **`not supported`**, a measured absence rather than an unrun
probe, because the typings publish no preference query — so the app supplies
one. Every hook takes `reducedMotion`, and `MotionValue.sample(elapsed, true)`
finishes an active run immediately at its target with zero velocity, including
an inertial coast. The library never guesses the preference; the same split
appears in the primitives, where `Button` and `IconButton` take a
`reducedMotion` prop for the busy spinner and `Switch` slides its thumb for
150 ms by default, landing in place of travelling only when the caller passes
`reducedMotion`.

## What the runtime measured

The runtime's own tween and this package's samples meet at one measured seam.
The probe (`motion-geometry`) and the rest of the table are on
[Runtime capabilities § Measured in a window](/docs/runtime#measured-in-a-window):

- A 3 s `easeInOut` transition painted `40, 43, 117, 123, 221, 240, 240, 240`,
  so the runtime tweens rather than jumping, and `onMotionComplete` fired once
  per run.
- The animated box **clips** its content instead of reflowing it: a fixed
  320 × 200 child kept its size while its parent was 120 × 40 and while it was
  240 × 240. Animate an outer `overflow: "hidden"` box for a collapsing sidebar
  or a growing row.
- `duration: 0` paints the two target sizes with no frame between them — the
  negative control, and the reason the hook example above assigns the value.

## Limits to design around

- **No `transform`.** Scale, rotate and translate have no style key; a
  `MotionValue` is a number, so motion is confined to the fields the runtime
  can paint.
- **A value, not a graph.** One sample is one scalar. A colour, a shadow or a
  multi-property timeline is several values you compose yourself.
- **No scheduler.** `Sequence` and `MotionValue` advance only when sampled, and
  the hooks sample on a 16 ms timer, so a paused tab pauses motion. A list that
  reorders while it animates still owns its own identity.
- **No boundary spring.** Inertia stops at its bound at zero velocity; a bounce
  is out of scope.
- **The runtime clips, it does not reflow.** A collapsing sidebar animates an
  outer clipped box; its content keeps its size throughout the run.

## Provenance

The spring and timeline maths is a TypeScript port of `open-gpui`'s
`crates/motion` (Apache-2.0), and `MotionValue` and the inertia API follow
`gpui-ce-motion` (MIT OR Apache-2.0). Neither is vendored or imported, and the
notices a port has to carry are recorded in
