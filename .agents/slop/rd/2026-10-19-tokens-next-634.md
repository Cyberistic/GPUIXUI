## Finding

**The field's query row charged its leading icon as an adornment.** Plan 624
added the query-row bound and plan 632 corrected the date trigger's disclosure
tier, but `fieldMinWidth` still charged two `fieldAdornmentSize` terms:

```ts
// metrics.ts, as of plan 632
fieldMinWidth ≥ max(
  chipMinWidth + 2 * controlPaddingX.md + 2 * borderWidth.thin, // 102
  2 * spacing.md + 2 * fieldAdornmentSize + 2 * spacing.md +
    typography.body.fontSize,                                   // 78
);
```

The lead is `<Icon size="md" />` — `iconSize.md` — and only the trailing action
is the adornment. At the shipped identity both tiers are 16, so the defect is
invisible in the shipped sets:

```ts
const lifted = extendTheme(getTheme("light"), {
  iconSize: { xs: 12, sm: 14, md: 20, lg: 24, xl: 28 },
  dimensions: { chipMinWidth: 10, fieldMinWidth: 81 },
});
```

returned **`[]`** from `themeMetricFailures` and `themeFailures` while the query
row needed `8 + 20 + 8 + 14 + 8 + 16 + 8 = 82`: a copied theme could lift its
icon tier and the field would clip or shove its own leading glyph while the
guarantee stayed green. The chip bound is 32 in this fixture, so only the query
row decides the result.
