## 1. Why

`packages/tokens/src/docs.test.ts` parses the colour tables in
`docs/tokens.md` and fails if they disagree with the shipped themes (plan 056).
The rest of the catalogue is hand-written and unguarded: typography, spacing,
radius, density, elevation, motion, border widths, icon sizes and avatar sizes.
A palette edit already fails the suite; a density or motion edit silently ships
a document that lies.

The typography, platform and colour tables are also generated by the docs site
from the package, but `docs/tokens.md` is the repo's own catalogue and the
source the Theming page's prose follows. It must be true on its own.

## 2. Design decision

Do **not** write six markdown parsers. Build the exact documented row from the
implementation and assert the markdown contains it:

```ts
expect(markdown, `spacing.${token}`).toContain(`| \`${token}\` | ${pixels} |`);
```

This is a one-way check (the markdown may carry extra rows), which is the
honest scope: the failure it guards is a documented value that no longer matches
the code. A parser would add brittle grammar for every table and buy nothing the
builders do not already give.

The only special case is density, whose `comfortable` row is labelled
`(default)`; build the label from `defaultDensity.name`.

## 4. The assertions

One `it` per table, each iterating the implementation:

| Test | Built row |
| ---- | --------- |
| typography | `` | `${role}` | ${fontSize} | ${lineHeight} | ${fontWeight} | `` for every non-family key of `typography` |
| spacing | `` | `${token}` | ${pixels} | `` |
| radius | `` | `${token}` | ${pixels} | `` |
| density | `` | `${label}` | ${h.sm} / ${h.md} / ${h.lg} | ${p.sm} / ${p.md} / ${p.lg} | ${rowHeight} | `` |
| elevation | `` | `${level}` | `${shadow}` | `${shadow}` | `` with `shadow = "${offsetX} ${offsetY} ${blurRadius} ${spreadRadius} ${color}"`; `overlay` asserts the documented empty list |
| motion | `` | `${level}` | ${milliseconds} | `` for every level except `ease` |
| borders, icons, avatars | `` | `borderWidth.thin` | 1 | ``, `iconSize.*`, `avatarSize.*` |

Typing rules: filter `Object.entries(...)` on `typeof value === "object"` /
`typeof value === "number"`; no casts, no `any`, no non-null assertions.

## 6. STOP conditions

Stop and report if:

- a guard fails because the document is **right** and the implementation is
  wrong — that is a product bug, not a docs bug; fix the implementation with its
  own test instead;
- a table's shape changed so the builder cannot describe it (for example the
  docs gained a column) — update this plan before changing the test;
- you are about to parse markdown with a general table parser — do not; use the
  builders in §4.

## 7. Test plan

- Every new `it` asserts a real substring built from the implementation, so
  `check:tests` accepts it and a wrong value fails it.
- **Able to fail:** change `` | `slow` | 320 | `` to `` | `slow` | 300 | `` in
  `docs/tokens.md`, run the suite, observe the motion test fail, revert, observe
  green. Do the same once for typography (`body` 14 → 13) and once for density
  (`compact` rowHeight 28 → 30).
- Record the observed failures in the commit message; do not claim a direction
  that was not run.

## 8. Acceptance criteria

- The seven tables in §4 are guarded; a value edit in any of them fails the
  package test suite with the token name in the message.
- No product source changes, no new dependency, no markdown parser.
- `nub run --filter @gpuixui/tokens test` and `nub run check` exit 0, and the
  failing direction was observed.
