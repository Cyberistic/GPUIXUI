# 507 — The icon catalogue: every shipped icon is visible and findable

**Status:** implemented (2026-10-18) · **Phase:** F (docs completeness / search) ·
**Owner:** docs-site
**Depends on:** `410`, `411`, `419`, `431`, `490`, `500`, `504`, `505`; the shipped
`@gpuixui/icons` package.

## 1. The defect this plan fixes

`/docs/components/icon` documents *how* an icon works but never says **which
icons exist**. The page tells the reader that `name` is an `IconName` and that
"TypeScript rejects an unknown name" — and then gives them no list to type from.
The package ships **48 icons** in `packages/icons/src/names.ts`, ordered and
typed, while the page shows none of them.

Measured against the production build on 2026-10-18:

| Query | Result before this plan | Should be |
| ----- | ----------------------- | --------- |
| `chevrons-up-down` | **`[]` — zero results** | `/docs/components/icon` (first) |
| `star-filled` | **`[]` — zero results** | `/docs/components/icon` (first) |
| `external-link` | prose about links, never the Icons page | `/docs/components/icon` (first) |
| `IconName` | `/docs/api-reference` (the type index) | Icons page also lists every name it admits |
| `arrow-left` | **`[]`** | `/docs/components/icon` (first) |

So a consumer who reads `name: "arrow-left"` in a package or an example is told
the docs have no such icon. This contradicts `MISSION.md`'s component-page
requirement ("important variants", "API/prop docs") and the site's own promise
that the Icons page documents the set. Plan 490 indexed the `icons` **record**
as one value export; the 48 names inside it were never indexed, the same gap
plans 504 and 505 closed for token roles and capability scenario ids.

There is a second, smaller defect: the gallery cannot be imported from the
package in the browser. `@gpuixui/icons`' root pulls `effect/Record` (through
`registry.ts`) into whatever imports it, and `src/architecture.test.ts` keeps the
Effect runtime and every GPUix runtime package out of the docs bundle. The
catalogue therefore has to be **generated at build time** from the package
source, which is the established pattern for `api-values.generated.ts`
(plan 490) and satisfies MISSION's single-source rule: a new icon must appear
with no docs edit beyond regenerating.

### 2.1 `src/lib/icon-catalogue.ts` (new)

The derivation, at the same test/script boundary as `src/lib/api-values.ts`
(`node:fs`, native array helpers; the browser never imports this module).

Exports:

- `interface IconCatalogueEntry { readonly name: string; readonly markup: string }`
  — `markup` is the exact `<svg …>…</svg>` string `packages/icons/src/registry.ts`
  hands to the runtime's `<svg source>`;
- `deriveIconCatalogue({ root })` — reads
  `packages/icons/src/names.ts` (the ordered `ICON_NAMES` array) and
  `packages/icons/src/registry.ts` (the `ATTRIBUTES` string list and the
  `shapes` map), then composes each entry as
  `<svg ${attributes}>${shape}</svg>` in `ICON_NAMES` order;
- `catalogueProblems({ entries, names, shapes })` — the ways the derivation can
  be wrong, each as a sentence naming the icon: a name with no shape, a shape
  with no name, a duplicate, a markup that is not exactly one `<svg>` element,
  or a paint other than the retintable `#000` the runtime replaces;
- `renderGeneratedModule(entries)` — the committed module's exact text, so the
  writer and the guard share one renderer.

Parsing rules, deliberately narrow (the source is ours and the package's own
`registry.test.ts` already enforces its shape):

- names: every `  "<name>",` line between `export const ICON_NAMES = [` and
  `] as const;`;
- attributes: every `'…'` literal between `const ATTRIBUTES = [` and
  `].join(" ");`;
- shapes: within the slice from `const shapes = {` to
  `} satisfies Record<IconName, string>;`, every
  `  key: '…'` / `  "key": '…'` pair (the value may sit on the next line).

If any of those three anchors disappears, `deriveIconCatalogue` returns **no
entries** and `catalogueProblems` reports it by name; it must never silently
produce a partial catalogue.

### 2.4 `src/components/icon-catalogue.tsx` (new)

- `browserMarkup(markup)` — replaces the retintable `#000` with
  `currentColor`. This is the same substitution GPUix's `<svg>` performs with
  `style.color`; without it the browser paints black-on-dark. Exported for the
  test.
- `filterIcons(query)` — case-insensitive substring match on the name; an empty
  query matches all. Exported for the test.
- `IconCatalogue()` — the rendered catalogue: a labelled filter input, an
  `aria-live` count (`N of 48 icons`), a grid of tiles, and an empty state with
  a **Clear filter** button. Each tile renders the icon inline with
  `dangerouslySetInnerHTML={ browserMarkup }` inside an `aria-hidden` wrapper
  (the name is the accessible content), at the `lg` step, in the current text
  colour, plus the name as inline code. Follow `component-index.tsx`'s markup
  and classes; no new styling vocabulary.

The markup is static, package-derived, and trusted: the `dangerouslySetInnerHTML`
is the only way to reuse the runtime's own SVG strings, and a comment says so.

### 2.7 `src/lib/icon-search.ts` (new)

A generated search document (the plan 504/505 shape):

| Field | Value |
| ----- | ----- |
| `index.title` | `Icon names` |
| `index.url` | `/docs/components/icon` |
| `index.content` | every icon name, one per line, plus `icon` and `glyph` |
| `index.keywords` | every icon name |
| `names` (promoted) | only the **hyphenated** names |

The promotion rule is the one plans 504/505 proved: an exact, distinctive name
(`chevrons-up-down`, `star-filled`) outranks prose, while a plain word that is
also an icon name (`search`, `copy`, `filter`, `list`, `star`, `user`, `x`) is
**not** promoted, so the component page that owns the word keeps the first
result. The content still lists every name, so a plain-word query can surface
the catalogue after the page it belongs to.

### 2.8 `src/lib/search.ts`

- add `iconSearchEntry` to `generatedEntries`;
- in `mergeResults`, a URL can now be **both** a component record and a
  generated document (the Icons page), so rank a candidate by the best of the
  two ranks instead of choosing one:

```ts
const ranks = [
  component === undefined ? undefined : componentRank(component, query),
  exactNameRank(generated, query),
].filter((value): value is number => value !== undefined);
const rank = ranks.length === 0 ? undefined : Math.min(...ranks);
```

Keep the page dedupe, the empty-query guard and the tie-breaks unchanged.

### 2.9 `src/lib/icon-catalogue.test.ts` (new)

listed none of the 48 names, so an icon name from the package was neither on the

## 5. STOP conditions

- **A promoted icon name displaces a component page for an ordinary word**
  (`search`, `copy`, `filter`, `input`, `label`): STOP — the hyphenated-name
  rule is the invariant, not a preference.
- **The derivation cannot reconstruct the runtime's exact markup** (the source
  no longer exposes `ATTRIBUTES`/`shapes` in a parseable shape): STOP and record
  the source change; do not hand-write markup in the docs.
- **The browser render disagrees with the runtime's tint** (a markup keeps a
  hard-coded paint other than `#000`): STOP — the transform is documented as
  the runtime's own rule, and an entry that breaks it needs a package change.
- **The gallery makes a page slower than the responsive/hydration smokes
  tolerate, or its grid clips at 390 px**: fix the grid inside `apps/docs`;
  `smoke:responsive` is the arbiter.
- **The search index grows the suite past the 120 s cold budget**: record the
  measurement; do not delete assertions.
- Any fix needs a path outside `apps/docs`, `TODO.md`, `PLAN.md` or
  `.agents/slop/plans/`: record a TODO row; do not edit it.

## 6. Acceptance criteria

- `/docs/components/icon` lists every icon the package ships, in the package's
  order, with its name and its real geometry, under a local filter.
- A new icon appears after `nub run --filter docs icons` and fails the suite
  while the generated file is stale — no docs edit beyond the command.
- `chevrons-up-down`, `star-filled` and `external-link` reach the Icons page
  first from ⌘K; `input`, `label` and `icon` keep their pages.
- The gallery is labelled as the package's markup drawn in the browser; no page

- `nub run check`, `nub run --filter docs test`, `smoke:build` and
  `smoke:browser` exit `0`.
- `TODO.md`, `PLAN.md` and the plan index are updated; the commits are pushed to
  `origin/agent/docs-site`.

### What changed beyond the plan

- **The freshness guard compares data, not bytes.** `oxfmt` rewrote a long
  `markup` string onto its own line and switched it to single quotes, so a byte
  comparison would have failed on formatting alone. The test now compares the
  imported catalogue with a fresh derivation (`toEqual`) and still pins the
  generated header's command; the writer emits the wrapped, single-quoted shape
  the formatter settles on, so regeneration leaves `nub run fmt` clean.
- **Two failures on the first run were real, and both were fixed in the code
  under test rather than the tests:**
  - `component-page-docs.test.tsx` enumerates every suite that reads
    `content/docs/components` and requires it on `/docs/component-pages`; the new
    catalogue suite is one, so the template's guard table gained a row.
  - Fumadocs' simple search tokenizes on hyphens, so a nonsense hyphenated query
    still matched ordinary prose. The "does not invent an icon name" check uses a
    single unknown token (`zzziconprobe`), and the plain-word regression check
    now names `search`, `copy`, `star` and `list` rather than relying on
    `input`/`label` alone — the measured `search("search")` first result is
    `/docs/components/search-input`.
- The generated catalogue is **48** entries, not the 47 the earlier README
  prose implied (the page never stated a count; no prose was changed).
