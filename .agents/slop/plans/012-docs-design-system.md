# 012 — Documentation: design system and token catalogue

**Workstream:** `tokens-theme`
**Phase:** B
**Depends on:** plan 011 (the implemented API).
**Files:** `docs/tokens.md`, `docs/design-system.md`.

These are the **repo documents** — maintainer-facing truth. They are not the
Fumadocs site (`apps/docs`), which the docs agent owns and which will consume
these documents. Every value and API in them must match the code; nothing is
aspirational.

---

## 1. Division of labour

| Document | Answers |
| -------- | ------- |
| `docs/design-system.md` | Why the system looks and behaves this way: identity, semantic-role model, light/dark decisions, type hierarchy, density, state model, accessibility policy, runtime constraints, extension philosophy. |
| `docs/tokens.md` | What exists: every public token group, every role, both theme values, helper APIs, the extension mechanism, migration/limitations. It is a reference, not an essay. |

They cross-link once at the top. Neither repeats the other's body at length.

## 2. `docs/design-system.md` — required structure

1. **Purpose** — what the design system is for; the library's render target
   (GPUix, native, inline style values) and the consequences.
2. **Identity** — "graphite and iris": cool neutral canvas, iris primary, calm
   desktop density. State that the identity is original and not copied from
   GPUI Kit, shadcn/ui or PanelUI; those are structural references only.
3. **Semantic roles, not shades** — components name intent (`background`,
   `mutedForeground`), never a ramp step. Explain the three-tier model:
   palette → semantic roles → component composition. Components do not add a
   fourth tier of component-specific tokens unless the value has no semantic
   home (and then it is a bug in the role set).
4. **Light and dark** — the canvas/surface/elevation strategy; dark is designed,
   not inverted; both themes expose the same roles; no pure black/white extremes
   for large surfaces.
5. **Typography** — the 10 roles and their jobs; why body is 14/20 and labels
   13/18; the mono roles; the missing-letter-spacing limitation.
6. **Spacing and density** — 2/4/6/8/12/16/24/32/48/64; the three density
   presets and what they change (control height, horizontal padding, row
   height); why density is a theme property, not a component prop.
7. **Radii, borders, elevation** — the radius scale; `border` vs `borderStrong`
   (decorative vs essential boundary); `sm/md/lg` shadows; overlays use the
   scrim colour, not a shadow.
8. **Interaction states** — hover, active, selected, disabled, focus. Map each
   to roles: `hover`, `active`, `selected`/`selectedForeground`,
   `disabled`/`disabledForeground`, `ring`. State that focus is an outline, not
   a border, so it never shifts layout.
9. **Accessibility** — the contrast policy and the test that enforces it. Table
   of thresholds (7:1 body, 4.5:1 secondary/on-colour, 3:1 focus and essential
   boundaries). State what is not covered: disabled text, placeholder as a
   label replacement, colour as the only signal.
10. **Runtime constraints** — no CSS variables, no CSS cascade, no inherited
    `color`, no letter spacing, no OS appearance query. Each with the honest
    consequence.
11. **Extension philosophy** — override semantics, scoped providers, what a
    brand theme may change, what it must not (do not remove roles; do not rely
    on mutation). Point to `docs/tokens.md` for the API.
12. **Non-goals** — no component-specific token catalogue, no theme editor, no
    high-contrast theme yet, no motion tokens yet.

## 3. `docs/tokens.md` — required structure

1. **Import** — core and `/react` entries; tree-shaking/no side effects.
2. **Colour roles** — one table with columns *Role · Light · Dark · Use*. Every
   role from `ThemeColors` appears exactly once, in the order of the interface.
   Values are the literal hex strings. A note says the table is generated by
   hand and checked by the contrast test; if a value changes, both change.
3. **Palette ramps** — the five ramps as compact tables or code blocks. Say
   plainly: components must use roles; ramps exist for docs and rare cases.
4. **Typography** — families, the weight set, the role table, `textStyle`.
5. **Spacing** — key/px table.
6. **Radius** — key/px table.
7. **Density** — preset table; `controlHeight`/`controlPaddingX`/`rowHeight`.
8. **Elevation** — shadow values for both themes and the structural type.
9. **Borders and icons** — widths and sizes.
10. **Theme API** — `Theme`, `ThemeConfig`, `ThemeOverrides`, `createTheme`,
    `extendTheme`, `getTheme`, `themes`, with a runnable example of a brand
    theme. State the merge rules (especially typography deep-merge, elevation
    replacement, mode immutability).
11. **React binding** — `ThemeProvider`, `useTheme`, scoped providers, mode
    switching example:

    ```tsx
    const [mode, setMode] = useState<ThemeMode>("dark");
    <ThemeProvider theme={getTheme(mode)}>
      <App onToggle={() => setMode(mode === "dark" ? "light" : "dark")} />
    </ThemeProvider>
    ```

    State that the app owns the switch because there is no OS appearance query.
12. **Using tokens in components** — the spread pattern with `textStyle`, the
    no-literals rule, and a short before/after example.
13. **Verification** — the contrast test file and command; how to run it.
14. **Limitations and future work** — link to `TODO.md` items: high-contrast
    theme, motion tokens, native gallery proof, Fumadocs page.

## 4. Accuracy rules

- Token values, role names and function signatures are copied from the package,
  not remembered. After writing, grep the source and compare the tables.
- Every code fence in `docs/tokens.md` must be valid TypeScript/TSX against the
  real API. If it cannot compile (e.g. it references an app component), keep it
  minimal and self-contained.
- Do not mention CSS variables, Tailwind or browser theming except in the
  "runtime constraints" limitation.
- Do not call the native gallery "done" before it exists.
- No screenshots or claims of native verification in these documents; the
  playground records that evidence.

## 5. Commands

There is no Markdown linter in the repo gate. Verification is:

```sh
nub run check          # code gates (docs must not break them)
nub run test
```

Plus a manual link check: every relative link resolves inside the repo, and
every symbol named in `docs/tokens.md` exists in `packages/tokens/src`.

Suggested mechanical check:

```sh
nub run --filter @gpuixui/tokens check-types
node -e "…"   # not required; prefer grep for exported names
```

## 6. STOP conditions

- If a documented token does not exist in code, stop and fix the code or the
  document — never ship documentation for an invented API.
- If the implemented API differs from plan 011, document the implementation and
  report the deviation in the commit; do not silently redefine the plan.
- If a docs claim needs native runtime evidence that does not exist, mark it as
  a limitation and add a TODO task.

## 7. Acceptance criteria
