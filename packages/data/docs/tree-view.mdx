---
title: Tree views
description: Expandable rows of a hierarchy, with one tab stop and arrow keys.
---

`TreeView` paints a tree of rows a reader opens, closes and walks; it composes
with `useExpandedRows`.

## Usage

```tsx
import { TreeView, useExpandedRows } from "@gpuixui/data";

const tree = useExpandedRows({
  roots: files,
  keyOf: (node) => node.name,
  childrenOf: (node) => node.children ?? [],
  labelOf: (node) => node.name,
  initialExpanded: ["src"],
});

<TreeView
  aria-label="Workspace files"
  height={260}
  rows={tree.rows}
  cursor={tree.cursor}
  onCursorChange={tree.setCursor}
  labelOf={(node) => node.name}
  onActivate={(row) => open(row.node)}
/>;
```

## API

| Prop | Type | Default | Consequence |
| ---- | ---- | ------- | ----------- |
| `rows` | `TreeRow<T>[]` | — | the visible rows, in paint order |
| `labelOf` | `(node: T) => string` | — | the row's accessible name and type-ahead match |
| `cursor` | `TreeCursor` | — | the caller's cursor; omit for an uncontrolled tree |
| `onCursorChange` | `(cursor: TreeCursor) => void` | — | reports every cursor |
| `defaultCursor` | `TreeCursor` | nothing open | the uncontrolled tree's start |
| `onActivate` | `(row: TreeRow<T>) => void` | — | a press or Enter on a row |
| `renderRow` | `(row: TreeRow<T>) => ReactNode` | `labelOf` as text | paints a row's content |
| `height` | `number` | — | a definite height; the rows scroll inside it |
| `testId` | `string` | — | the tree's locator |

## The controller

`useExpandedRows({ roots, keyOf, childrenOf, labelOf, initialExpanded, initialActive })`
returns the rows and the cursor, and the edits an application makes to them:
`rows`, `cursor`, `expanded`, `active`, `setCursor`, `setActive`, `toggle`,
`setExpanded(key, open)`, `expandAll`, `collapseAll`, `pressKey(key)`,
`typeAhead(prefix)` and `reveal(key)`. Every one is a write over the pure model
in `tree/logic`, so an Effect- or store-driven tree composes the same functions
without this hook.

`initialActive` moves the cursor without a press; the first paint is the
baseline, so mounting a tree never steals the window's focus.

## Keyboard

The tree is one Tab stop. Up/Down/Home/End move the cursor and the platform
focus together; Right opens a closed branch, steps into an open one, and leaves
a leaf where it is; Left closes an open branch and otherwise steps out to the
parent, while a **root stays put** — a root has no parent, and an empty cursor
falls back to the first painted row, which would move a reader standing on a
later root. Enter and Space toggle the branch under the cursor or activate a
leaf; a printable character jumps to the first row after the cursor whose label
starts with the typed prefix.

## A reveal lands the focus, not only the cursor

`reveal(key)` opens the path to a node and moves the cursor to it, which is the
shape a search hit or a "show this file" command needs. The cursor comes from
the caller, not from the tree's key handler, so the tree tells the two apart: a
row its own keys reached is focused in the same commit, while a caller-driven
row is re-taken on the **next tick**, after the runtime has handed the pressed
control the focus (`data-tree-lifecycle` measured the Reveal button keeping it).

A key that leaves the cursor where it was — Up on the first row, Down on the
last, Enter on a branch that opens under the active row — has no row to focus,
so it is not a move the tree made. It cannot leave a mark that makes the next
reveal look like the tree's own: `tree.test.tsx`'s `takes the focus on a reveal
after a key that moved nothing` presses Up on the first row, asks for a reveal
and requires the revealed row to hold native focus after the tick.

## Limitations

- One active row; a multi-select tree is not shipped.
- The tree does not virtualize itself; compose `VirtualList` in children mode.
- A row that changes height while painted re-measures on the next frame.
- The docs site cannot render this component live.
