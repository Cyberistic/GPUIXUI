title: NumberField
description: A number in a text field, with steps and optional bounds.
---

`NumberField` is a numeric text field. GPUix's `<input>` has **no numeric
mode** — no `type`, no `min`, no spinner — so parsing, clamping, stepping and
the draft text are this package's (`core/number.ts`). It is not a slider: the
user types an exact number, and the arrows are a convenience.

## Usage

```tsx
import { NumberField, Label, Stack } from "@gpuixui/primitives";
import { useState } from "react";

const [copies, setCopies] = useState(1);

<Stack direction="column" gap="xs">
  <Label description="1–99">Copies</Label>
  <NumberField label="Copies" value={copies} onValueChange={setCopies} min={1} max={99} />
</Stack>;
```

An untouched field with neither `value` nor `defaultValue` renders empty, the
way a native number field does — it does not start with a zero to delete. A
`value` supplied after mount shows immediately (plan `326`), so a form can load
its record without remounting the field.

## Bounds

`min` and `max` bound **the field, not the edit**: a supplied `value` goes
through the same clamp as typed text, so a record loaded with `150` under
`max={100}` paints `100`, announces `100`, and steps from `100`. The steppers and
the arrow keys agree with the paint — before plan `362` the field painted `150`
while `ArrowUp` reported a *smaller* `100`, and the first `ArrowDown` only
reached the bound. A step or a commit that lands on the value already painted
reports nothing, so a bound never looks like a change.

The bounds are **made total before they reach the paint** (plan `371`): a bound
that is not a finite number is treated as absent on that side, and an inverted
pair is swapped, the rule every slider and meter follows. Before that rule,
`min={NaN}` painted the string `"NaN"` and swallowed every step, `min={100}
max={0}` collapsed to `0` for a value of `150`, and `step={Infinity}` painted
`"Infinity"`. A `step` that is not a finite positive number is one.

The **value is made total the same way** (plan `392`): a non-finite `value` or
`defaultValue` reads as a number the field can paint, so it can never show
`"NaN"` or `"Infinity"`. `NaN` reads as the field's floor — its `min`, else `0`
— which is the rule `Slider` already follows. An infinity reads as a finite
neighbour inside the bounds: `+Infinity` is `max` when one exists, otherwise the
neutral `0` clamped up to a positive `min`; `-Infinity` is `min` when one exists,
otherwise `0` clamped down to a negative `max` (plan `753`). An absent bound
therefore never paints a value from the **opposite** side — `value={-Infinity}`
under `max={100}` shows `0`, not `100`. The keyboard uses the same value: a field
whose value was not a number steps from the painted neighbour instead of
swallowing every key. A `precision` that is not a finite number is `0` decimals.

The two spin buttons read that **same normalised range** (plan `378`), so with
`min={100} max={0}` the field is simply `0…100`: at `0` the up button is live and
the down button is blocked, and at `100` the reverse. Before that rule both
buttons compared the raw props, which every painted value satisfies, so an
inverted pair blocked the pointer while the arrow keys kept stepping.

## Draft and precision

While the user types, the **draft text** is kept verbatim (`1.` stays `1.`), so
the caret never jumps. Every edit that parses reports the clamped number
through `onValueChange`; on blur or `Enter` the draft is reformatted to `precision`.
A draft belongs to the value it started from and the value it reported, so a
**controlled field follows an external change**: when a reset or a reloaded
record sets `value` to something the draft did not ask for, the field paints
that value instead of the stale text (plan `325`).

A **decimal step is exact**: `stepNumber` trims its result to 12 decimal places,
so `0.2` stepped by `0.1` is `0.3` rather than `0.30000000000000004`. `precision`
remains a display rule — it never rounds the value a caller receives.

## API

| Prop | Type | Default | Consequence |
| ---- | ---- | ------- | ----------- |
| `value` | `number` | — | controlled value; a non-finite value reads as a finite neighbour (plan `392`) |
| `defaultValue` | `number` | none | start value; the field shows empty without one, and a non-finite default reads as the floor |
| `onValueChange` | `(value: number) => void` | — | the clamped number, after a valid edit or step |
| `onSubmit` | `(event) => void` | — | Enter: the draft is committed and reformatted first |
| `onClick` | `(event) => void` | — | the host click; a `Tooltip` trigger's dismissal writes here (the native input receives no mouse-down) |
| `min` / `max` | `number` | none | bound the value; absent or non-finite means unbounded, an inverted pair is swapped |
| `step` | `number` | `1` | arrow step; a non-finite or non-positive step is `1` |
| `precision` | `number` | `0` | decimals shown on commit; a non-finite precision is `0` |
| `size` | `"sm" \| "md" \| "lg"` | `"md"` | no effect since plan `372`: a field is one height (`h-9`, 36 px) |
| `disabled` | `boolean` | `false` | read-only, out of the tab order, inert; a pending draft is not committed on blur |
| `invalid` | `boolean` | `false` | destructive border |
| `label` | `string` | none | accessible name |
| `aria-description` | `string` | none | description announced after the name; trimmed, and a blank value is absent (a `Tooltip` writes its text here) |
| `placeholder` | `string` | none | empty-field hint |
| `autoFocus` | `boolean` | `false` | focus on every mount, including a field added after a loading state (plan `584`); the ring paints from mount |
| `formatValue` | `(value: number) => string` | fixed decimals | display text; a blank result falls back to the fixed-decimal text (plan `593`); parsing stays decimal |
| `style` | `StateStyle<FieldState>` | — | merged last; an object or a state callback |
| `testId` | `string` | — | stable locator on the field's chrome; the inner text host is `${testId}-input` |

## Keyboard

| Key | Effect |
| --- | ------ |
| `ArrowUp` | + one step |
| `ArrowDown` | − one step |
| `PageUp` / `PageDown` | ± ten steps |
| `Enter` | commit, reformat, then call `onSubmit` |

`Enter` reaches the field as the host's **`submit`**, not as a key event — the
editor consumes the key down (measured, plan `339`). The draft is committed and
reformatted before the caller's `onSubmit` runs, so `1.5` becomes `1.50` with
`precision={2}` and an app can save or advance on the same gesture.

`ArrowLeft`, `ArrowRight`, `Home` and `End` move the **native caret**. GPUix
0.10.0 consumes those key downs inside the editor before a component handler
sees them (measured: `12` + `Left` + `3` paints `132`, plan `338`), so they
cannot step and there is **no keyboard shortcut to a bound** — type the bound,
or hold `PageUp`/`PageDown`. That is the right split for a text field: the
caret keys are how a user edits the digits they already typed.

The spin buttons are pointer affordances, **not tab stops**: the field is one
tab stop and Up/Down are the keyboard path, as in a native spinner. A click on a
stepper returns focus to the input so the next arrow works.

A caller's `onKeyDown` **and** `onKeyUp` reach the input, like every other
control in the package; the field's own step rule runs first on key down, then
the caller's handler.

## Accessibility

- **Release-runtime focus:** the pinned 0.10.0 runtime moves native focus but
  delivers no `onFocus`/`onBlur` to a component
  ([measured](../../../docs/gpuix-capabilities.md#focus-events)). The ring still
  paints: `ThemeProvider`'s native-focus tracker samples
  `getFocusedElementId()` every 50 ms, so focus reaches the paint up to one tick
  late (plan `590`). The tracker also drives the **draft commit** when focus
  leaves, because the host never reports the blur; a runtime that does dispatch
  `onBlur` still commits from the event first, so the two paths cannot double
  report (plan `591`). Role, name, tab order, keyboard operation and activation
  are unaffected.
- The input is a `TextInput` with the name from `label`; the steppers are
  `presentation`, so a screen reader sees one named number field rather than
  three controls.
- The value is the native input's text, which the runtime exposes to AccessKit.
  There is no `aria-valuenow`/`min`/`max` in GPUix 0.10.0.
- A disabled field is `readOnly`, out of the tab order and paints the disabled
  chrome; it commits no pending draft on blur; assistive technology hears
  read-only, which is the honest state (the host has no `disabled` prop).
- **Slot trigger:** forwards a `Tooltip`'s handlers and `aria-description` to
  its inner input, so the tip opens on keyboard focus. A text host receives no
  `onMouseEnter`, so hover cannot open it (measured, plan `345`).

## Theming

The field uses the shared field recipe (`INPUT_BASE` from `@gpuixui/tw`, plan
`372`): **36 high, 12 horizontal padding, 6 radius, 14/20 type**, with the
recipe's focus ring on the **wrapper** and its invalid/disabled buckets. The
theme supplies the paint (`colors.input`, `colors.border`,
`colors.inputForeground`), the stepper column keeps `paddingRight: 0` so it owns
the right edge, and its icons are `colors.mutedForeground`. A field does not
follow `density` and `size` no longer moves it. The recipe's `shadow-xs` paints
the resting elevation, which the focus ring replaces (plan `585`).


## Style by state

The same `FieldState` as `Input` — `disabled`, `focused`, `invalid` — resolved
after the wrapper's chrome:

```tsx
<NumberField
  label="Copies"
  invalid={tooMany}
  style={(state) => ({ opacity: state.disabled ? 0.5 : 1 })}
/>
```

## Limitations

- **Decimal text only.** `1,5`, `0x10` and `Infinity` are rejected rather than
  guessed at; a locale decimal needs `formatValue` for display and parsing
  before the value reaches the field.
- **No `type="number"`, `inputMode` or `maxLength`.** The host input takes
  `value`, `placeholder`, `readOnly`, `theme` and its events — nothing else.
- **No drag-to-scrub.** A scrub could keep tracking outside the field — the
  runtime captures the pressed element (measured in plan 063) — but the gesture
  is not implemented; the steppers are the honest input for now.
- **No keyboard jump to `min`/`max`.** `Home`/`End` belong to the native caret
  (plan `338`); type the bound instead.

  out-of-range state, disabled/invalid.
- `runtime/number-field.runtime.test.tsx` — real typing through the native input
  reports `12`; `1.5` with `precision={2}`; `999` against `max=100` reports
  `100`; arrow/PageDown step; a decimal step reports `0.3` (not binary noise);
  `ArrowLeft`/`ArrowRight`/`Home`/`End` move the caret and report no value (plan
  `338`); `Enter` commits the draft to `1.50` and calls `onSubmit` once, and a
  disabled field does neither (plan `339`); a hit-tested stepper press steps and
  refocuses; the chrome ring paints from mount with `autoFocus`; a disabled field
  refuses text, keys and clicks. **Plan `362`:** a supplied `150` under `max=100`
  paints and announces `100`, `ArrowUp` reports nothing and `ArrowDown` reports
  `99`; an enabled field commits its draft on blur while a field disabled after
  the same edit reports nothing. Measured 2026-10-17 (plans 054 §9, 064 §6 and
  077 §7) and 2026-10-18 (plans `338`, `339`, `362`). **Plan `591`:** the blur
  commit runs from the native-focus tracker on a runtime that dispatches no
  `onBlur` — typing `1.5` with `precision={2}` and leaving the field paints
  `1.50`, and a deferring controlled parent receives the second value — while
  the event path still wins where the runtime sends one. The `autoFocus` ring
  also clears once the tracker sees another host, and the disabled case still
  reports nothing. **Plan `642`:** a draft typed after an earlier `Enter` still
  commits when focus leaves — the host-blur de-duplication flag is owned only
  by the host-blur path, so `1.50x` does not stay painted on an unfocused
  field. **Plan `593`:** a `formatValue` returning only whitespace (a
  missing computed unit) no longer blanks the field — `numberDisplay` falls back
  to the fixed-decimal text, and the runtime reads `12.00`. **Plan `371`:** a
  non-finite bound is ignored and an inverted pair is swapped — four fields
  (`min={NaN}`, `max={NaN}`, `min=100 max=0`, `step={Infinity}`) paint only
  finite values, the swapped range steps `100 → 99 → 100`, and an infinite step
  reports `6`; proven in `runtime/nonsense-numbers.runtime.test.tsx` and the
  core range cases. **Plan `378`:** the spin buttons resolve their blocked state
  from that same range, so the swapped pair leaves the up button live at `0` and
  blocks the down one (the reverse at `100`); the element tree and a hit-tested
  runtime click prove both ends. **Plan `392`:** a non-finite value is a finite
  one before it paints — `value={NaN}`/`defaultValue={NaN}` paint `"0"` (or
  `"10"` under `min={10}`), unbounded `value={±Infinity}` paint `"0"`, and
  `precision={Infinity}` paints `0` decimals; a `NaN` field steps to `-1`
  instead of reporting nothing. **Plan `753`:** with no bound on an infinity's
  own side it took the *other* bound — `value={-Infinity} max={100}` painted
  `"100"` and `value={Infinity} min={-100}` painted `"-100"`; both now paint the
  neutral `"0"` clamped into the bound that exists, and the single-bound cases
  (`max={-10}`, `min={10}`) are unchanged. Proven in
  `runtime/nonsense-numbers.runtime.test.tsx` (5 cases, two new fields) and the
  core range cases.
