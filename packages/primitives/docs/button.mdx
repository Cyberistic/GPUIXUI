---
title: Button
description: The primary action — clickable and keyboard-activatable, with busy and disabled states.
---

`Button` is the action primitive. `@gpuix/react` 0.11.0 publishes a headless
`Button`/`buttonProps`; this component keeps its own activation contract
(`core/keyboard.ts`: Enter on key down, Space on key up, a held key ignored) and
adds the recipe, `loading`, and the parts contract on top, so the keyboard rules
it ships are the ones its tests and runtime probes measure. **The headless
primitive is not adopted, and that is a decision with a reason**: `buttonProps`
keeps a disabled button in the tab order (`tabIndex: -1`) where this component
removes the stop, exposes only `{ disabled }` to its `style` callback where this
one reports focus too, and has no `loading`/`Spinner` state or
`aria-description="Loading"`. Its Space release also fires without the held-key
guard this component applies. The measured comparison is in `TODO.md` §Salvage.

## Usage

```tsx
import { Button, Stack } from "@gpuixui/primitives";

<Stack direction="row" gap="sm">
  <Button variant="outline">Cancel</Button>
  <Button variant="primary" onActivate={save} loading={saving}>
    Save changes
  </Button>
</Stack>;
```

## Variants

| `variant` | Rest | Hover / press |
| --------- | ---- | ------------- |
| `primary` (default) | `primary` fill, `primaryForeground` text | derived fill — `filledHover` / `filledPressed` |
| `secondary` | `secondary` fill | derived fill — `filledHover` / `filledPressed` |
| `outline` | border only — `borderStrong`, the measured control boundary | hover wash |
| `ghost` | no chrome | hover wash |
| `destructive` | `destructive` fill | derived fill — `filledHover` / `filledPressed` |
| `link` | text in `brandText` — the brand derived until it reads as text | underline + hover wash |

A filled action's hover and press are **opaque** fills the theme owns: they move
toward the theme's foreground (`filledHover` / `filledPressed` in
`@gpuixui/tokens`), so the same action reads as one colour on a card and on a
dialog. The old half-alpha lift let the surface behind the control show through,
and a translucent fill cannot be measured for label contrast at all. The label
keeps the text floor on both fills.

## Sizes and states

| `size` | Height | Horizontal padding |
| ------ | ------ | ------------------ |
| `sm` | `density.controlHeight.sm` | `density.controlPaddingX.sm` |
| `md` (default) | `density.controlHeight.md` | `density.controlPaddingX.md` |
| `lg` | `density.controlHeight.lg` | `density.controlPaddingX.lg` |

- `square` — equal width and height, no horizontal padding: an icon-only button.
- `fullWidth` — stretches to its parent.
- `disabled` — refuses click and keys, and leaves the tab order, even while it
  is also `loading`. A filled
  action (`primary`, `secondary`, `destructive`) paints the neutral pair —
  `disabled` behind `disabledForeground`, the roles `contrastPairs` measures on
  every surface a control sits on — rather than fading itself; an `outline`,
  `ghost` or `link` action has no fill to collapse into and keeps the fade.
- `loading` — shows a spinner in the variant's own on-colour (a busy primary
  button paints `primaryForeground`, not a brand dot on a brand fill), announces
  `Loading`, refuses activation, and **stays focusable** — unless it is also
  `disabled`, which wins the tab stop because a disabled control declares no
  ring. A disabled busy button
  paints the neutral pair, so its spinner moves to `on-disabled`
  (`disabledForeground`). `reducedMotion` reaches that spinner, because the busy
  state is the only part of a button that moves; the runtime exposes no
  reduced-motion preference, so the caller passes its own.

## API

| Prop | Type | Default | Consequence |
| ---- | ---- | ------- | ----------- |
| `variant` | `ButtonVariant` | `"primary"` | the paint from `core/variants.ts` |
| `size` | `"sm" \| "md" \| "lg"` | `"md"` | height and padding from density |
| `square` | `boolean` | `false` | icon-only geometry |
| `fullWidth` | `boolean` | `false` | `width: 100%` |
| `disabled` | `boolean` | `false` | blocks activation, leaves the tab order |
| `loading` | `boolean` | `false` | spinner, `Loading` description, blocks activation |
| `reducedMotion` | `boolean` | `false` | holds the busy spinner's lit dot; forwarded to `Spinner` |
| `leading` / `trailing` | `ReactNode` | none | an icon or element on either side |
| `label` | `string` | none | accessible name; required for an icon-only button |
| `onActivate` | `(event: EventPayload) => void` | none | click or activating key, with the event that caused it; not called while busy |
| `onClick` / `onKeyDown` / `onKeyUp` / `onFocus` / `onBlur` | host handlers | none | composed with the button's own; yours runs first |
| `onMouseEnter` / `onMouseLeave` | host handlers | none | forwarded to the host; the pair a `Tooltip` trigger needs |
| `aria-description` | `string` | none | supplementary description; `Tooltip` passes the tip here, and a busy button announces `Loading` instead |
| `ref` | `Ref<PublicInstance>` | — | the element itself: a trigger anchors the surface it opens to it |
| `aria-expanded` / `aria-selected` | `boolean` | — | announced state — an open menu or popover, and the current page |
| other host props | `ActionHostProps` | — | forwarded unchanged (`onMouseDown`/`onMouseMove`/`onMouseUp`, `onLayout`, `autoFocus`, …) |
| `style` | `StateStyle<ButtonState>` | — | resolved against the live state and merged last |
| `testId` | `string` | — | stable locator |
| `children` | `ReactNode` | — | the visible label |

The five host handlers are `InteractionProps`. They are **composed**, never
substituted: your handler runs first with the runtime's own event and the button
still activates. A busy or disabled button installs no `onClick` at all, so
neither your handler nor `onActivate` runs; keys and focus stay observable.

`onActivate` carries the event that activated the button rather than nothing: a
pointer activation hands over the runtime's `click` payload, whose `x`/`y` is the
point that was pressed, and a keyboard activation hands over the
`keyDown`/`keyUp` payload the button decided on. `KeyEvent` extends
`EventPayload`, so one handler serves both and `eventType` says which happened —
a ripple can be born at the press point and a trigger can forward the caller's
own `onClick` without losing it:

```tsx
<Button
  onActivate={(event) => {
    // A pointer press carries x/y; a key carries `key`.
    recordActivation(event);
  }}
>
  Save
</Button>;
```

The pointer pair and `aria-description` are `TooltipTriggerProps`: GPUix's
`TooltipTrigger asChild` merges its handlers into the element it wraps, and the
runtime delivers a hover only to the element that registered the listener, so
the button forwards them to its own host. That is what makes `<Tooltip><Button
… /></Tooltip>` open on hover and announce the tip.

The rest of the runtime's host props are `ActionHostProps`, forwarded unchanged
because a button is also the trigger a surface opens from: the `ref` is the
element the popover or menu anchors to, `aria-expanded`/`aria-selected` are the
state assistive technology reads off that same element, and the pointer moves
are what a hover-opened surface listens to.

```tsx
<Button ref={setTrigger} aria-expanded={open} variant="ghost">
  Filters
</Button>;
```

`setTrigger` is the surface's own anchor and `open` its state. The props this
component **owns** — role, tab stop, accessible name, `style`, `testId` and
every handler the activation contract composes — are written after the spread,
so no host prop can replace the behaviour.

## Keyboard

| Key | Contract |
| --- | -------- |
| Enter | activates on key **down** |
| Space | activates on key **up** |
| held key | repeat events never activate |

`disabled` and `loading` refuse both. A `disabled` button is not tabbable; a
`loading` one is, so a keyboard user is not dropped from the page mid-action.
The two together follow `disabled`: a button that is disabled *and* busy leaves
the tab order, because the disabled rule paints no ring and the stop would be a
cue-less control.
A Space **press** calls `preventDefault()`, so the platform default (scrolling a
container) does not run while activation waits for the release.

## Accessibility

- Role: `button`; the name comes from `label`, or from a plain text child when
  `label` is absent or blank — a blank label is omitted rather than published as
  an empty name.
- `loading` sets `aria-description="Loading"` — this runtime has no `aria-busy`.
- There is no `aria-disabled`: a disabled button is removed from the tab order
  instead, which is the strongest truthful alternative.
- Focus is a **keyboard-only outline**: the button declares `focusVisible`
  (`controlRing` from `core/focus.ts`, `colors.ring` at `borderWidth.strong`)
  at rest, and the runtime paints it after keyboard input only. A mouse click
  shows no ring, which is the native contract (measured in plan 053). A disabled
  button declares no ring: disabling the focused button does not move the
  runtime's focus, so a declared ring would stay painted on a control that
  refuses every key.

## Theming

The recipe (`buttonClass`, compiled through the primitives' registry) resolves
fill, text, border, hover and active from the theme, and `controlRing`
(`core/focus.ts`) declares the keyboard ring (`keyboardRing`); `buttonVariants`
maps each variant to theme **roles** — one variant, `link`, paints a colour
derived from a role rather than the role itself. Size and padding come from
`density`.

`link` is the one derivation: `primary` is a **fill** — it carries
`primaryForeground` and is measured as a surface — so written as text it lands
under the 4.5:1 reader floor on the washes a link tints (4.30:1 on the base
light theme's `active`, 3.10:1 in macOS dark). The recipe's `text-brand` utility
resolves `brandText(theme)` instead: the brand moved toward `foreground` in 2%
steps until the least readable of `brandTextSurfaces` clears the theme's own
floor, and returned unchanged for a brand that already reads.

`style` takes a `StateStyle<ButtonState>` — a `StyleDesc`, or a callback that
receives `{ disabled, focused }` and returns one. The result merges after every
role decision, so a callback is the last word on a property the recipe also sets:

```tsx
<Button style={(state) => ({ opacity: state.focused ? 1 : 0.9 })}>Save</Button>
```

`loading` is not in the state: a busy button reports `disabled`, because it
refuses activation.

### The disabled paint

A disabled filled action wears the **neutral pair**, not a fade:
`disabled` behind `disabledForeground` — `disabledAction` in `@gpuixui/tokens`,
the roles `contrastPairs` measures on every surface a control sits on. A 50%
fade composites the label into whatever is behind the control: on the card of
macOS, Linux, Windows 7 (Aero) and Windows XP (Luna) light it lands at
1.47:1–1.49:1, so the state is invisible exactly where a dialog's action lives.
`paintsFilledSurface` reads the variant table, so a new filled variant inherits
the paint; `outline`, `ghost` and `link` have no fill of their own — the pair
would turn each into a grey box — and keep the fade on the page, where the
tokens package measures it.

```tsx
<Button disabled>Save</Button> {/* disabled + disabledForeground */}
<Button variant="ghost" disabled>
  Cancel
</Button> {/* the fade: no fill to collapse into */}
```

### The keyboard dim

While one control has keyboard focus, the runtime dims every other focusable
element to `keyboardFocusDimOpacity` (40%) as a "where can Tab go" cue. On a
filled action that composites the label into its own fill — the pair is held to
4.5:1 at rest and lands at 1.3–3.2:1 dimmed (`keyboardDimFailures`) — so
`primary`, `secondary` and `destructive` declare `keyboardFocusDim: false` and
keep their label at full opacity. `outline`, `ghost` and `link` have no fill to
collapse into and keep the cue. `paintsFilledSurface` derives the split from the
variant table, so a variant that gains a fill inherits the rule. A caller can put
the dim back with `style`, which merges last.

## Limitations

- The ring's paint is the runtime's: the unit and runtime suites assert the
  declaration, and the playground's `focus-visible` probe holds the paint
  (plan 053).
- No `aria-disabled` and no `aria-pressed`/toggle-button state.
- An icon-only button must pass `label`; use `IconButton`, whose required prop is
  the name.
- No native button element: the runtime exposes a `div` with role and handlers.
- Overlaps the runtime's headless `Button`: `@gpuix/react` 0.11.0 ships
  `Button`/`buttonProps`, and this component predates it. Adoption was evaluated
  and declined — `buttonProps` lacks `loading`, the focused `style` state and the
  held-key guard, and keeps a disabled button in the tab order; the comparison is
  in `TODO.md` §Salvage, so nobody re-litigates it from memory.
