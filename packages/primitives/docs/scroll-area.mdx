---
title: ScrollArea
description: A bounded container that scrolls on the chosen axes.
---

`ScrollArea` owns the overflow axes, the keyboard contract and the position
report; it paints no chrome of its own. GPUix paints the
scrollbar with the platform theme, so the thumb cannot be tinted and there is no
fade mask. It is a `<div>`: the runtime has no separate scroller element.

## Usage

```tsx
import { ScrollArea, Stack, Text } from "@gpuixui/primitives";

<ScrollArea axis="vertical" label="Activity" style={{ height: 240 }}>
  <Stack direction="column" gap="sm">
    {rows.map((row) => (
      <Text role="body" key={row}>{row}</Text>
    ))}
  </Stack>
</ScrollArea>;
```

**Give it a bounded size.** A scroll container with no height constraint grows
with its content and never scrolls.

**A non-blank label makes it a keyboard scroll stop.** The runtime does not move
a container from the keyboard on its own, so a labelled area becomes a named
`region` with `tabIndex={0}` and its own keys. Without a label — or with one
that is only whitespace after trimming — it is a plain container and stays out
of the tab order: a focus stop nothing can announce is worse than no stop, and
adding one to every existing layout silently would be the worse default
(plan `396`).

## API

| Prop | Type | Default | Consequence |
| ---- | ---- | ------- | ----------- |
| `axis` | `"vertical" \| "horizontal" \| "both"` | `"vertical"` | which overflow axes are `scroll` (the others are `hidden`) |
| `label` | `string` | none | a non-blank value names the region (trimmed) **and** makes it a focusable keyboard scroll stop; a blank one is ignored |
| `onScroll` | `(event: EventPayload) => void` | none | wheel/trackpad **deltas** (`deltaX`, `deltaY`, `precise`, `touchPhase`) |
| `onScrollPositionChange` | `(position: ScrollPosition) => void` | none | the absolute offset, after a wheel, keyboard or focus-reveal scroll, only when it changed |
| `style` | `StateStyle<ScrollAreaState>` | — | merged last; put the bounded size here; an object or a state callback |
| `aria-description` | `string` | none | an extra description announced after the name; trimmed, and a blank value is absent (a `Tooltip` writes its tip here) |
| `children` | `ReactNode` | — | content |
| `testId` | `string` | — | stable locator |
| `ref` | `Ref<ScrollAreaHandle>` | none | `element` for measuring and `scrollTo`, which reports the position it lands on |

## Scroll position

`onScroll` reports a delta, not a position: the `EventPayload` has no offset, and
a scroll this component performs itself (the keyboard contract below) dispatches
**no** `onScroll` at all. `onScrollPositionChange` is the complete signal: it
reads the runtime's own `getScrollOffset` after every wheel and keyboard move, so
it reports where the region actually is — including a clamped `End` — and stays
silent when the position did not change.

```tsx
import { useState } from "react";
import { ScrollArea } from "@gpuixui/primitives";

const [atTop, setAtTop] = useState(true);

<ScrollArea
  label="Activity"
  onScrollPositionChange={(position) => setAtTop(position.y === 0)}
  style={{ height: 240 }}
>
  {rows}
</ScrollArea>;
```

`ScrollPosition` is `{ x, y }`: `y` is `0` at the top and negative below it, `x`
is `0` at the left and negative to the right. The initial position is `{0, 0}`
and is not reported — the callback is a change signal, like `onValueChange`.

**To move the region** use its handle — `scrollTo` reports the position it lands
on, which a raw `renderer.scrollTo` cannot:

```tsx
import { useRef } from "react";
import { ScrollArea, type ScrollAreaHandle } from "@gpuixui/primitives";

const area = useRef<ScrollAreaHandle | null>(null);

<ScrollArea ref={area} label="Activity" style={{ height: 240 }}>
  {rows}
</ScrollArea>;

// Inside a handler: back to the top. The runtime clamps either axis.
area.current?.scrollTo({ y: 0 });
```

The handle is `{ element, scrollTo }`: `element` is the viewport host for
`renderer.getElementBounds`, and an omitted axis in `scrollTo` keeps its current
offset. There is no controlled position prop on purpose: "the caller set it
again" and "the user moved it" would need a state machine the primitive does not
own.

## Keyboard

A **labelled** area is one tab stop. While it holds focus:

| Key | Movement |
| --- | -------- |
| `ArrowDown` / `ArrowUp` | one line (three body lines) down / up |
| `PageDown` / `PageUp` | one page (the viewport less one line) |
| `Home` / `End` | the start / end of the scrolled content |
| `ArrowRight` / `ArrowLeft` | one line right / left, on a horizontal or `both` area |

Keys for an axis the area does not scroll are ignored. The handler checks the
runtime's focused element id against the container's own, so a field inside the
area keeps its arrow keys instead of scrolling the region.

## Focus reveal

A focusable descendant that takes native focus — by `Tab`, a click, or a
programmatic `focusElement` — is scrolled inside the region. `Tab` therefore
cannot leave the keyboard on a control painted below the fold.

The area measures the focused host and its own painted viewport, then moves by
the overflow on the axes it scrolls: a `vertical` area never moves `x`. The
move goes through `scrollTo`, not the runtime's `scrollIntoView` — measured,
that verb does not move a plain scroller at all (plan `606`). A scroll the area
performs this way reports through `onScrollPositionChange`, so a caller sees it.

Every control that owns its focus state participates: the shared `useFocus` and
`useRovingFocus` hooks (buttons, fields, the roving groups, sliders) and the two
hand-rolled groups (`CheckboxGroup`, `OTPField`). A control outside the area has
no reveal; with nested areas the nearest one moves.

**One limit.** A focused host that reports no bounds — an element that paints no
surface of its own — cannot be measured, so the region does not move.

## Tooltip trigger

A **labelled** area accepts the `Tooltip` slot contract: the wrapper forwards the
slot's handlers and composes its focus/blur/key handlers with the region's own
scroll rule, so wrapping a region does not cost its keyboard scroll. The tip's
string also becomes the `Region`'s `aria-description`, which is announced on
focus and carries the hint while the tip is shut.

```tsx
import { ScrollArea, Tooltip } from "@gpuixui/primitives";

<Tooltip content="Scroll for newer entries">
  <ScrollArea label="Activity" style={{ height: 240 }}>
    {rows}
  </ScrollArea>
</Tooltip>;
```

**Hover has one runtime limit.** GPUix delivers a mouse event to the element the
pointer hit-tests and does not bubble it to an ancestor — the rule that also
makes a text-host tooltip keyboard-only. The tip opens on hover only while the
pointer is over the region itself: an area the content does not cover, a
scrollbar gutter, or content that opts out with `pointerEvents: "none"`.

**Keyboard open has one limit too.** The area's public `ref` is the imperative
scroll handle, so the only ref a tooltip could use is already taken; on a runtime
that dispatches no focus events (the pinned 0.10.0 build, plan `583`) a wrapped
area's tip stays hover-only. Its `aria-description` still reaches assistive
technology, and the region itself scrolls by keyboard. Use `InfoTip` or a
`Button` trigger when the tip must open on `Tab`.

An **unlabelled** area has no role and no tab stop, so it is not a trigger
either — label it first.

## Accessibility

- **Release-runtime focus:** the pinned 0.10.0 runtime moves native focus but
  delivers no `onFocus`/`onBlur` to a component
  ([measured](../../../docs/gpuix-capabilities.md#focus-events)). The ring still
  paints: `ThemeProvider`'s native-focus tracker samples
  `getFocusedElementId()` every 50 ms, so focus reaches the paint up to one tick
  late (plan `590`). Role, name, tab order, keyboard operation and activation
  are unaffected.
A labelled area is a named `region` and a focus stop, and paints the focus ring.
That is the keyboard path for a region whose content is not itself focusable.
An unlabelled area — including one whose label is blank — has no role and is not
announced as a region: pair it with a heading, or label it.

## Theming

The axes and the focus ring are resolved (`scrollStyle`, `focusRing`); the
scrollbar's colour and width belong to the platform theme. `theme.colors.scrollbar`
exists but cannot reach the 0.10.0 scrollbar.

## Style by state

`style` takes an object or a callback over `ScrollAreaState` — the runtime's own
`StateStyle` type — merged last on the viewport:

```tsx
<ScrollArea style={(state) => ({ opacity: state.focused ? 0.9 : 1 })} />
```

| Field | Type | Meaning |
| ----- | ---- | ------- |
| `focused` | `boolean` | the labelled region holds native focus; always false for an unlabelled area |

The callback's result merges after the component's own rules, so it wins per
property; returning `{}` keeps the default look. The state type is exported.

## Limitations


- **No scrollbar tint and no scrollbar width control** in GPUix 0.10.0
  (`scrollbarColor`/`scrollbarWidth` exist only on the unreleased `main`).
- **No fade mask** at the edges.
- **No controlled scroll position.** `onScrollPositionChange` reports where the
  region is, and the `ref` handle's `scrollTo` moves it; a controlled
  `scrollPosition` prop would have to tell "set again" from "user moved", so it
  is not offered.
- **A component-performed scroll emits no `onScroll`.** The arrow/page/Home/End
  moves go through the renderer, which dispatches no scroll event; use
  `onScrollPositionChange` for the position and `onScroll` only for pointer
  deltas.
- **A focused host with no reported bounds cannot be revealed.** The area
  measures the host through `getElementBounds`, so an element that paints no
  surface of its own is not moved into view.
- No virtualisation: a long list mounts every row. `packages/data-grid` owns the
  virtual-list work when it lands.
