---
title: Tooltip
description: A short label on hover or keyboard focus — a themed wrapper over GPUix's Tooltip.
---

`Tooltip` reuses `@gpuix/react/tooltip` for the anchored layer, the open delay
and dismissal, and themes the tip to the popover surface and caption type. It is
a wrapper, not a reimplementation. It also makes the tip anchor to **its
trigger**: GPUix's tooltip root otherwise stretches to its parent, which put the
tip at the edge or centre of the surrounding layout (plan 060).

## Usage

```tsx
import { Button, Tooltip } from "@gpuixui/primitives";

<Tooltip content="Delete this file" side="bottom">
  <Button label="Delete">Delete</Button>
</Tooltip>;
```

The child must be a single **focusable element with a role and a name**.
`Tooltip`'s trigger clones its child with the hover, focus, key and description
props the runtime's slot injects. Every single-root focusable Tier 1 control
accepts that contract:

| Trigger | Hover | Keyboard focus |
| ------- | ----- | -------------- |
| `Button`, `IconButton`, `Toggle` | yes | yes |
| `Checkbox`, `Switch`, `Slider`, `Select` | yes | yes |
| `Surface` (focusable + labelled) | yes | yes |
| `ScrollArea` (labelled) | the region itself only | yes |
| `Input`, `TextArea`, `NumberField` | **no** (text host) | yes |
| `InfoTip` | yes | yes |
| `RangeSlider`, `OTPField`, `Rating`, `CheckboxGroup`, `ToggleGroup` | no | no |

A native `<input>`/`<textarea>` host receives no `onMouseEnter` in GPUix 0.10.0
(measured, plan `345` §0), so a field's tip opens on keyboard focus only — never
on hover. The roving composites (`RangeSlider`, `OTPField`, `Rating`,
`CheckboxGroup`, `ToggleGroup`) have no single focusable root, so they are not
triggers; put the tip on a label, an `InfoTip`, or a wrapper `div` with a role
and a name.

A labelled `ScrollArea` is a single focusable root, so it accepts the contract
and its tip becomes the `Region`'s description (plan `399b`). The slot's `ref`
receives the area's imperative handle, so the handle carries the viewport's `id`
and the wrapper can recognise the focus the tracker reports: `Tab` opens the tip
(plan `610`). Its hover path has the runtime's hit-testing limit: GPUix does not
bubble a mouse event to an ancestor, so the tip opens only when the pointer is
over the region itself (an uncovered area, the scrollbar gutter, or content with
`pointerEvents: "none"`). A content-filled region is a keyboard trigger.

A focusable, labelled `Surface` is the same shape: one host div with
`role="group"`, a name and a tab stop, whose raster image is decorative. It
forwards the contract, and measured, **both** paths work — the full-size image
does not swallow the pointer (plan `733`). A static surface has no focus path,
so it is not a trigger.

### Full-width triggers

The root hugs its trigger so the tip anchors to it (plan `060`), which means a
child asking for `width: "100%"` has nothing definite to resolve against.
`Slider`'s track is always 100 % wide, so it needs an explicit root width;
measured, a Slider inside a `Tooltip` without one paints a 16 × 32 px track. The
same applies to `fullWidth` `Input`/`Select`/`Button`:

```tsx
<Tooltip content="Alert volume" style={{ width: 320 }}>
  <Slider label="Volume" defaultValue={40} />
</Tooltip>;
```

`style` is merged over the root's hugging style. It sizes the **anchor**, so the
child and the tip stay aligned.

A component that drops those props will not open the tip — this package's `Box`
is a container with no event props, and the data-driven groups do not implement
the contract, so use a raw styled `div` or `InfoTip` for a non-button trigger.
A bare focus stop with no role produces no accessibility node at all.

For the common "info icon that explains a term" case, use **InfoTip** instead of
writing that trigger by hand: it owns the role, the name, the tab stop and the
focus ring.

## Open state

Hover, focus, click and Escape drive the tip by default. Supplying `open` makes
it **controlled**: the wrapper reports every request through `onOpenChange` and
the tip changes only when the parent passes a new value. That is what a one-time
hint, a product tour, or a "the shortcut moved here" callout needs.

```tsx
const [hintOpen, setHintOpen] = useState(false);

<>
  <Button label="Show hint" onClick={() => setHintOpen(true)}>
    Show hint
  </Button>
  <Tooltip
    content="Press Cmd-K to search"
    open={hintOpen}
    onOpenChange={setHintOpen}
    side="bottom"
  >
    <Button label="Search">Search</Button>
  </Tooltip>
</>;
```

`defaultOpen` starts an uncontrolled tip open (a tour whose first step is
already visible). The tip is still dismissable by the runtime's own paths —
Escape on the trigger, a click, or the pointer leaving — and each one reports
`false` to `onOpenChange`.

The same value drives the wrapper's measurements, so a tip opened from code is
placed from its trigger's real box: it flips below at the window's top edge just
like a hovered tip. `disableHoverableContent` closes the tip as soon as the
pointer leaves the trigger, so its own surface cannot be hovered; the default
(`false`) keeps it open while the pointer travels onto the tip.

## Placement

The root sets `alignSelf: "flex-start"` (`tooltipRootStyle`), so it hugs the
trigger instead of filling the parent. The anchored layer then measures the
trigger, in a column **and** a row parent.

`align` decides which edge of the trigger the tip lines up with:

| `align` | Result |
| ------- | ------ |
| `start` (default) | the panel's start edge meets the trigger's start edge — exact |
| `end` | the panel's end edge meets the trigger's end edge — exact |
| `center` | the panel's centre meets the trigger's centre within 1 px |

The runtime's own `center` is not usable: it puts the panel's **end** on the
trigger's centre line, half a panel off (plans `060` §0, `156` §8). The wrapper
never passes it through — it maps `center` to `start` plus half the difference
between the trigger and the open tip. The difference is taken on the **layer's
own axis**: above/below aligns horizontally, so widths; `side="left"`/`"right"`
aligns vertically, so heights (measured, plan `098`: a width difference handed to
the vertical axis painted the tip 90 px below its trigger). The correction is
applied in a layout effect, before the frame is painted, so a centre tip does not
visibly jump (plans `095`, `098`).

`side` decides which side of the trigger the tip opens on. It prefers **above**,
and flips **below** when the tip does not fit above — the runtime's layer is
`fit="snap"`, which clamps a layer inside the window **without flipping it**
(plan `156` §8), so at the top edge the tip used to open at `y 8..34` over a
trigger at `y 12..30` (plan `067` §1). The wrapper measures its root and
estimates the tip's height from `tooltipStyle` (padding, one caption line,
border) for the first frame, then uses the painted tip's measured height, so a
wrapped tip flips too (plan `391`). With no `side` it only decides the vertical
axis; `left`/`right` is used when asked for.

A **requested side is a preference on both axes.** The wrapper measures the
trigger's box: when the tip cannot fit on the requested side it opens on the
other one, or on the roomier side when it fits on neither. The runtime alone
would clamp it — measured on a trigger at `x 12..72`, a `side="left"` tip painted
`x 8..55`, over the trigger (plan `335`), and a `side="top"` tip painted
`y 8..34` over a trigger at `y 12..36` (plan `336`).

**A window resize re-places the tip.** The wrapper observes the size the host
reports (`useWindowSize`, sampled every 100 ms only while a tip is open) and
re-measures the painted tip when it changes, so the side, the wrapped height and
the width cap all follow. Measured (plan `604`): before the subscription, a
`side="bottom"` tip stayed at `y 241` over a trigger at `y 212..236` after the
host reported a 250-high window, and a 1 258 px 60-word tip ignored a 300 px
report. A long tip whose re-wrapped height no longer fits above now flips below.

**The trigger's own box is followed too.** GPUix has no `onLayout`, and the
runtime re-anchors an open layer without re-deciding the side the wrapper chose.
The wrapper therefore samples the trigger on the same 100 ms cadence while the
tip is open, so a layout change (a sidebar collapsing, a sibling reflowing) is
a placement input like a window resize. Measured (plan `645`): a trigger moved
from `y 712` to `y 12` while a top-side tip was open left the tip at `y 13..37`
over a trigger at `y 12..36`; it now flips below. The sampler sleeps while the
tip is closed.

## API

| Prop | Type | Default | Consequence |
| ---- | ---- | ------- | ----------- |
| `content` | `ReactNode` | — (required) | the tip; long text wraps inside a cap set by the resolved side's room. Content that paints nothing — a string that trims to nothing, a computed `null` or an empty list — is **no tip**: the trigger renders unchanged (plans `573`, `744`) |
| `label` | `string` | a string content's text | the tip's accessible summary — the trigger's description and the tip's name. A **node** tip needs one, because the runtime cannot read text out of a node (plan 742) |
| `children` | `ReactNode` | — (required) | the trigger, a focusable host element |
| `open` | `boolean` | uncontrolled | controls the tip; requests arrive through `onOpenChange` |
| `defaultOpen` | `boolean` | `false` | initial open state when uncontrolled |
| `onOpenChange` | `(open: boolean) => void` | — | called when the tooltip asks to open or close |
| `disableHoverableContent` | `boolean` | provider (`false`) | closes as soon as the pointer leaves the trigger |
| `side` | `FloatingSide` | auto — above, flipped below when it does not fit; a `left`/`right` side flips when it cannot fit | preferred placement on both axes |
| `align` | `FloatingAlign` | `"start"` | alignment against the trigger; `center` is measured exact — see Placement |
| `delay` | `number` | provider default | hover delay in milliseconds |
| `style` | `StyleDesc` | — | merged over the hugging root; a full-width trigger needs a width here |
| `testId` | `string` | — | locator on the **tip** |

## Keyboard

Owned by GPUix: the tip opens when its trigger takes keyboard focus, and Escape
dismisses it. A click or pointer press dismisses it.

The wrapper, not the runtime alone, remembers a dismissal: a tip opened by the
focus tracker is not in the runtime's own open state, and the runtime's close on
the same press is computed from the previous frame (measured, plan `605`). Every
single-root trigger therefore forwards the press edge it actually receives —
`onMouseDown` on a `div` host, `onClick` on the native `<input>`/`<textarea>`
hosts, which receive no mouse-down event. The dismissal lasts until focus leaves
or, for a hovered tip, until the pointer leaves and returns.

## Accessibility

- **Release-runtime focus:** the pinned 0.10.0 runtime moves native focus but
  delivers no `onFocus`/`onBlur` to a component
  ([measured](../../../docs/gpuix-capabilities.md#focus-events)). The trigger's
  ring still paints: `ThemeProvider`'s native-focus tracker samples
  `getFocusedElementId()` every 50 ms, so focus reaches the paint up to one tick
  late (plan `590`). **The tip opens on keyboard focus too:** the wrapper learns
  its trigger's host id through the slot's `ref` (each single-root primitive
  forwards it, plan `596`) and compares it with the tracker's sample, so Tab
  opens the tip even though the runtime sends no `onFocus`. A click or Escape
  dismisses it while the trigger keeps focus; leaving and returning reopens it.
  A `ScrollArea`'s handle carries the viewport `id`, so its wrapped tip opens on
  `Tab` too (plan `610`). Role, name, tab order, keyboard operation and
  activation are otherwise unaffected.
- **A string tip is the trigger's description.** GPUix 0.10.0 has no
  `aria-describedby`, but it exposes `aria-description`; the wrapper writes the
  string content there, so a screen reader announces the explanation when the
  trigger takes focus, even while the tip is closed. A real string is trimmed
  for the tree (the painted text is unchanged), and a blank one is absent.
- **A blank string is no tip** (plan `573`). A computed missing translation must
  not publish `aria-description: "   "` or open an empty popover named with
  whitespace; the child renders without the trigger wrapper, the description and
  the layer.
- **Content that paints nothing is no tip** (plan `744`). The plan-`573` gate
  covered strings only, so a computed **node** tip that resolved to `null`
  opened an empty anchored layer and published an unnamed `tooltip` node, while
  `false` and a blank string opened nothing — whether a blank tip appeared
  depended on which falsy value the caller's conditional produced. The gate is
  the same `paintsContent` rule the labelled `Checkbox`/`Switch` rows use
  (plan `743`): absent content returns the child unchanged, and a `label` cannot
  resurrect it. Any **element** is still content — even an empty fragment —
  because the component cannot know what an element paints.
- **A blank description is no description** (plan `586`). The rule is not
  tooltip-specific: every control that takes the public `aria-description` prop
  trims a real value and omits a blank one, because a computed empty translation
  is the same defect whether the tip wrote it or the caller did.
- **The open tip is its own node.** The content carries `role="tooltip"` and,
  for a string, an `aria-label` with the same text — measured in the runtime
  (plan `071`). Non-string content is painted and becomes a `tooltip` node, and
  it takes its name from `label` — the same string describes the trigger. A
  node tip **without** a label paints unnamed, because the runtime cannot read
  text out of a node and the wrapper does not invent a name (plan `742`).
- The trigger must be focusable **and** named. A bare `div tabIndex={0}` gets
  focus but produces no accessibility node, so it cannot carry the description;
  give it a role (`role="img"` for an info icon) and an `aria-label`.
- A tooltip is **supplementary**: the same information must be reachable without
  hovering (visible text, or the control's name).
- There is no `focusVisible` state, so a mouse-opened and a keyboard-opened tip
  look identical.

## Theming

`tooltipStyle` uses the `popover` surface, `radius.sm`, `elevation.overlay`, the
`caption` type and one spacing step of inset. The wrapper caps the tip to the
room its side and alignment have (the window less the margins) and wraps the
text inside that cap; the element-tree caller, which has no viewport, keeps the
single-line `nowrap` form. The tip is chrome, so it declares `userSelect:
"none"` — a drag across it must not take the hint's text (measured, plan `398`);
`Tooltip.style` is merged last, so a caller can opt back in.

**Long content (plan `391`).** The runtime keeps a layer's left edge inside the
window margin but never caps its width: measured, a 200-word tip painted **6 270 px
wide** in a 1 280 px window, its text 6 258 px. The cap is the room the resolved
side and alignment actually have — a `start` tip begins at the anchor's left, an
`end` tip ends at its right, and a centred tip needs equal room on both sides.
A tip **beside** its trigger is capped by that side's room: a `left` tip ends at
the trigger's left edge (`triggerLeft − margin`), a `right` one starts at its
right edge (`viewportWidth − margin − triggerRight`), so a long tip wraps
instead of painting across its trigger (plan `393`). `align` places the other
axis on those sides and does not change the width. The painted tip's own box is
the anchor once it exists for a vertical side; a horizontal side uses the
trigger's edges, because a clamped layer's box would sit across the trigger.

## Limitations

- The trigger must be a focusable element that forwards the slot contract
  (above). Every single-root control does; `Box` and the roving composites do
  not, and a text host cannot open on hover.
- **A native text host has no hover.** GPUix 0.10.0 delivers `onMouseEnter` to a
  `div` but not to an `<input>`/`<textarea>` (measured, plan `345` §0), so a
  field's tip is keyboard-only. Nothing in this wrapper can change that.
- **The root hugs, so full-width children need `style`.** A child with
  `width: "100%"` resolves against the hugging root and collapses; a `Slider`
  without an explicit root width paints 16 px. `style` on `Tooltip` supplies the
  width (see Full-width triggers).
- **A `center` tip measures once per size.** The runtime has no layout callback,
  so the tip's box is known only after its first layout; the offset is applied
  in a layout effect before paint, so there is no visible jump. A content change
  while the tip is open re-measures (plan `391`), a window resize re-places the
  tip and re-caps it (plan `604`), and a trigger that moves under an open tip is
  re-measured on the same 100 ms cadence (plan `645`). The correction lands on
  the next sample, not in the same frame: GPUix has no `onLayout`.
- **The flip estimates one line, then measures.** The side is first chosen from
  `tooltipHeight` (padding + one caption line + border) because the tip does not
  exist yet. Once it is painted, its measured height drives the decision, so a
  wrapped tip flips on the next frame instead of staying on a side with no room
  (plan `391`). A tip taller than both gaps still clamps.
- **A tip taller than the window is clamped.** Text wraps inside the width cap,
  but there is no height cap or scrolling; a tip longer than the window is
  clipped by the runtime at the window edge. A paragraph belongs in a popover,
  not a tooltip.
- No `aria-describedby` association: the content is the trigger's
  `aria-description` instead, which is a description but not a reference.
- A non-string tip needs `label`: the runtime cannot read text out of a node, so
  an unlabelled rich tip is painted and becomes a `tooltip` node, but is not
  announced and adds no description to its trigger (plan `742`).
- No rich content: text wraps, but a paragraph with headings, actions or a form
  is a popover, not a tooltip.
- No arrow/caret and no touch-long-press behaviour.
- **The interactions are GPUix's; the open state is this wrapper's.** Hover,
  focus, click, Escape and the hover delay are the published tooltip's; `open`,
  `defaultOpen`, `onOpenChange` and `disableHoverableContent` follow the
  package's one controlled rule (plan `347`). A controlled parent that ignores
  an `onOpenChange(false)` request keeps the tip open — it owns the value.
- **A controlled tip is placed from its trigger's box, not from an event.** The
  root is measured while the tip is closed, so opening from code chooses the
  side before the first painted frame. While the tip stays open the trigger is
  re-sampled every 100 ms (plan `645`), so a layout change is followed too.

## Verification

- `src/components/Select.test.tsx` — the wrapper's theme spec, the root hug, the
  default `align` at the render seam, the tip-height estimate checked against
  `tooltipStyle`, and the description/name mapping for string and non-string
  content (plan `071`). **Rich tips (742):** a node tip named from its `label`
  (trimmed) writes both the trigger's description and the tip's name, an
  unlabelled one stays unnamed, a label shortens a string tip's announcement
  without changing its painted text, a blank label falls back, and a label
  cannot resurrect a whitespace-only string. **Blank content (573):** a
  whitespace-only string returns
  the child alone (no trigger wrapper, no tip), and a real string is trimmed for
  the description and the tip's name. **Absent content (744):** `src/components/Tooltip.test.tsx`
  returns the child alone for `null`, `undefined`, booleans, a blank string and
  an empty list, keeps a real string and a real node tip, and proves a label
  cannot resurrect absent content — the old string-only gate opened a wrapper for
  the absent values. **Open state (347):** the resolved `open`,
  the `disableHoverableContent` flag and the `onOpenChange` handler reach the
  host root, and a closed tip still passes `open={false}` rather than leaving
  the runtime uncontrolled. **Long content (391):** a cap makes the tip wrap and
  puts both `maxWidth` and `whiteSpace: normal` on the rendered tip; the
  uncapped tree keeps one line.

  roomier), the alignment rule on both axes (widths above/below, heights
  beside — plans `098`, `335`), and the tip width cap for every alignment and a
  horizontal side (plans `391`, `393`).
- `runtime/tooltip-side-cap.runtime.test.tsx` — a 60-word tip on a `left` and a
  `right` side is no wider than that side's room (the failing direction painted
  1 262 px where 984/1 140 were offered), a short tip keeps its natural width,
  and two triggers 120 px apart get tips 120 px apart (plan `393`).
- `runtime/floating-resize.runtime.test.tsx` — the size the host reports is

  a narrower window, a re-wrapped long tip flips below when it no longer fits
  above, and a `Select` list proves the same signal (plan `604`; the failing
  directions are recorded in that plan's §8). The same file follows a trigger
  that moves while open — a top-side tip that covered its moved trigger flips
  below — and proves the sampler is silent while the tip is closed (plan `645`).
- `runtime/tooltip-rich.runtime.test.tsx` — a rich (node) tip: with `label` the
  open tip is a `tooltip` node named by it and the trigger carries the same
  description; without one the tip paints and stays unnamed; a blank label
  leaves a string tip's own text as the announcement (plan `742`). An absent
  computed tip (`content={null}`) paints no layer, publishes no `tooltip` node
  and leaves the trigger with no description, even with a `label` (plan `744`).
- `runtime/tooltip-dismiss.runtime.test.tsx` — a focus-opened tip is dismissed
  by a real click on every single-root trigger (`Button`, `IconButton`, `Toggle`,
  `Checkbox`, `Switch`, `Input`, `TextArea`, `NumberField`, `Select`, `Slider`,
  `InfoTip`), and a hovered tip dismisses and reopens on a fresh entry (plan
  `605`; the pre-fix code left the tip painted on all eleven focus cases).
- `runtime/fields.runtime.test.tsx` — opens on hover and on keyboard focus,
  dismisses on click, keeps its content inside the anchoring frame, paints the
  popover role, paints the tip against the trigger in a column (`start`, `end`)
  and in a row (`bottom`), and **centres it within 1 px** of a 400 px trigger
  (plan `095`; the failing direction was 176.5 px left). Removing the root hug fails the `end` and row
  tests; making `center` the default fails the first (plan 060 §6).
  **Placement (067):** at the top edge the tip opens below its trigger
  (`8 >= 30` fails without the decision), a tip with room above stays above, and
  the painted height equals the estimate.
  **Horizontal sides (098):** `side="right"` and `side="left"` with
  `align="center"` centre the tip on the trigger's vertical centre within 1 px
  (the failing direction was 90 px low), and the left case has real room instead
