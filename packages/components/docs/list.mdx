---
title: List
description: A vertical collection of rows, optionally single- or multi-selectable.
---

`List` presents rows. With `selectionMode="single"` it becomes a `listbox`: arrow
keys move a roving tab stop, a click selects, and the list behaves as a single tab
stop instead of one per row. `selectionMode="multiple"` keeps that keyboard model
and adds the desktop selection modifiers. In both modes, typing the first letters
of a row jumps to it. A single or unselectable list can also pass `onActivate` to
run a row action — open a file, load a record — without treating every selection
change as an action. A plain list with `onActivate` keeps the same roving tab
stop and runs the focused row on `Enter`; without it the list is purely
presentational.

```tsx
import {
  List,
  ListItem,
  ListItemDescription,
  ListItemTitle,
} from "@gpuixui/components/list";

<List selectionMode="single" defaultValue="readme">
  <ListItem value="readme" textValue="README.md">
    <ListItemTitle>README.md</ListItemTitle>
    <ListItemDescription>~/GPUIXUI</ListItemDescription>
  </ListItem>
  <ListItem value="list" textValue="list.tsx">
    <ListItemTitle>list.tsx</ListItemTitle>
  </ListItem>
</List>;
```

## Modes

| `selectionMode` | Role | Tab stop | Keyboard |
| --------------- | ---- | -------- | -------- |
| `none` (default) | `list` / `listitem` | none; one roving row when `onActivate` is set | activation keys when `onActivate` is set |
| `single` | `listbox` / `option` | exactly one row | see below |
| `multiple` | `listbox` / `option` | exactly one row | see below |

## Keyboard (single mode)

| Key | Effect |
| --- | ------ |
| `↓` | focus the next enabled row, wrapping |
| `↑` | focus the previous enabled row, wrapping |
| `Ctrl+N` / `Ctrl+P` | the desktop equivalents of `↓` / `↑` |
| `Home` | focus the first enabled row |
| `End` | focus the last enabled row |
| `Enter` | select the focused row, then run `onActivate` when the list has one |
| `Space` | select the focused row only; it never runs the row action |
| Letter keys | jump to the next enabled row whose `textValue` starts with the typed prefix |

A disabled row is skipped by the arrow keys, by `Home`/`End` and by clicks; it can
never be selected, and it paints no hover or press fill and no pointer cursor.

Every key starts from the row that holds focus, whether the user arrived by a
click, an arrow, `autoFocus` or `Tab`. A native focus change does not dispatch
React's `onFocus` in `@gpuix/native@0.10.0`, so the list asks the renderer which
row is focused when a key arrives instead of trusting its own last-moved state.

## Keyboard (plain, with `onActivate`)

A `selectionMode="none"` list with `onActivate` is a list of actions: it takes one
roving tab stop and the same navigation keys, but has no selection to change.

| Key | Effect |
| --- | ------ |
| `↓` / `↑` | focus the next / previous enabled row, wrapping |
| `Ctrl+N` / `Ctrl+P` | the desktop equivalents of `↓` / `↑` |
| `Home` / `End` | focus the first / last enabled row |
| `Enter` | run `onActivate` for the focused row |
| `Space` | nothing — there is no selection to set |
| Letter keys | jump by `textValue`, as in the selectable modes |

A plain list **without** `onActivate` is presentational: no row is focusable and
the list handles no keys.

## Keyboard (multiple mode)

Movement works exactly as in single mode. Selection differs:

| Key | Effect |
| --- | ------ |
| `Space` / `Enter` | toggle the focused row, keeping the rest |
| `Shift+↓` / `Shift+↑` | move focus and select the range from the anchor |
| `↓` / `↑` (no shift) | move focus and re-anchor; the selection stays |
| `Cmd+A` / `Ctrl+A` | select every enabled row; focus stays put |

Select-all becomes the new anchor at the first enabled row, so a following
`Shift`+click extends from the top of the list. Single-mode lists ignore the key.
Type-ahead works here too: a typed jump moves focus and re-anchors without
changing the selection, so a following `Shift`+click extends from the row reached.

## Type-ahead

Type the first letters of a row to jump to it. Matching is a case-insensitive
**prefix** (not fuzzy), reads `ListItem`'s `textValue`, and searches the rows
after the current one, wrapping to the first match. A repeated letter therefore
cycles through the rows that start with it, the desktop convention. Disabled rows
and rows without `textValue` are skipped.

```tsx
<List selectionMode="single">
  <ListItem value="readme" textValue="README.md">
    <ListItemTitle>README.md</ListItemTitle>
  </ListItem>
  <ListItem value="design" textValue="Design notes">
    <ListItemTitle>Design notes</ListItemTitle>
  </ListItem>
</List>
```

Typing `d` focuses “Design notes”; typing `d` again stays there (one match).
Typing `r` from “Design notes” wraps back to “README.md”.

The typed prefix lives for 500ms. The window is a lazy comparison against
Effect's monotonic clock, not a timer: nothing runs while the list is idle, and a
prefix that matches nothing is cleared so the next letter starts a fresh search.

## Activation

Selection is state; activation is an action. Pass `onActivate` when a row must
**do** something — open a file, load a record, navigate:

```tsx
<List
  selectionMode="single"
  value={file}
  onValueChange={setFile}
  onActivate={(id) => openFile(id)}
>
  <ListItem value="readme" textValue="README.md">
    <ListItemTitle>README.md</ListItemTitle>
  </ListItem>
</List>;
```

| Gesture | Result |
| ------- | ------ |
| `Enter` (single) | selects the focused row, then calls `onActivate` with its value |
| `Space` (single) | selects only; it never activates |
| click (single) | selects, then calls `onActivate` |
| `Enter` (`selectionMode="none"` + `onActivate`) | calls `onActivate` for the focused row |
| `Space` (`selectionMode="none"` + `onActivate`) | nothing; there is no selection to make |
| click (`selectionMode="none"`) | calls `onActivate` immediately; there is no selection to make |
| click or `Enter` on a disabled row | nothing |
| any gesture on a `multiple` list | no activation; that variant does not accept the prop |

Passing `onActivate` is opt-in for the row-action contract: a picker that only
needs a choice should omit it, because a click will select without running
anything. A multiple-selection list is a set of toggles, so activation would run
by accident during range selection; the prop is rejected at the type level rather
than ignored at runtime.

There is no separate double-click action; the runtime's host events carry no
reliable double-click signal, so a click would have to mean both select and
activate. Use `Enter`/click activation, or render an explicit action control in
the row's `trailing` slot when the interaction must be mouse-only.

A control placed in `leading` or `trailing` owns its own keys: `Enter` runs only
that control, arrows do not move the list's focus, and typing into a field there
never reaches type-ahead. A click on it does not activate the row either.

## Selection

Controlled and uncontrolled both work, like every stateful component here:

```tsx
// Uncontrolled: the list remembers.
<List selectionMode="single" defaultValue="a" onValueChange={log} />;
<List
  selectionMode="multiple"
  defaultValue={["a"]}
  onValueChange={log}
/>;

// Controlled: the app remembers.
<List selectionMode="single" value={selected} onValueChange={setSelected} />;
<List
  selectionMode="multiple"
  value={assigned}
  onValueChange={setAssigned}
/>;
```

In controlled mode the list reports the change and leaves `aria-selected` where
the consumer put it — a suite asserts exactly that, because silently updating
would be the classic controlled-component bug.

### Multiple selection

| Pointer | Effect |
| ------- | ------ |
| click | select only that row; it becomes the anchor |
| `Cmd`/`Ctrl`+click | toggle that row, keeping the rest; it becomes the anchor |
| `Shift`+click | select the enabled range from the anchor to that row |

A range never includes a disabled row. Values are reported in the order they were
selected, without duplicates. Selecting the same set again reports nothing new.
Single mode still has no second click that clears the value; a multiple list
clears by toggling its last selected row.

**Not built**: no drag reorder and no `aria-multiselectable` (see Accessibility).

`autoFocus` on a row focuses it on mount and moves the list's roving state and
ring to it — the runtime applies native focus after React's effects and never
dispatches `onFocus`.

## Dynamic rows

A list whose rows are data — search results, a filtered file list, a permission
set — can change while it is focused. The tab stop and focus never ride a row
that is gone:

- Removing the row that owns the tab stop hands the stop to the selected row,
  else the first enabled row. Focus follows it when the list itself held the
  user's focus.
- Disabling that row does the same, so the stop never lands on a row that cannot
  be activated, and the disabled row stops painting the focus ring.
- A row that changes `disabled` or `textValue` is updated in place, so its
  authored position never drifts: arrows, `Home`/`End`, `Shift` ranges and
  type-ahead keep the declaration order.
- If the consumer focuses another control in the same update, the list leaves
  that focus alone.
- An emptied list focuses nothing, and rows that arrive later do not grab focus.

The rule follows the row the **list** focused. A focusable control placed in a
row's `trailing` slot is the consumer's own focus target and is not tracked; it
also owns its keys, so a key pressed in it never acts on the row.

## API

`List` and `ListItem` take the GPUix host props and merge `style` last.

| `List` prop | Type | Default |
| ----------- | ---- | ------- |
| `selectionMode` | `"none" \| "single" \| "multiple"` | `"none"` |
| `value` / `defaultValue` | `string` (single) · `ReadonlyArray<string>` (multiple) | — / `""` · `[]` |
| `onValueChange` | `(value: string) => void` (single) · `(values: ReadonlyArray<string>) => void` (multiple) | — |
| `onActivate` | `(value: string) => void` — single and `none` only; absent from the multiple variant | — |
| `dense` | `boolean` | `false` |

The value type follows the mode: a `single` list cannot be given an array and a
`multiple` list cannot be given a string — the props are a discriminated union,
so the compiler enforces it.

| `ListItem` prop | Type | Default |
| --------------- | ---- | ------- |
| `value` | `string` (required) | — |
| `textValue` | `string` — the text type-ahead matches; omit and the row is not searched | — |
| `disabled` | `boolean` | `false` |
| `leading` | `ReactNode` | — |
| `trailing` | `ReactNode` | — |

`ListItemTitle` is the row's one line; `ListItemDescription` is its second, muted
and ellipsised.

`ListItem` used outside `List` throws — a programming error at the boundary, not a
runtime state to recover from.

## Sizing

A row is `density.rowHeight + spacing.md` tall (40px on the default comfortable
density) and `density.rowHeight` when `dense` (32px). Selection paints
`colors.selected` / `colors.selectedForeground`; hover paints `colors.accent`;
a disabled row is drawn at 50% opacity with `cursor: not-allowed` and no hover or
press fill.

GPUix hover is per element: a child control's hover cancels its row's `hover`
style, so the row would lose its tint under a trailing button. `Button` and
`IconButton` report their pointer crossings to the enclosing row, and the row
keeps `colors.accent` while one of them is hovered (plan 606). A custom
interactive child does not participate; the row's own tint is per element.

## Style by state

`ListItem.style` takes a `StyleDesc` or a function of `ListItemState`
(`{ active, disabled, selected }`); `active` is the row the list's roving focus
is on.

```tsx
<ListItem
  value="readme"
  style={(state) => ({ opacity: state.selected ? 1 : 0.85 })}
>
  <ListItemTitle>README.md</ListItemTitle>
</ListItem>
```

## Accessibility

Disabled controls announce **Disabled** through `aria-description`; 0.10.0 has no
`aria-disabled` semantics (plan 516).

- `role="list"`/`"listitem"` without selection and `listbox`/`option` with it, so
  assistive technology reads a list of rows either way.
- `aria-selected` is set on every row in both selectable modes, so the selection
  (including each member of a multiple selection) is announced rather than only
  painted.
- **`aria-multiselectable` cannot be declared.** `@gpuix/native@0.10.0`'s
  `HostProps` has no such attribute, so assistive technology learns the mode from
  the per-row `aria-selected` values, not from the listbox itself.
- **The active row's focus ring shows for a click too.** `@gpuix/native@0.10.0`
  has no `focusVisible`, so a keyboard-only ring cannot be declared; the ring is
  the runtime's honest maximum. A `Tab` entry raises no React focus event, so the
  ring appears on the row when the first key arrives; the key and the selection
  already act on the renderer's focused row.
- Rows are reached as one list; Tab does not stop at every row.

## Limitations

- No drag reorder, no group headers, no nested rows.
- Activation is a callback, not a link: there is no `href`, no navigation
  service and no role change, so an activatable row is not announced as a link.
- A plain list without `onActivate` is presentational by design: its rows are not
  focusable and it handles no keys. Add `onActivate` when the rows are actions.
- A multiple list has no activation at all (the prop is rejected by the type),
  because a double gesture would run an action while building a range.
- Type-ahead searches `textValue`, not the rendered `ListItemTitle`: the row is a
  composition, so the list cannot read its text. An omitted `textValue` makes the
  row unsearchable rather than guessing.
- No `aria-multiselectable` in 0.10.0 (see Accessibility).
- No virtualisation: a `List` renders every row. A roving-focus move repaints
  only the two rows that changed, but the runtime still reconciles the whole
  collection and re-focuses natively — a 1,000-row list costs ≈0.6–2.5 s per
  move on this host (`docs/performance.md`). Long collections belong in
  `virtual-list`, which is a separate component with its own API.
- The rows are not accessible by index: the API is `value`-based.
- Hover is per element. Only `Button` and `IconButton` report their hover to the
  row; a custom interactive child in `leading`/`trailing` still cancels the
  row's tint while the pointer is over it.
- Focus tracking follows the rows the list focused. A focusable control inside a
  row's `trailing` slot is not tracked if the row disappears (see Dynamic rows).

- Focus cues are seeded by `autoFocus`; the runtime does not reliably deliver
  React `focus`/`blur`, so a ring may not paint when focus moves by code
  (plans 390/603/605).

`src/internal/collection.test.ts` for the navigation arithmetic,
`src/internal/typeahead.test.ts` for the shared prefix matching,
`src/list/selection.test.ts` for the multiple-selection rules, and
`src/list/row-state.test.ts` for the row-mask store: the modes and
their roles, the absence and uniqueness of the tab stop, selection by click and by
key, a disabled row rejecting both and carrying no pointer affordance, real
focus moving with wrap-around past a
disabled row, `Home`/`End`, the accent hover on a real mouse move (including
under a trailing `Button`, clearing when the pointer leaves, and after a hovered
control is removed), the dense
height, the controlled list not moving its own selection, type-ahead jumping and
cycling while skipping disabled and unlabelled rows, activation by `Enter` and by
click (and not by `Space`, a disabled row, a plain list without the prop, or a
held `Enter` repeating), the
arrow key reaching the row that activates, a plain activatable list's single tab
stop and its arrow/`Enter` path (with `Space` deliberately inert), and — in
multiple mode — plain/`Cmd`/`Shift` clicks, `Space` toggling, `Shift+Arrow`
ranges, `Cmd`/`Ctrl`+A selecting every enabled row, and a disabled row never
entering a selection. A row that is disabled and enabled again keeps its authored
position, so the next arrow key reaches its neighbour. A focus move repaints exactly the two rows that changed,
counted through the public `style` function. Dynamic rows: a removed or newly
disabled row never keeps the tab stop, focus follows the stop when the list held
it, a consumer's own focus in the same update is never stolen, and an emptied
list that refills does not grab focus. A control in a row's `leading`/`trailing`
slot keeps its own `Enter` (the row does not also activate) and a field there
keeps native focus while typing. A keyboard origin the React tree never saw — a
row reached with `Tab` — is still the row `Space`, `Enter`, an arrow and
type-ahead act from, because the list reads the renderer's focused id.
