---
title: Multi-step form
description: A workflow that validates one step at a time and submits the whole draft once.
---

`MultiStepForm` composes two landed pieces: `Form`'s schema-to-message validation
and `Stepper`'s progress indicator. It owns the step machine; the draft stays in
the caller's hands, exactly as with `Form`.

`next` validates **only the current step** before advancing, `back` never
validates, and `submit` runs the full schema once, on the last step, and hands
back the **decoded** value. A failed action paints one `role="alert"` summary and
locates every message at its schema path through `errorFor`.

## Usage

```tsx
import { Field, FieldInput, MultiStepForm } from "@gpuixui/components";
import { Button } from "@gpuixui/primitives";
import * as Schema from "effect/Schema";

const AccountFields = Schema.Struct({ email: Schema.NonEmptyString });
const BillingFields = Schema.Struct({ card: Schema.NonEmptyString });

const Checkout = Schema.Struct({
  email: Schema.NonEmptyString,
  card: Schema.NonEmptyString,
});

const steps = [
  { id: "account", label: "Account", schema: AccountFields },
  { id: "billing", label: "Billing", schema: BillingFields },
] as const;

<MultiStepForm
  schema={Checkout}
  value={{ email, card }}
  steps={steps}
  onSubmit={(checkout) => save(checkout)}
  label="Checkout"
>
  {(form) => (
    <div style={{ display: "flex", flexDirection: "column", gap: 12 }}>
      {form.step.id === "account" ? (
        <Field label="Email" error={form.errorFor("email")}>
          <FieldInput value={email} onChange={(event) => setEmail(event.value ?? "")} />
        </Field>
      ) : (
        <Field label="Card" error={form.errorFor("card")}>
          <FieldInput value={card} onChange={(event) => setCard(event.value ?? "")} />
        </Field>
      )}
      <div style={{ display: "flex", flexDirection: "row", gap: 8 }}>
        <Button onClick={form.back} disabled={form.isFirst || form.pending}>
          Back
        </Button>
        <Button
          onClick={form.isLast ? form.submit : form.next}
          disabled={form.pending}
        >
          {form.isLast ? "Place order" : "Continue"}
        </Button>
      </div>
    </div>
  )}
</MultiStepForm>;
```

The runnable build is `examples/multi-step-form.example.tsx`, registered in
`examples/index.ts` and mounted by the package's native example suite
(`src/behaviour/examples.test.tsx`). It uses the package's local button stand-in,
which is replaced when `@gpuixui/primitives`' theme provider and
`@gpuixui/tokens/react` become one (`TODO.md` → Interlocks).

## Steps are projection schemas

Each step names a schema that validates the draft as it stands. A projection is
enough: `Schema` decoding ignores keys the schema does not declare (measured for
both `Schema.Struct` and `Schema.Class`), so the same draft validates step by step
and again at the end.

```ts
const AccountFields = Schema.Struct({ email: Schema.NonEmptyString });
```

A failure's path is then the same key path the full schema reports, so the
`Field` on the current step paints the message with the same `errorFor` call the
final submit would use.

The `steps` prop is a non-empty tuple, so an empty workflow is a type error, not
an empty render.

## The render prop

`MultiStepForm` is one part (`docs/component-api.md` §8). The render prop is the
only way to reach its actions and state, as with `Form`:

```ts
interface MultiStepFormState {
  readonly index: number;
  readonly step: MultiStepFormStep;
  readonly isFirst: boolean;
  readonly isLast: boolean;
  readonly errors: ReadonlyArray<string>;
  readonly fieldErrors: ReadonlyArray<FieldMessage>;
  readonly pending: boolean;
  readonly errorFor: (
    path: PropertyKey | ReadonlyArray<PropertyKey>,
  ) => string | undefined;
  readonly next: () => void;
  readonly back: () => void;
  readonly submit: () => void;
}

interface MultiStepFormStep {
  readonly id: string;
  readonly label: string;
  readonly description?: string;
  readonly schema: Schema.ConstraintDecoder<unknown>;
}
```

`MultiStepForm` renders the `Stepper` and the error summary itself. The render
prop owns the current step's fields and the primary/secondary controls.

## Step lifecycle

1. `next()` is a no-op while `pending` or on the last step. It validates the
   current step; a failure keeps the index and shows that step's messages, a
   success clears them and moves forward.
2. `back()` is a no-op while `pending` or on the first step. It never validates,
   so a user can always leave a step that is failing.
3. `submit()` is a no-op while `pending` or **before the last step**, so a stray
   early call cannot report fields the user has not reached. On the last step it
   decodes the full schema; a failure shows every message, a success calls
   `onSubmit` once with the decoded value.
4. A message is stored with the index that produced it and only painted while
   that index is current. Moving to another step therefore cannot show the
   previous step's failure — including a move the caller made through the
   controlled `step` prop.
5. `pending` is the caller's async state, as in `Form`: the component does not
   track a request and never claims one finished.

## Revalidation

Add `revalidate` to the workflow in the usage example to re-check a failed
action while the user edits.

Nothing is validated before the first failed `next` or `submit`. After one, a
change to `value` re-runs **the schema that produced the stored messages** — the
step's projection for a failed `next`, the full schema for a failed final
`submit` — and updates the summary and `errorFor`. An edit that fixes the step
clears its messages without moving the step, so the caller still presses
`next` to advance. The draft is compared by identity: pass a new value when it
changes.

## API

| Part | Renders | Props |
| ---- | ------- | ----- |
| `MultiStepForm` | `div` (`role="form"` when `label` is given) + `Stepper` + the summary | `schema: Schema.ConstraintDecoder<T>` (required), `value: unknown` (required), `steps: readonly [MultiStepFormStep, ...MultiStepFormStep[]]` (required), `onSubmit: (value: T) => void` (required), `pending?: boolean`, `revalidate?: boolean`, `label?: string`, `step?: number`, `defaultStep?: number`, `onStepChange?: (index: number) => void`, `children: (state: MultiStepFormState) => ReactNode` |

`step` is controlled, `defaultStep` (default `0`) uncontrolled, and
`onStepChange` reports every accepted move in both modes. The resolved step is
always a whole, in-range index: a finite value is truncated and clamped, so a
controlled index outside the range or a fractional one cannot crash the render
or name no step, and a non-finite value starts at the first step. The controlled
value itself is never rewritten; `next` reports the whole index it moved to.

Every part takes the GPUix host props and merges `style` last.

## Theming

The workflow uses the same tokens as `Form`: `spacing.lg` between the indicator,
the summary and the step content, and `caption` type in `colors.destructive` for
each message. The indicator is `Stepper`, so its marker and label colours come
from the theme. There are no literal colours or sizes.

## Accessibility

- With `label`, the root is `role="form"` named by `aria-label`. Without it the
  root is a plain container: 0.10.0 has no `aria-labelledby`, so an unnamed form
  is not exposed as a landmark.
- The summary is a single `role="alert"`, so a failed action is announced once;
  each distinct message is its own text node.
- `Stepper` renders the steps as a `role="list"`; the current item carries
  `aria-selected` because 0.10.0 has no `aria-current`.
- The controls are the caller's: give each a real label and pass
  `disabled={form.pending}`.

## Limitations

- Owned-value: the caller passes the draft; there is no field registration.
- A step validator is a projection schema, so its keys are declared twice — once
  in the step schema and once in the full schema. That duplication is explicit;
  there is no schema-partitioning helper.
- A failed **final** submit reports every message by path, including fields on
  earlier steps. The summary names them; the caller must move back for the
  inline `Field` to paint them.
- No step click: `Stepper` is display-only in this runtime, so `next` and `back`
  are the only moves.
- `revalidate` compares the owned draft by identity, after a failed action only.
- The docs site cannot render this component live — it is a GPUix host tree, not
  DOM. The code above is the real source.

- Focus cues are seeded by `autoFocus`; the runtime does not reliably deliver
  React `focus`/`blur`, so a ring may not paint when focus moves by code
  (plans 390/603/605).

## Verification

`src/behaviour/multi-step-form.test.tsx` runs in the real GPUix renderer (17 tests): the first step and the indicator's current item, an invalid `next` showing
its message in both themes, a valid `next` advancing once and clearing the
message, `back` leaving a failing step, the last-step submit delivering the
decoded instance in both themes, an invalid final submit showing every message,
`submit` before the last step doing nothing, `pending` locking all three actions,
a controlled `step` staying authoritative, an out-of-range controlled index
clamping, a fractional controlled index naming the whole step below it (and
`next` reporting a whole index), a non-finite controlled index starting at the
first step, a controlled move hiding the previous step's message, one alert
with one text node per distinct message, no validation before the first failed
action, a failed step re-checking when the draft changes, and messages
persisting when `revalidate` is off.

```sh
nub run --filter @gpuixui/components test:behaviour
```
