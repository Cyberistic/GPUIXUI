title: Tabs
description: A roving-focus tab list and the panels it switches.

`Tabs` switches between panels that share one region. Selection lives in the tab
set, focus lives on a trigger, and the two move together unless `activation` says
otherwise.

```tsx
import {
  Tabs,
  TabsContent,
  TabsIndicator,
  TabsList,
  TabsTrigger,
} from "@gpuixui/components/tabs";

<Tabs defaultValue="profile">
  <TabsList label="Account">
    <TabsIndicator />
    <TabsTrigger value="profile">Profile</TabsTrigger>
    <TabsTrigger value="notifications">Notifications</TabsTrigger>
  </TabsList>
  <TabsContent value="profile">…</TabsContent>
  <TabsContent value="notifications">…</TabsContent>
</Tabs>;
```

## Anatomy

| Part | Responsibility |
| ---- | -------------- |
| `Tabs` | the selected value, the trigger registry, the tab stop |
| `TabsList` | `role="tablist"`, the arrow/Home/End keys, the rail |
| `TabsIndicator` | the rail's selected cue: one measured bar that travels between tabs |
| `TabsTrigger` | one `role="tab"`, `aria-selected`, its own focus |
| `TabsContent` | one `role="tabpanel"`, mounted only while selected and its trigger is registered |

Only the selected trigger is in the tab order; every other trigger is `-1`.
Arrow keys move focus *and* the selection in `automatic` mode; in `manual` mode
they only move focus, and Enter/Space selects. Disabled triggers are skipped by
every key and cannot be clicked. A move starts from the tab that actually holds
native focus (read from the renderer at key time); the last highlighted tab is
only the fallback, because a live click and `autoFocus` move focus without
running React's `onFocus`.

## Orientation

`orientation` defaults to `"horizontal"`. A vertical set puts the rail in a
column beside the panel and maps the arrow keys to the axis — `Down`/`Up`
instead of `Right`/`Left`. Home/End, wrapping, disabled skipping, manual
activation and the controlled rule are identical on both axes.

```tsx
<Tabs defaultValue="general" orientation="vertical">
  <TabsList label="Workspace sections">
    <TabsTrigger value="general">General</TabsTrigger>
    <TabsTrigger value="members" disabled>
      Members
    </TabsTrigger>
    <TabsTrigger value="billing">Billing</TabsTrigger>
  </TabsList>
  <TabsContent value="general">…</TabsContent>
  <TabsContent value="billing">…</TabsContent>
</Tabs>
```

`examples/tabs.example.tsx` exports both shapes: the horizontal account settings
and the vertical workspace settings, each with an indicator.

## Indicator

A tab rail has one selected state. Without an indicator the selected trigger
paints its own `card` fill; mounting `TabsIndicator` inside `TabsList` moves that
cue into one shared element, a bar on the rail's inner edge that spans the
selected tab and slides to the next one.

```tsx
<TabsList label="Account settings">
  <TabsIndicator />
  <TabsTrigger value="profile">Profile</TabsTrigger>
  <TabsTrigger value="billing">Billing</TabsTrigger>
</TabsList>
```

- The bar is measured, not inferred: the rail's and the selected trigger's boxes
  are read after commit, so it follows a label that grows, a theme or density
  change and a window resize.
- It hugs the rail's inner bottom edge (horizontal) or inner left edge
  (vertical) and is exactly as long as the selected trigger.
- `left`, `top`, `width` and `height` animate over 150 ms `easeOut`;
  `animate={false}` snaps. The runtime has no reduced-motion signal, so the app
  chooses.
- While the indicator is mounted the selected trigger keeps only its
  `foreground` text colour — the pair never paints two fills. Leave the
  indicator out and today's filled pill is unchanged.
- A set with no selected tab, or whose selected trigger is not registered,
  paints no bar rather than a bar at the origin.

## Keyboard

| Key | Result |
| ---- | ------ |
| `ArrowRight` / `ArrowLeft` (horizontal) | next/previous enabled tab, wrapping |
| `ArrowDown` / `ArrowUp` (vertical) | next/previous enabled tab, wrapping |
| `Home` / `End` | first/last enabled tab |
| `Enter` | select the focused tab on press (the only way in `manual`) |
| `Space` | select the focused tab on release |

## Controlled and uncontrolled

```tsx
<Tabs defaultValue="profile">…</Tabs>;                     // remembers
<Tabs value={tab} onValueChange={setTab}>…</Tabs>;         // app remembers
```

A controlled tab set reports a click or key but does not switch its panel until
the consumer re-renders with the new `value` — the classic contract, tested.
Pressing the tab that is already selected reports nothing: a request for the
value the set already holds is a no-op in both modes (plan 517). Supplying both
`value` and `defaultValue` is tolerated: `value` wins and `defaultValue` seeds
only the uncontrolled case, with no warning.

## A tab that changes

Tabs are often built from data: a settings surface disables a section while it
loads, or drops one that the current plan does not include. The tab stop follows
the live tabs:

- A trigger that disappears or turns `disabled` never keeps the tab stop, focus
  or the highlight. The stop falls to the selected tab, else the first enabled
  one. The handover reads the renderer's focused host, because a `Tab` entry and
  a programmatic move focus the trigger without running React's `onFocus`; the
  last tab the component focused is only the fallback. Focus follows the stop
  while the caller's control is still mounted. A trigger removed in the same
  update has no host left to report, so the stop moves but focus is left to the
  app (a missing focus signal, not a kept one — plan 646).
- Handover **does not change the selection**: the panel the consumer chose (or
  the controlled `value`) stays. A disabled selected tab keeps its panel until
  the app changes the value.
- If the consumer focuses another control in the same update, the tab set leaves
  that focus alone.
- A tab keeps its declaration position when it is disabled and enabled again:
  the registry updates the row in place instead of re-registering it, so arrow
  movement still follows the authored order.

```tsx
<Tabs defaultValue="general">
  <TabsList label="Workspace sections">
    <TabsTrigger value="general">General</TabsTrigger>
    <TabsTrigger value="billing" disabled={billingIsLoading}>
      Billing
    </TabsTrigger>
  </TabsList>
  <TabsContent value="general">…</TabsContent>
  <TabsContent value="billing">…</TabsContent>
</Tabs>;
```

A panel follows the live triggers: it renders only while a trigger with its
value is registered. Removing the trigger therefore takes its panel with it,
whether the value came from the uncontrolled selection or a controlled `value`;
the selection itself is never rewritten, so re-adding the trigger brings the
panel back. A **disabled** selected tab still keeps its panel — it is a tab, it
just refuses input.

## API

Every part takes the GPUix host props and **merges `style` last**.

| Part | Renders | Props |
| ---- | ------- | ----- |
| `Tabs` | provider (no host element) | `value?: string`, `defaultValue?: string` (default `""`), `onValueChange?: (value: string) => void`, `orientation?: "horizontal" \| "vertical"` (default `"horizontal"`), `activation?: "automatic" \| "manual"` (default `"automatic"`) |
| `TabsList` | `div` (`role="tablist"`) | `label?: string` (the list's accessible name) |
| `TabsIndicator` | `div`, absolutely positioned in the rail | `thickness?: number` (default `2`), `animate?: boolean` (default `true`), `testId?: string` (default `<list testId>-indicator`, else `tabs-indicator`), `style?: StyleDesc` |
| `TabsTrigger` | `div` (`role="tab"`) | `value: string` (required), `disabled?: boolean` (default `false`), `style?: StateStyle<{ active: boolean; disabled: boolean; focused: boolean; highlighted: boolean; orientation: TabsOrientation }>` |
| `TabsContent` | `div` (`role="tabpanel"`), only while a live trigger with `value` is registered | `value: string` (required); an `aria-label` overrides the trigger's name |

`autoFocus` sets the initial `focused` state and the roving highlight, so the
trigger's ring is painted on the first commit — the runtime applies native focus
after React's effects and never dispatches `onFocus`.

## Theming

The rail paints `colors.background`, a `borderWidth.thin` border in `colors.border`
and `radius.md`. The selected trigger takes `colors.card` with
`colors.foreground`; unselected triggers use `colors.mutedForeground` and hover
with `colors.hover`. Trigger height is `controlHeight(theme, "md")`.

`TabsIndicator` paints `colors.primary` with `radius.sm`. While it is mounted
the selected trigger drops `colors.card`, so the rail's emphasis is one element.

## Style by state

`style` takes a `StyleDesc` or a function of `TabsTriggerState`
(`{ active, disabled, focused, highlighted, orientation }`); the result merges
after the trigger's own rules.

```tsx
<TabsTrigger
  value="profile"
  style={(state) => ({ opacity: state.disabled ? 0.4 : 1 })}
/>
```

## Accessibility and limitations

Disabled controls announce **Disabled** through `aria-description`; 0.10.0 has no
`aria-disabled` semantics (plan 516).

- `role="tablist"`, `role="tab"`, `role="tabpanel"` and `aria-selected` are
  exposed; the roving tab index is the single-stop pattern. Give the list a
  `label` so the tab set has a name — the shipped examples do, and a caller
  `aria-label` wins over it.
- Each trigger names itself from its plain-text child, because 0.10.0 reports no
  name from contents; a trigger composed from elements passes `aria-label`.
- **No `aria-orientation`, `aria-controls` or `aria-labelledby`** in
  `@gpuix/native@0.10.0`: `HostProps` exposes only `aria-label`,
  `aria-description`, `aria-expanded`, `aria-selected`, `aria-valuetext` and
  `aria-level`. A panel borrows its trigger's name instead — the same plain-text
  label the trigger paints (plan 391) — so `<TabsTrigger value="profile">Profile</TabsTrigger>`
  announces the panel as `Profile`, not `profile`. An explicit `aria-label` on
  `TabsContent` wins; a composed trigger with no plain text falls back to the
  value. A panel with no live trigger is not painted at all. The
  trigger→panel relationship itself stays positional.
- The list owns the keys because a key event on a focused trigger bubbles to the
  list — measured in the real renderer, the same behaviour `List` relies on.
- Vertical tab sets put the rail in a column beside the panel; the axis is a
  layout and keyboard choice, not an ARIA attribute (unavailable, below).

- A focused tab that is **removed** hands the tab stop and focus to the selected
  tab. Because 0.10.0 dispatches no `focus`/`blur` and a removed host cannot be
  read, the holder is sampled every 50 ms while the tab exists; a removal inside
  that window is still a lost focus (plans 646/712).
- Focus cues are seeded by `autoFocus` and then follow the renderer's focused
  host (a 50 ms sample through the shared `useFocusState` host id), so a tab
  reached by `Tab`, a programmatic move or a press paints the ring and losing
  focus clears it (plan 752); caller `onBlur` still runs only when the runtime
  delivers one.
- `TabsIndicator` is measured from the rail and the selected trigger: the bar's
  start along the rail is **the component's own `spacing.xs` padding**, so a
  caller who overrides `TabsList`'s `style.padding` shifts it off the tab. The
  runtime has no `transform`, so the slide animates `left`/`top`/`width`/`height`
  rather than translating, and there is no reduced-motion signal. RTL is out of
  scope (no logical edges in 0.10.0).

## Verification

`src/behaviour/tabs.test.tsx` runs in the real GPUix renderer (44 tests): click
switching, the active theme role in both themes, an arrow move starting from a
natively focused tab that never ran `onFocus`, arrow wrap with a disabled tab,
manual activation waiting for Enter, Space selecting on release, Home/End, the
controlled contract, a press on the already-selected uncontrolled tab reporting
nothing (plan 517), a panel whose value matches nothing, a caller `ref`, a caller
`onBlur` composed with the focus ring, a trigger ring that follows a native focus
move and clears when focus leaves (plan 752), and four vertical-axis cases — Down/Up
movement with wrap, Left/Right ignored, the row/column layout, and manual
activation. Dynamic tabs: a tab that becomes disabled hands the tab stop and
focus to a live tab through the renderer's focused host (a native focus move
never runs `onFocus`), a disabled tab stops reporting itself as highlighted, the
handover never changes the selection, a consumer's same-update focus is never
stolen, and a disable/enable round trip keeps the authored tab order; the focused
tab is sampled while it exists, so removing it hands the tab stop **and** focus
to the selected tab, removing another tab leaves focus alone, and a consumer's
same-update focus still wins (plans 646/712). A panel needs a live
trigger: removing a trigger unmounts its panel
(and restoring it brings the panel back without changing the selection), a
controlled value with no trigger paints nothing, and a disabled selected tab
still keeps its panel (plan 566). Panels are named by their triggers: the caller's
`aria-label` override, the value fallback for a composed trigger, and a label
change renaming the panel without reordering the row (plan 564). The vertical
guard is
proven in both directions: inverting the axis mapping fails the movement and
axis-isolation tests, inverting the layout fails the layout test, and forcing
`selectsOnFocus` to `true` fails the manual test.

The indicator (plan 715) is measured in the real renderer: it sits on the
selected tab's span and the rail's inner edge, follows a selection change, is
caught mid-slide on the first frame after a switch, hangs on the left edge in a
vertical set, paints the active theme's `primary`, and refuses to paint with no
selection or after its selected trigger is removed. Mounting it takes the
selected fill off the trigger — the same tree without an indicator still paints
`colors.card` — keeps a caller's `testId`, follows a controlled `value`, and
stays put when a controlled set refuses the press. Four mutations each fail a
case: dropping the motion makes the bar jump, dropping the rail's padding puts
the span and the vertical bar in the wrong place, ignoring the indicator in the
trigger's fill doubles the emphasis, and discarding the caller's `testId` breaks
the naming case.

A trigger forwards `onBlur` after clearing its focus ring, so the caller's handler
runs exactly once.
