---
title: Popover
description: A floating panel anchored to the control that opened it.
---

`Popover` floats a surface next to its trigger without making the rest of the
window modal. Positioning is GPUix's own `anchored` layer. Measured against
0.10.0, the runtime **snaps** a surface inside the window but does not flip it,
and its `center` alignment centres on the trigger's containing block rather than
the trigger. The component therefore owns the placement correction: it flips a
snapped surface back off its trigger and converts `align="center"` into a
measured centre. It also owns the open state and the dismissal rules.

```tsx
import {
  Popover,
  PopoverContent,
  PopoverTrigger,
} from "@gpuixui/components/popover";

<Popover>
  <PopoverTrigger>Columns</PopoverTrigger>
  <PopoverContent side="bottom" align="end">
    <ColumnToggles />
  </PopoverContent>
</Popover>;
```

## Anatomy

| Part | Responsibility |
| ---- | -------------- |
| `Popover` | open state and the positioning root the anchored layer measures |
| `PopoverTrigger` | a button that toggles the popover, `aria-expanded` included |
| `PopoverContent` | the floating surface, rendered only while open |

`PopoverContent` takes `side` (`top`/`right`/`bottom`/`left`, default `"bottom"`),
`align` (`start`/`center`/`end`, default `"start"`), `sideOffset` (default `6`) and
`collisionPadding` (default `8`, the margin kept from the window edge when the
surface snaps). When the snapped surface would cover its trigger, the component
opens it on the opposite side if that side has room, otherwise on the roomier
side. `align="center"` is exact: the runtime's `center` is not used.
`alignOffset` is still added on top if the caller needs its own adjustment.
A non-finite `sideOffset`, `alignOffset` or `collisionPadding` keeps its
documented default, so a malformed number cannot drop the gap, the measured
centre correction or the window margin (plan 813).

## Dismissal

| Action | Result |
| ------ | ------ |
| `Escape` | closes, and returns focus to the trigger |
| `Tab` | moves to the next control inside the panel; past the last one it closes, and focus continues with the app control after the trigger |
| `Shift+Tab` | the same, backwards; stepping back over a control and then tabbing forward again continues the walk instead of closing the panel |
| press outside | closes without moving focus (the press already gave it) |
| press inside | does nothing |
| click the trigger while open | closes it |

Mounted open together with a dialog, the panel is still the top layer: one
`Escape` closes the panel and leaves the dialog open (plan 732).

The walk owns its key. Inside a `Dialog` or `Drawer` the modal's Tab trap would
otherwise advance focus a second time on the same press, so the panel claims each
`Tab` it handles and the modal leaves it alone; the trap resumes when the panel
closes (plan 719).

The popover is a layer in the same dismiss stack as `Dialog`, so pressing outside
both closes the popover first and leaves the dialog open. A press on the
popover's own trigger is not an outside press: the layer claims it and the click
that follows closes the popover. The runtime delivers that click in a later task
than the press, so the rule reads the press position rather than marking the next
click.

## Controlled and uncontrolled

```tsx
<Popover defaultOpen>…</Popover>;                       // remembers
<Popover open={open} onOpenChange={setOpen}>…</Popover>; // app remembers
```

## Focus and keyboard

Focus moves to the panel's **first control** on open — or to the panel itself
when it has none — so keys reach the content without a click. Tab then walks the
panel's tab stops; it closes only at either end, where focus continues with the
next (or previous) control after the trigger. A popover is not modal, so it never
traps, and a keyboard user is never left on an unmounted surface.

`autoFocus={false}` leaves focus to the caller (the date picker uses this to keep
focus on its calendar); Tab then closes the panel, as it did before.

## API

The trigger and the surface merge `style` last.

| Part | Renders | Props |
| ---- | ------- | ----- |
| `Popover` | provider (no host element) | `open?: boolean`, `defaultOpen?: boolean` (default `false`), `onOpenChange?: (open: boolean) => void` |
| `PopoverTrigger` | `div` (`role="button"`, `aria-expanded`) | the button's `variant`, `size` and `disabled` |
| `PopoverContent` | anchored surface | `side?: "top" \| "right" \| "bottom" \| "left"` (default `"bottom"`), `align?: "start" \| "center" \| "end"` (default `"start"`), `sideOffset?: number` (default `6`), `collisionPadding?: number` (default `8`), `alignOffset?: number` (default `0`) |

## Theming

The surface paints `colors.popover` / `colors.popoverForeground`,
`radius.lg`, `borderWidth.thin` in `colors.border`, the `md` elevation and
`spacing.lg` padding, with a 200px minimum width.

## Motion

`PopoverContent` runs `motionFromClasses` from `@gpuixui/tw` through
`AnimatePresence`: a 100 ms opacity fade plus the shadcn
`slide-in-from-*` offset for the resolved side (bottom → from top, left → from
right, and so on). The panel stays mounted for the exit and is inert while it
leaves. `zoom-in-95`/`zoom-out-95` are recorded as unsupported: GPUI has no
transform, so no scale is faked.

## Accessibility and limitations

- `aria-expanded` on the trigger.
- **No `aria-haspopup`, `aria-controls` or `aria-labelledby`**:
  `@gpuix/native@0.10.0` exposes only `aria-label`, `aria-description`,
  `aria-expanded`, `aria-selected`, `aria-valuetext` and `aria-level` (see
  `HostProps` in `@gpuix/native/dist/host.d.ts`), so the link between trigger and
  surface is positional, not semantic.
- Positioning is the runtime's anchored layer: there is no arrow, no custom anchor
  element, and no separate backdrop. The runtime snaps, so the component flips
  once when the snapped surface would cover its trigger; it does not do
  continuous collision-aware placement while the window resizes. Keep a popover's
  content short; for a form that must block the window, use **Dialog**.
- `align="center"` cannot centre a surface that would leave the window: the
  runtime's snap margin wins at the edges.
- A press outside hands focus to whatever was pressed, so focus is not restored to
  the trigger in that path. Escape is the keyboard path that restores it.
- The renderer has no way to list an element's tab stops, so the panel's first
  stop is the one measured on open. Content that removes or adds tab stops while
  open cannot trap the user — the stops walked in the current direction bound the
  cycle — but a stop removed mid-cycle can cost one extra Tab before the panel
  closes. Turning round starts a new walk, so a step back never ends it early.
- The animated panel wrapper carries `<testId>-surface`, while the panel keeps
  `<testId>`. The wrapper is the border box and the reported content size is its
  padding box, so the two differ by the border width (plan 540, plan 597).

- Focus cues are seeded by `autoFocus`; the runtime does not reliably deliver
  React `focus`/`blur`, so a ring may not paint when focus moves by code
  (plans 390/603/605).
- The runtime coerces a non-finite host offset to `0`, so the component
  normalises `sideOffset`, `alignOffset` and `collisionPadding` itself; an
  explicit `0` or negative offset is passed through unchanged (plan 813).

## Verification

`src/behaviour/popover.test.tsx` runs in the real GPUix renderer (30 tests):
opens below the trigger by measured bounds, honours `side="right"`, centres a
requested panel on its trigger, opens above a trigger near the window bottom
instead of covering it, keeps the default gap, the measured centre and the
window-margin flip when `sideOffset`/`alignOffset`/`collisionPadding` is
non-finite (plan 813), Escape closing and restoring focus, an outside press
closing without the following click re-opening it, a **held** press on the
trigger closing it on release and staying closed, a press inside keeping it
open, Tab closing a control-less panel while handing focus to the next app
control, opening focus on the first control, Tab walking the panel's controls
(two presses, panel still open), Tab past the last control closing and continuing
after the trigger, Shift+Tab walking backwards and leaving before the first
control, tabbing forward again after a step back walking to the last control and
leaving at the end (not closing on the step back), turning round and leaving
before the first control, closing rather than trapping when the first tab stop is
removed, a
controlled popover reporting `onOpenChange` while staying as the consumer says
(including an inline consumer that keeps it closed), both themes, a caller
trigger `ref`, the 100 ms fade + side slide, the panel remaining through its
exit before it unmounts, and a controlled close the caller refuses leaving the
panel and focus where they are (Escape and Tab), with focus moving only when the
close is accepted. Two further cases place that panel inside a `Dialog`: Tab
walks its controls once each and closes after the last, Shift+Tab leaves before
the trigger, and the dialog's own caller still observes every claimed key
(plan 719).

A panel mounted open together with its dialog closes alone and leaves the dialog open (plan 732).
