title: Form
description: Schema validation and a submit lifecycle around a group of fields.

`Form` joins two things the package already ships: the schema-to-message
validation in `validation/logic.ts`, and the `Field` parts around each control. A
submit runs the schema; a failure shows every message in one summary **and**
locates each message at the field path that produced it; a success calls
`onSubmit` with the **decoded** value.

It is **owned-value**: the runtime has no form element and no DOM to read values
from, so you pass the value you already hold. `Form` never invents a second
source of truth.

## Usage

```tsx
import { Field, FieldInput, Form } from "@gpuixui/components";
import { Button } from "@gpuixui/primitives";

const Signup = Schema.Struct({
  email: Schema.NonEmptyString,
  name: Schema.NonEmptyString,
});

<Form
  schema={Signup}
  value={{ email, name }}
  pending={saving}
  onSubmit={save}
  label="Create account"
>
  {(form) => (
    <div style={{ display: "flex", flexDirection: "column", gap: 12 }}>
      <Field
        label="Email"
        description="We never share it"
        error={form.errorFor("email")}
      >
        <FieldInput value={email} onChange={(event) => setEmail(event.value ?? "")} />
      </Field>
      <Field label="Name" error={form.errorFor("name")}>
        <FieldInput value={name} onChange={(event) => setName(event.value ?? "")} />
      </Field>
      <Button onClick={form.submit} disabled={form.pending}>
        Create account
      </Button>
    </div>
  )}
</Form>;
```

The runnable build is `examples/form.example.tsx`, registered in
`examples/index.ts` and mounted by the package's native example suite
(`src/behaviour/examples.test.tsx`). It uses the package's local button stand-in,
which is replaced when
`@gpuixui/primitives`' theme provider and `@gpuixui/tokens/react` become one
(`TODO.md` → Interlocks).

## The render prop

`Form` is one part (`docs/component-api.md` §8). There is no `FormSubmit` or
`FormMessage` part, so the only way to reach the submit action — and the state
you need to render it — is the render prop:

```ts
interface FormState {
  readonly errors: ReadonlyArray<string>;
  readonly fieldErrors: ReadonlyArray<FieldMessage>;
  readonly pending: boolean;
  readonly submit: () => void;
  readonly errorFor: (
    path: PropertyKey | ReadonlyArray<PropertyKey>,
  ) => string | undefined;
}

interface FieldMessage {
  readonly path: ReadonlyArray<PropertyKey>;
  readonly message: string;
}
```

`Form` renders the error summary itself, so the render prop does not have to. The
summary is a `role="alert"` row with one `<text>` per message, in schema order.
`fieldErrors` is the same validation pass with the path kept; `errorFor` is the
ergonomic lookup over it. Pass a single key for a top-level field
(`form.errorFor("email")`) or an array for a nested one
(`form.errorFor(["user", "email"])`). A field the schema accepted returns
`undefined`, so `error={form.errorFor("email")}` hides the message for free.
`validateFields` is exported from `@gpuixui/components/validation/logic` for a
caller that validates outside a `Form`.

## Submit lifecycle

1. `submit()` is a no-op while `pending` is true.
2. The value is decoded with your `schema` (`Schema.decodeUnknownResult`).
3. On failure, the messages from `validateFields` are shown (as a summary and
   with their paths) and `onSubmit` is not called. The messages are the schema's
   own text, never a package invention.
4. On success, the errors clear and `onSubmit` receives the decoded value — a
   class instance if `schema` is a `Schema.Class`, not the raw object.

The caller owns the request: pass `pending` while it runs, then re-render with a
new value. The form does not track a request, so it never claims one finished.

## Revalidation

By default a failed submit's messages stay until the next submit. Add
`revalidate` to the form in the usage example to re-check them as the user
edits.

The rules are deliberate:

1. Nothing is validated before the first failed submit, so an untouched form
   never greets the user with errors.
2. After a failure, changing `value` or `schema` runs the same validation pass
   and updates both the summary and every `errorFor` result. `onSubmit` is never
   called by a re-check.
3. Fixing one field removes only its message; fixing everything removes the
   summary and leaves the form valid to submit; a new failure replaces the old
   one.

`value` is compared by **identity**, the React convention. Pass a new value when
the draft changes; mutating the same object in place is not detected. An
unrelated re-render with a new object re-checks the schema but repaints nothing,
because equal messages keep the previous array identity.

## API

| Part | Renders | Props |
| ---- | ------- | ----- |
| `Form` | `div` (`role="form"` when `label` is given) | `schema: Schema.ConstraintDecoder<T>` (required), `value: unknown` (required), `onSubmit: (value: T) => void` (required), `pending?: boolean`, `revalidate?: boolean`, `label?: string`, `children: (state: FormState) => ReactNode` |

Every part takes the GPUix host props and merges `style` last.

## Validation

- The schema decides; `Form` only runs it. `validation/logic.ts` maps its issues
  to messages with `SchemaIssue.makeFormatterDefault`, so a `message` annotation
  reaches the user verbatim.
- One submit reports every failing field (`validateFields` uses
  `errors: "all"`), in schema order. A path is the schema's own key sequence,
  root-first; a failure on the value itself has path `[]`.
- Two failures that share a message on **different** fields stay two entries,
  because each belongs under its own control. The summary deduplicates by
  message, so `errors` is the shorter list.
- `errorFor` is the same data, looked up by path. `Field` paints the message it
  is given, so inline validation never re-runs the schema or invents a second
  message.
- There is no validate-on-blur or validate-on-keystroke; the first validation
  is the caller's `submit`. `revalidate` only re-checks after a failure.
- Without `revalidate`, errors persist until the next submit. With it, a value
  change re-checks them; the owned value is compared by identity, so the caller
  must pass a new value rather than mutate one in place.

## Theming

The form's layout uses `spacing.lg`; the summary uses `caption` type in
`colors.destructive`. There are no literal colours or sizes.

## Accessibility

- With `label`, the root is `role="form"` named by `aria-label`. Without it the
  root is a plain container: 0.10.0 has no `aria-labelledby`, so an unnamed form
  is not exposed as a landmark.
- The summary is a single `role="alert"`, so a failed submit is announced once;
  each message is its own text node.
- The submit control is the caller's: give it a real label and pass
  `disabled={form.pending}`.

## Limitations

- Owned-value: the caller passes the value; there is no field registration.
- A message carries the schema's key path, not a display label. Renaming a field
  in the UI does not change the path; pass the schema's keys to `errorFor`.
- `revalidate` compares the owned value by identity: the caller must pass a new
  value; an unrelated re-render with a new object re-checks but repaints nothing.
- The docs site cannot render this component live — it is a GPUix host tree, not
  DOM. The code above is the real source.

- Focus cues are seeded by `autoFocus`; the runtime does not reliably deliver
  React `focus`/`blur`, so a ring may not paint when focus moves by code
  (plans 390/603/605).

## Verification

`src/behaviour/form.test.tsx` runs in the real GPUix renderer (13 tests): idle
state, a valid submit delivering the decoded instance, an invalid submit showing
every message and never submitting, one alert with separate message nodes,
`pending` blocking a submit, a consumer `style` winning while the summary paints
destructively in both themes, the named form landmark, each message located at
its field path (with an accepted field returning `undefined`), an inline
`Field` painting the located message plus the destructive input border, no
validation before the first failed submit, a fixed field's message clearing on
edit, the summary clearing when an edit makes the form valid, and messages
persisting when `revalidate` is off.
`src/validation/logic.test.ts` has 4 cases for `validateFields`/`errorFor`'s
lookup, including nested and root paths, plus 5 for `sameFieldMessages` (path,
message, order and length).
