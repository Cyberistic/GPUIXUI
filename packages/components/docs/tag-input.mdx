---
title: Tag input
description: A set of tokens entered through a field, with removable chips.
---

`TagInput` edits a list of tokens: the caller owns the list, the component owns
the draft and the add/remove rules. Chips are rendered from the caller's value,
so nothing the component holds is invisible to the caller.

## Usage

```tsx
import { TagInput, TagInputChip, TagInputField } from "@gpuixui/components";

const [tags, setTags] = useState<ReadonlyArray<string>>(["design"]);

<TagInput label="Tags" value={tags} onValueChange={setTags} max={5}>
  {tags.map((tag) => (
    <TagInputChip key={tag} value={tag} />
  ))}
  <TagInputField placeholder="Add a tag…" />
</TagInput>;
```

The runnable build is `examples/tag-input.example.tsx`, registered in
`examples/index.ts` and mounted by the package's native example suite
(`src/behaviour/examples.test.tsx`).

## The token rules

| Action | Result |
| ------ | ------ |
| `Enter` in a non-empty field | trims and commits the draft, clears it |
| Typing `,` | commits everything before it; the remainder stays the draft |
| Pasting `"a,b"` | adds both tokens |
| A token already present | ignored, unless `allowDuplicates` |
| Reaching `max` | further additions are refused; existing tokens stay. A fractional cap truncates (`1.5` means one token) and a non-finite one means no cap (plan 662) |
| The chip's clear control | removes that token |
| Whitespace-only input | never becomes a token |
| A refused edit (duplicate, `max`, empty draft) | reports no change: `onValueChange` is not called |

A pasted list arrives as one `onChange` carrying every comma-separated token, so
the whole list commits at once. A comma the user types is a different shape — it
has an empty tail — so everything before it commits and the field stays ready for
the next token.

Removal is the chip control. **Backspace on an empty field is not wired**: the
installed `@gpuix/native@0.10.0` emits no `keyDown` for Backspace or Delete in
the test renderer, so the component cannot promise (or test) that gesture. The
docs and the inventory row record it rather than fake it.

The rules are pure (`src/tag-input/logic.ts`: `splitDraft`, `addTokens`,
`removeToken`) so they are covered without a renderer.

## API

| Part | Renders | Props |
| ---- | ------- | ----- |
| `TagInput` | `div` with `role="group"`, the field surface and focus ring | `value` (required), `onValueChange` (required), `label` (required), `max?`, `allowDuplicates?`, `disabled?`, children |
| `TagInputField` | `<input>` | input props minus `value`/`onChange`/`onSubmit`, `style?: StateStyle<TagInputFieldState>` |
| `TagInputChip` | chip `div` with a removal `role="button"` | `value` (required), `style?: StateStyle<TagInputChipState>` |

`TagInputFieldState` and `TagInputChipState` are `{ disabled }`.

There is **no uncontrolled mode**: chips must be rendered from a value the caller
holds, so a `defaultValue` the caller cannot read would be a trap. Use a
controlled list.

## Theming

The group uses `background`, `border`, `radius.md`, `controlHeight` and
`focusRing`; chips use `muted` / `mutedForeground` and `radius.sm`; the clear
control shows an `accent` hover. Disabled is `opacity` plus a `readOnly` field
that leaves the tab order, ignores `autoFocus` and paints no ring (0.10.0 has no
`aria-disabled`). A custom theme changes all of it — see [Theming](/docs/theming).

## Accessibility

Disabled controls announce **Disabled** through `aria-description`; 0.10.0 has no
`aria-disabled` semantics (plan 516).

- The root is a named `group`; every chip's removal control is a `button` named
  "Remove <token>".
- A chip with `testId="chip-design"` renders its removal control as
  `testId="chip-design-remove"`, so a consumer or a harness can address one
  token's control without coordinates.
- The field is a real input, so typing, selection and focus are native. A
  focused chip's removal control paints the token ring, and a field with
  `autoFocus` seeds the group ring (the runtime applies native focus after
  React's effects, so `onFocus` never runs — plan 522).
- Removing a chip by keyboard is possible by tabbing to its control and pressing
  `Enter`, or releasing `Space`.
- There is no `aria-disabled` in 0.10.0; the field and the group announce
  `Disabled` through `aria-description`.

## Limitations

- Controlled only (see above).
- No Backspace-on-empty removal (unobservable in 0.10.0).
- No token autocomplete, suggestions or validation; compose with `Combobox` or a
  schema when the tokens must be constrained.
- Commas are always separators; a token cannot contain a comma.
- Chips are rendered by the caller, so ordering is the caller's choice.

- Focus cues are seeded by `autoFocus`; the runtime does not reliably deliver
  React `focus`/`blur`, so a ring may not paint when focus moves by code
  (plans 390/603/605).

## Verification

`src/behaviour/tag-input.test.tsx` runs in the real GPUix renderer (16 tests):
rendering, Enter, comma commit, duplicates, the named removal control, removal
by pointer and Space release, the chip control's focus ring, the group ring a
field's `autoFocus` seeds, `max`, a fractional `max`, a disabled field
(read-only, no removal controls, no Enter path, out of the tab order, ignoring
`autoFocus` and painting no ring), a caller that refuses a change, and a refused
duplicate, cap or empty commit reporting nothing.

`src/tag-input/logic.test.ts` (16 pure tests) covers splitting, trimming,
duplicates, the integer and fractional cap, a non-finite cap, and first-match
removal.

```sh
nub run --filter @gpuixui/components test
nub run --filter @gpuixui/components test:behaviour
```
