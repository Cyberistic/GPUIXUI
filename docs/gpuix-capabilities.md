# GPUix capabilities — what the pinned runtime provides, what it does not

`MISSION.md` forbids presenting a capability the runtime lacks as if it worked.
This document is the durable record: one row per capability, the verdict, the
evidence, and the strongest honest alternative. Component plans and
`COMPONENTS.md`'s **GPUix support** column cite this file instead of restating a
verdict, and the documentation site publishes the reader-facing subset at
`/docs/runtime`.

**Pinned runtime:** `@gpuix/react` / `@gpuix/native` **0.11.0**, Apache-2.0. The
rows were re-read against the installed typings on 2026-10-21 — `StyleDesc`,
`HostProps`, `ElementType` and the host props in
`node_modules/@gpuix/native/dist/host.d.ts`, and the renderer methods in
`index.d.ts`. Where a row says *measured*, a probe in `apps/playground` reports
the fact from a real paint, not from a type; the probe id is in the row and its
measurement is in `apps/playground/README.md`.

**Two levels of evidence, kept apart.** A typed field proves an API is
*publishable*; only a probe proves it *paints*. A row marked `unverified` has
neither and must not be assumed to work.

## 1. Host elements

`ElementType` is exactly:

```ts
"div" | "text" | "img" | "svg" | "canvas" | "input" | "textarea" | "anchored" | "code" | "diff" | "markdown" | "virtual-list";
```

`canvas` is a blank host element — it appears in the union but has no
2D-context or draw props, so custom drawing is **not** available. `anchored`
positions its content and paints no surface of its own (the overlay packages put
the surface on a child `div`). `virtual-list` takes either children — retained in
the React tree, with only the off-screen build and paint skipped — or
`itemCount` + `estimatedItemHeight` + `windowStart` plus a row renderer, where the
app mounts the slice; a compound-children list therefore cannot be truly windowed
through it.

## 2. Provided by the runtime

Headless React components in `@gpuix/react` 0.11.0: `Select` + parts, `Combobox`
+ parts, `Tooltip` + parts, `Button`/`buttonProps` (`@gpuix/react/button`),
`Dialog` + parts, `AnimatePresence`/`motion`, and `floating`'s `FloatingLayer`,
`renderSlot`, `useControllableState`, `mergeStyles` and `StateStyle`. These give
behaviour and positioning; they ship no visual design.

Renderer methods the library builds on (`@gpuix/native` `index.d.ts`):
`focusElement`, `focusNext`, `focusPrevious`, `focusNextWithin`,
`focusPreviousWithin`, `getFocusedElementId`, `getElementBounds`,
`getElementsAt`, `getAllText`, `getPaintedText`, `getPaintedHighlights`,
`getScrollOffset`, `getSelectedText`, `promptForPaths`, `registerFont`,
`setImage`, `setImagePixels`, and the `simulate*`/automation surface the tests
drive.

## 3. The limits

Verdicts: **supported** · **supported, with limits** · **not supported** ·
**unverified** (absent from the typings and not measured — never assume it).

| Capability | Verdict | Evidence | Workaround |
| ---------- | ------- | -------- | ---------- |
| Flexbox and grid | supported | `StyleDesc.display`, `flexDirection`, `flexWrap`, `gap`/`rowGap`/`columnGap`, `alignItems`, `justifyContent`; `gridTemplateColumns`/`Rows` are integers | — |
| Grid span | not supported | no `gridColumn`/`gridRow`; only `gridColumnMin`/`gridRowMin` track sizing | size the track, or give the item an explicit width |
| Two-stop linear gradients | supported, with limits | `LinearGradientBackground.stops` is a 2-tuple; `angle` in degrees; `colorSpace` `srgb` or `oklab` | — |
| Multi-stop, radial, conic, repeating gradients | not supported | the stop tuple holds exactly two | paint a stack of divs, or an `svg` |
| `boxShadow`, including `inset` | supported | `BoxShadow` is a structured object with `inset` | — |
| Per-corner radii, per-side border widths, a two-value `borderStyle` | supported | `StyleDesc` corner and side fields; `borderStyle` is `solid` or `dashed` | — |
| Opacity | supported | `StyleDesc.opacity` | — |
| `aspectRatio` | supported | `StyleDesc.aspectRatio` — width divided by height | — |
| Text truncation | supported | `whiteSpace: "nowrap"`, `textOverflow` with `ellipsis` and `ellipsis-start`, `lineClamp` | — |
| Per-element `transform` / `rotate` / `scale` / `translate` / `skew` | not supported | no such field in `StyleDesc` | animate the numeric `MotionStyle` fields with `@gpuixui/motion`; static rotation/scale is unrepresentable |
| `zIndex` / stacking order | not supported in the published API | no `zIndex` in the published `StyleDesc`; paint order is tree order, so an overlay must render last (`toast.mdx`, `tabs.mdx`) | render the surface last in the tree. **The repo's source-built `darwin-x64` binding carries a local `zIndex` patch** (`apps/playground/patches/gpuix-zindex.patch`) — do not write against it in library code |
| Sticky positioning | not supported | **measured** by `data-grid-fixed-header`: a `position: "sticky"` child inside its scroller moved by exactly the scroll amount, i.e. it paints as `relative`. `position` is typed `string`, so the type does not say this | put the header **outside** the row scroller as a sibling; wrap header and rows in one `overflowX` scroller so both move together |
| Frozen column | supported, with limits | **Composed, not provided** — with no sticky, a frozen first column is the header rule on the other axis, and **measured** by `data-grid-frozen-column` (a 120px label pane beside a 240px grid over 60 × 28px rows): a wheel over the grid moves both panes to `-300` and a wheel over the frozen column moves both to `-600`, because the app mirrors `onScrollChange` into `scrollTo` on the other pane in **both** directions; the row under the reader keeps its `y` across panes; a `deltaX` wheel pans the grid 200px and leaves the frozen column still (a frozen column does not pan); a press on a frozen cell selects the row for the whole grid; and a `-10000` wheel clamps both panes at the same `-(60 × 28 − 240) = -1440`. **Measured in a window** by `frozen-column-lifecycle` (the same 120px column and 240px grid): the mirror lands in the **same frame** as the wheel — `scrollTo` paints synchronously from inside `onScrollChange`, so both panes report one offset after a single settle, where a mirror on the next render would leave the column one frame behind — the sideways pan is the grid's alone, and a press on a frozen cell selects the row for the grid | compose two scrollers, one per pane, and mirror their offsets through `onScrollChange` + `scrollTo`, guarding the echo with a **ref** — `scrollTo` paints synchronously, so the target's own change arrives inside the call and would otherwise mirror back. Share one row identity, set `overflowX` only on the pane that pans, and expect no single-scroller freeze |
| Table sort and selection | supported, with limits | **Composed, not provided** — a table is flex rows of fixed-width cells, and the two interactions MISSION names were **measured** by `table-lifecycle` in a window (60 rows of 28px in a 300×200 viewport, three columns in a 380px content box, so 80px of horizontal travel): a press selects the record it hit **and that row holds the focus** (`selected=r3`, focus on the pressed row), so the key that follows reaches that row's own `onKeyDown` with no synthetic focus; `down` roves focus and selection together to the next record (`selected=r4`) through the handler's own `renderer.focusElement`; a press on the size header sorts by the column it hit and a second press flips the direction (ascending, then descending) while the selected **record** survives the sort (`selected=r4` still); the header keeps its painted `y` while a −100 wheel moves the rows under it, and a wheel **over** the header scrolls nothing, because the header is a sibling outside the row scroller — moved inside it, the same wheel paints the header at `y = -36`; and one `overflowX` box around header and body pans both to the same `x` (−60), so a header cell and its column stay aligned after a pan. One measured constraint: a sortable header whose painted centre is clipped by the horizontal viewport sorts nothing, because the automation protocol aims a press at the element's centre — the probe's first run put the third column at 280…380 in a 300px frame and the press changed no order | key sort and selection by **record**, never by row index, so a sort cannot move the selection; give every row `tabIndex={0}` so the press focuses it, and move the focus with `focusElement` from the row's own key handler; keep the header a **sibling above** the row scroller and wrap both in one `overflowX` scroller; keep a sortable column's painted centre inside the frame, or pan the header before expecting a press to land |
| `backdropFilter` / per-element blur | not supported | no such field; blur exists only as the window backdrop | use an opaque or translucent fill |
| Window backdrop vibrancy (`windowBackground: "blurred"`) | supported, with limits | `WindowOptions.windowBackground` is honoured, not ignored. **Measured** by `window-backdrop` (one 900×520 window per run, captured at 1800×1040 — the display's 2× scale, read back rather than assumed): an `opaque` window's unpainted surface carries alpha **255**, `transparent` and `blurred` both carry alpha **0**, and the app's painted box stayed `rgba(217, 67, 43, 255)` in all three. Two limits: the app-side capture of `blurred` is **byte-identical** to `transparent`, because the vibrancy is composited behind the window, so no app frame proves the blur; and a second `init` in one process fails with `A GPUI application already exists on this thread`, so each mode is its own CLI run (`--window-background <mode>`). A translucent app fill composites against the window's surface rather than the theme literal: `#D9432B80` painted `rgba(109, 34, 22, 255)` in an opaque window | let the **unpainted** area carry the translucency and paint the content opaque; use `"blurred"` for the effect and confirm the look by eye on the target OS — do not claim it from a capture. One window per process, so a translucent and an opaque window cannot be compared in one run |
| CSS `filter`, `clip-path`, blend modes, text shadow | not supported | absent from `StyleDesc` | compose the effect from `div`/`svg` layers |
| CSS shorthand and `calc()` strings | not supported | values are numbers or colours, not a CSS string | `@gpuixui/tw` resolves a numeric `calc()` to a number before it reaches the runtime |
| Keyframe animations, variants, shared-layout transitions | not supported | `MotionProps` drives `width`, `height`, `opacity`, `top`, `right`, `bottom`, `left`, `borderRadius` with duration/delay/ease | `@gpuixui/motion` springs over those fields; a cross-fade is `opacity` |
| Animation interruption | supported | a target change starts the next transition from the current visible value | — |
| Animated geometry and content clipping | supported, with limits | `motion` tweens painted geometry. **Measured** by `motion-geometry` on a 120×40 box with `transition={{ duration: 3, ease: "easeInOut" }}`: eight presses ~50ms apart painted `40, 43, 117, 123, 221, 240, 240, 240` — a tween, not a jump — and settled at 240×240, the reverse run tweened `240, 240, 167, 63, 59.5, 40, 40, 40`, and `onMotionComplete` fired once per run. **The animated box clips its content rather than reflowing it**: a fixed 320×200 child kept that size while the box was 120×40 and while it was 240×240. `duration: 0` is the negative control (two target sizes, no frame between them) | animate an **outer** clipping box (`overflow: "hidden"`) for a collapsing sidebar or a growing row — the content inside stands still, it is not re-laid out; read `onMotionComplete` when a finished run should unmount or unlock; a numeric target lands exactly, so the settled box is the value written |
| Reduced-motion detection | not supported | **A measured absence, not an unrun probe.** `@gpuix/native` 0.11.0's `index.d.ts` publishes no preference query — no `appearance`, `prefers*` or `reduce*` export, and `WindowOptions` carries no such option — so there is no value to read. `@gpuixui/motion` already takes the policy from the caller: `MotionValue.sample(elapsedMs, reducedMotion)` jumps to the target when the boolean is `true`, and the React hooks take `options.reducedMotion`. No library component reads a system preference | the app owns the policy: detect it in the app's own layer, pass the boolean into `@gpuixui/motion` (see [Motion](/docs/motion)), and keep motion optional and short — never the carrier of meaning |
| Custom paint | not supported | `canvas` is in `ElementType` but blank | render `svg`; there is no retained draw API |
| Inline SVG painting | supported, with limits | `<svg source>` paints its markup, but **as one tint**: `@gpuix/native`'s `SvgElement` renders through GPUI's icon element, so the whole markup is masked in `style.color` and a shape's own `fill` never reaches the frame. **Measured** by `content-surfaces`: all five shapes painted in the one source tint, while five stacked `<svg>` elements each painted their own (bar green, bubble blue, line red, axis yellow, label orange); `<text>` inside the markup paints | stack one `<svg>` per colour — a multi-series chart is one element per series; labels can live in the markup, but a gradient or a per-shape palette inside one element is not available |
| Container queries | not supported | no such field; `useWindowSize` is the responsive hook | measure the box (`onLayout`, on `div`/`text`) or `useWindowSize` and branch in the component |
| Canvas drawing | not supported | as above — no 2D context, and **measured** by `content-surfaces`: a `<canvas>` tracks no painted bounds and paints nothing, so the fill behind it shows through | as above |
| IME composition | not supported | no composition events reach React | compose from `onInput`/`onKeyDown` at the application layer; live IME preview needs a runtime change |
| Window-level key events | supported, with limits | `render({ onKeyDown })` is the **only** app-level key path: the focused element's own `onKeyDown` runs first and the window handler after it, with `event.modifiers` set. **Measured** by the headless `window-key-shortcut` (`simulateKeystrokes("cmd-k")` runs the element handler and then the window handler, with the modifier set) and by `window-shortcut-lifecycle` in a window: the runner installs the handler once and forwards to the shipped `useWindowKey` seam; `cmd-k` opens the palette (`open=true last=cmd-k`, its text painted), `Escape` closes it, and after a press on another element — `getFocusedElementId` names the other element, not the probe — `cmd-k` still opens it. Dropping the runner's forwarding is the negative control (nothing reaches the app) | install one handler at the root and route accelerators from it; the focused element sees the key first, so a chord a field needs belongs to the field. A shortcut fires only while the window is focused, so a background hotkey needs a runtime change |
| Global / system shortcut | not supported | key events fire only while the window is focused | window-level `onKeyDown`; a background hotkey needs a runtime change |
| Tray / menu bar / status item | not supported | no such host | ship an in-window menu |
| Application menu (adding items) | not supported | the runtime installs a **fixed macOS menu bar** at window init — an Apple menu (Services, Hide, Hide Others, Show All, Quit) and a Window menu (Minimize, Zoom, Close), with **no Edit menu** on purpose so ⌘C/⌘V reach the window's text handling; ⌘Q/⌘H/⌥⌘H/⌘M/⌘W are bound. There is no API to add, remove or reorder an item: `app_menu::init` and `default_menus` are `pub(crate)`, `WindowOptions.appName` only names the Hide/Quit items, and no napi method takes a menu in `@gpuix/native` 0.11.0's `index.d.ts`. Read from the pinned source, not from a type | draw the menu **inside** the window — a `div` over the shipped dropdown/context-menu parts; a native item's callback cannot be attached, and the fixed bar exists only on macOS, so Linux and Windows menus are the app's own |
| Native view / webview / embedded browser | not supported | no child-view host | `markdown`/`code`/`diff` surfaces |
| Image painting | supported, with limits | `<img>` paints a path, an http(s) URL and a data-URL PNG; a pixel buffer through `ref.setImagePixels(width, height, …)` paints **only from a layout effect** — from a passive `useEffect` the element keeps its `img: no src` fallback. **Measured** by `content-surfaces` in both directions | upload pixels in `useLayoutEffect`/`useEffect`-before-paint (the upstream waveform example's pattern, not a preference); a data URL needs no timing |
| Raster and vector chart surfaces | supported | a chart has no host element and no drawing surface, so it is **composed** — and the route was **measured** by `chart-raster` (three 14×30 bars in a band per series, 19 checks): a `ref.setImagePixels` buffer keeps each pixel's own colour, so three series paint `#2ECC71`, `#3498DB` and `#E74C3C` inside **one** element, which a tinted `<svg source>` cannot do; the buffer's `0, 0, 0, 0` margin composites onto the surface behind the element (the `#14223A` card shows through), so a chart inherits the card it sits on instead of painting an opaque rectangle; a second buffer replaces the frame whole on a data change with no re-mount and no re-layout call; and `setImage` decoding SVG **bytes** paints every `fill` its own colour (`#B14AFF`, `#00A893`, `#FF8A00`) — the vector route `<svg source>` cannot take. Two limits: a **translucent** bar over another bar is unmeasured (only a fully transparent pixel is proved to composite), and the element scales its buffer to its box, so a chart drawn at its layout size is the safe shape | raster a multi-colour plot through `setImagePixels` from a **layout effect** (the timing `content-surfaces` measures for a pixel buffer) and re-push the buffer when the data changes; take `setImage` with SVG bytes for a vector plot; compose axis and legend labels as `<text>` beside the image, because the raster carries only the marks; `<svg source>` stays one tint, so it is never the multi-colour route |
| Terminal rendering | supported | `render(<App />, { terminal: true })`, `isTerminal()` | — |
| Headless dialog | supported | `@gpuix/react/dialog` owns the Escape layer and the Tab trap | the library keeps its styled compound `Dialog` so it can theme it; the headless one is not wrapped |
| Portals | supported, with limits | `createPortal` is published, and **measured** by `portal-layer` in a window: a portalled card paints inside its **target's** box, outside an ancestor's clip, keeps the React context provided above the caller, receives a pointer press and keys typed in its field, and unpaints when detached; adding it back paints it again. Two measured limits: `getPaintedText` still lists a clipped sibling's glyphs although no pixel reached the frame, and a clip only holds when the clipping box is the child's containing block (`position: "relative"`, as in CSS). The binding opens one window per process and has no drag host feature, so a portal moves content to another layer **in the same window** | render a floating surface through `createPortal` when it must escape a clip; prove a clip from a capture rather than the paint report; give the clipping box `position: "relative"`; a detached tab is a layer or pane move in the **same window**, not a second OS window |
| Tab / Shift+Tab focus traversal | supported, with limits | native tab order; `focusNext`/`focusPrevious`/`focusNextWithin` move focus from code. A synthetic `"tab"` key does not traverse the offscreen `TestRenderer` | drive traversal through the renderer calls in tests |
| Pointer, keyboard and focus events | supported, with limits | `HostProps.onClick` (primary only), `onAuxClick`, `onMouseDown`/`Up`/`Move`/`Enter`/`Leave`, `onMouseDownOutside`, `onKeyDown`/`Up`, `onFocus`/`onBlur`, `onLayout` (`div`/`text` only). **Measured:** a `Tab` traversal **does** run React's `onFocus` on 0.11.0 — `tooltip-lifecycle` focuses the trigger and its tip opens, and `tabs-lifecycle` counts `focuses=1` for the same traversal. An earlier run recorded the opposite because it read the frame before the event arrived | a press is primary-only, so a secondary press arrives as `onAuxClick`, and `onLayout` reports only on a `div` or a `text`. A key move still reads the key event's own `elementId` (the `Tabs` move origin does), because the first arrow after a traversal must move off the tab it reached rather than the selection; a focus handler needs no substitute |
| Scroll events | supported, with limits | both listeners fire, and they report **different** things. **Measured** by `scroll-lifecycle`: `onScroll`'s `deltaX`/`deltaY` is the wheel input the window received — a `-100000` wheel reports `-100000` after the offset travelled 200px and clamped — while `onScrollChange`'s `scrollX`/`scrollY` is the clamped absolute pair `getScrollOffset` returns | a scrollbar, a saved position or a "follow the tail" scroller reads `onScrollChange`; use `onScroll` only for the gesture's own delta |
| Horizontal scrollers | supported | `overflowX: "scroll"` makes a real horizontal scroller. **Measured** by `scroll-horizontal` in a 320px viewport holding 18 × 80px columns: the strip reports an offset and starts at `x = 0`; a `deltaX = -160` wheel moves it left (negative scrolls right, the same sign rule as `deltaY`) and leaves `y = 0`, because a horizontal gesture does not move the vertical axis; `onScroll` reports a non-zero `deltaX`; and a `deltaX = -4000` wheel clamps exactly at `-(18 × 80 − 320) = -1120`. Dropping `overflowX` is the negative control (no offset is reported at all) | put a wide table, a tab rail or a code block in its own `overflowX` scroller and read the clamped offset from `onScrollChange`; a horizontal wheel is not a vertical one, so a pane that needs both axes needs both overflow values |
| Reveal a selection in a scroller | supported, with limits | the runtime does **not** move a scroller to a selection. **Measured** by `tab-overflow` (eight 80px tabs in a 320px rail): pressing `End` selects tab 7 while the plain rail stays at `x = 0` and the selected tab starts past the rail's right edge (`x ≥ 320`), so it is genuinely clipped. Calling the selected element's own `scrollIntoView()` moves the rail to `x = -320` and paints tab 7 wholly inside it — but the call resolves **one** scroll target, the nearest ancestor scroll container, and scrolls it to the **index of its direct child**: a nested rail whose tabs sit inside a wrapper row moves only `x = -1`, because the direct child is the row, not the tab. `getElementBounds` reports the painted position inside a scroller, so a reveal can be asserted on the box | call `scrollIntoView()` on the selected element after a selection change, and keep the tabs (or rows) as **direct children** of the `overflowX` scroller — a wrapper row makes the selected tab unreachable, so the fix is layout rather than a second call. Do not expect the runtime to reveal a keyed selection by itself |
| Drag auto-scroll | supported, with limits | **Composed, not provided**: the runtime does not scroll a pane because a pointer rests near its edge. **Measured** by `drag-autoscroll` (two 320×200 rails of 24 rows; row 4 dragged 10px in eight moves with its centre `y = 180` inside the 200px rail's 24px band): the plain rail stayed at `y = 0` through all eight moves, while a rail whose `onMouseMove` reads its own `getElementBounds` and calls `renderer.scrollTo(id, 0, offset - 16)` inside the band moved to `y = -128` — one step per move, driven by the component. `scrollTo` paints synchronously, so state written **after** the call is not committed when the drag returns (`moves=0` while the offset had reached `-128`) | own the edge band, the step and the clamp in the component: read the pane's own bounds, compute the next offset in a **ref** and increment before calling `scrollTo`; a drag that grows a tree or reaches a far row needs this, because nothing scrolls on its own |
| Pointer capture | supported, with limits | `renderer.rs` arms GPUI's pointer capture on a left mouse down **only** for an element that listens to both `onMouseDown` and `onMouseMove` (the host's `mouseDown`/`mouseMove`); **measured** by `pointer-capture`: the paired sample kept all eight moves and its release 120px outside its box (`both=8 bothUnder=0 bothUp=1`), a move-only sample got the one pre-press move and the sibling received the eight (`move=1 moveUnder=8`), and the shipped `Slider` followed a drag that left its track (`slider=66 sliderChanges=9`) | a splitter, drag handle or slider must subscribe to **both** `onMouseDown` and `onMouseMove`; a move-only element captures nothing, so the element under the pointer resolves the drag |
| Cross-pane drag | supported, with limits | **Composed, not provided.** A cross-pane drag is pointer listeners on each pane, and the protocol delivers the whole gesture — press, eight moves, release — **before** React commits the render the press scheduled. **Measured** by `drag-between-panes` (real `mouseMove`s with the button held, not a synthesised down/move/up): a handler that gated on a `dragging` **state** therefore saw `false` for every move and the drag never started, while a synchronous press flag let each pane resolve the drop (`zone=right drops=1`, then `zone=left drops=2`, each pane counting the travel over itself). The dragged item there listens to `onMouseDown` alone, so it captures nothing and the pane under the pointer sees every move — the `pointer-capture` rule | set the press flag in a **ref** synchronously and keep state only for the readout; the element that must follow the pointer past its own box subscribes to **both** `onMouseDown` and `onMouseMove`, while a "drop on whatever is under the pointer" model listens on the panes instead |
| Drag reorder | supported, with limits | **Composed, not provided**: a reorderable row subscribes to both `onMouseDown` and `onMouseMove`, so the runtime's pointer capture means **the dragged row keeps the whole gesture** and no drop target hears it. **Measured** by `drag-reorder` (four 44px rows in a 280px column, a press on `alpha` and eight moves onto `delta`'s label): `heard=0` after every drag, and no other row's `onMouseUp` ran, so a drop cannot be a listener; `renderer.getElementsAt(x, y)` reports the label **above** the row first (`top=other`), so the drop is the first id the list reports that is one of its rows — reading only the topmost id yields `over=none misses=1` and no reorder — and the painted order follows the move (`order=bravo,charlie,delta,alpha`, with `row-alpha` taking `row-delta`'s old `y`), while a release outside every row is a miss and leaves the order alone. Dropping the row's `onMouseMove` disarms capture: the target row hears the release (`heard=1`) and nothing reorders | subscribe to **both** listeners on the row that is dragged; resolve the drop by scanning `getElementsAt` for the first id that belongs to a row rather than trusting the topmost one (a row's `<text>` label sits above it); apply the move to the row's own identity, not the label's; keep the press flag in a **ref** (`drag-between-panes` measured why state is too late). There is no drag host feature, so this is a pointer gesture the component owns — no drag image, no cross-application payload and no drag between windows (one window per process); an OS file drop goes through `onFileDrop` |
| Keyboard focus dim | supported, with limits | while one element has keyboard focus the runtime multiplies **every other focusable element's** opacity by `keyboardFocusDimOpacity` (`0.4`) — fill and text — per element and on by default. **Measured** by `keyboard-focus-dim` (the dimmed sample loses exact-fill pixels, the focused one and the one declaring `keyboardFocusDim: false` keep theirs) and by `filled-action-dim` on the shipped actions (a ghost's 611 label pixels go to 0, a filled action keeps all 66 008 because it declares the opt-out, and a caller's `style` merges last and can put the cue back). Two limits: the cue buries a label — the tightest placement measures 1.27:1 (`primary` over a card in Linux light) — and **a focused `input`/`textarea` casts no dim at all**, because `renderer.rs`'s keyboard-focus path returns nothing for a text field | a filled action or a field's value opts out with `keyboardFocusDim: false` (the library's filled buttons do, through `paintsFilledSurface`); the opt-out is not needed for a control beside a form, since a focused field dims nothing. A control with no fill keeps the cue — it is what tells a reader where Tab is |
| Resizable panels and dock reflow | supported, with limits | **Composed, not provided**: a splitter is pointer capture over a caller-owned width. `panel-resize` drags a divider and clamps it; `split-pane-lifecycle` kept all eight moves 80px outside a 6px divider's box; `docking-nested` keeps nested levels' widths independent and collapses a pane to 0 and back. The signal a dock re-clamps on is **measured** by `dock-reflow` (a 120px sidebar, a flexible centre and a fixed 100px inspector in a 560px row): the centre's `onLayout` fires again when the sidebar takes 100px, the settled payload is the painted box (`w=240`, equal to `bounds`), the **first** pass of that same reflow reports the box the pane still has (`w=340`, `reports=2`), and the inspector whose box did **not** change is still reported to (its count reaches 2). A split's `max` is the caller's number, not its container's width | subscribe to **both** `onMouseDown` and `onMouseMove` on the divider so pointer capture arms; re-clamp from the width `onLayout` **gives** you, idempotently — a stale pass arrives first and an unchanged pane is reported to — never from the container's width in the same tick as the state change; a dock passes its own bounds instead of trusting an inner split's `max` |

## 4. Accessibility and motion, cross-cutting

The gap components cite most often is the aria subset above: a checkbox cannot
announce `checked`, a slider cannot announce a numeric value, and a control
cannot be named by a sibling `Label`. Each component documents the consequence
on its own page rather than implying the attribute exists.

A keyboard traversal **does** run React's `onFocus` on 0.11.0 — measured by
`tooltip-lifecycle` (the traversal reaches the trigger and the tip opens) and
`tabs-lifecycle` (`focuses=1`). An earlier version of this record said the
opposite because the probe read the frame before the event arrived, so a
component may open a focus-only surface from `onFocus`. A key *move* still reads
the key event's own `elementId` or `getFocusedElementId`: the first arrow after a
traversal must move off the tab it reached rather than the selection, which the
event names directly.

Assistive technology sees a node only when it has **both** an id (always set) and
a `role`; `"none"`/`"presentation"` remove the node. The `a11y-tree` scenario
read the tree those rules produce: the role reaches the platform under its own
name (`option` is `ListBoxOption`), the seven `aria-*` attributes land on
`label`/`description`/`author_id`/`selected`/`expanded`/`level`/`value`, a
`<text>` is a `Label`, and a roleless `div` carrying only an `aria-label` is
absent from the tree. That tree is the offscreen `TestRenderer`'s; a window's
automation protocol has no a11y verb, so it is not among the window probes above.
Focus rings are painted by `focusVisible`, which is measured to paint after Tab
and never after a mouse press — the tokens package owns the helper
(`keyboardFocusRing`) and the policy.

Motion is springs over numeric fields only, with no keyframes and no preference
query: the runtime exposes no reduced-motion flag, so `@gpuixui/motion` takes it
as a caller-supplied boolean (`MotionValue.sample(elapsedMs, reducedMotion)` and
the hooks' `options.reducedMotion`), and the app owns the policy. The
state-driven design rule is to make motion optional and short, never the carrier
of meaning. Where it runs it is a real tween on painted
geometry: a 3s box painted eight intermediate heights between 40 and 240, landed
exactly at 240, and fired `onMotionComplete` once (`motion-geometry`). The
animated box **clips** its content — a fixed 320×200 child kept its size while
the box was 120×40 and while it was 240×240 — so a collapsing sidebar animates an
outer `overflow: "hidden"` box instead of expecting the panel inside to re-lay
out.

## 5. Keeping this document true

- `apps/docs/src/lib/capability-doc.test.ts` reads this file and holds the rows
  whose capability is encoded in `@gpuixui/runtime`'s `capabilities` matrix to
  that matrix: a row and the code cannot disagree about whether the runtime
  supports something, and a new matrix key without a row fails by name.
- The same test holds `/docs/runtime` to this file: the site's *measured in a
  window* and *measured offscreen* sections must name the probes behind every gap
  and measured behaviour they list (`data-grid-fixed-header`, `editor-surface`, `tooltip-lifecycle`,
  `tabs-lifecycle`, `scroll-lifecycle`, `pointer-capture`, `content-surfaces`,
  `selection-lifecycle`, `clipboard-lifecycle`, `virtual-tree-lifecycle`,
  `virtual-list-lifecycle`, `virtual-list-windowed`, `virtual-list-rows`,
  `virtual-list-expand`, `portal-layer`, `data-grid-frozen-column`,
  `select-lifecycle`, `floating-sides`, `dock-reflow`, `docking-nested`,
  `panel-resize`, `split-pane-lifecycle`, `a11y-tree`, `drag-between-panes`,
  `keyboard-focus-dim`, `filled-action-dim`, `motion-geometry`,
  `scroll-horizontal`, `tab-overflow`, `drag-autoscroll`,
  `window-key-shortcut`, `window-shortcut-lifecycle`,
  `loading-row-correction`, `window-resize-reflow`, `drag-reorder`,
  `table-lifecycle`, `frozen-column-lifecycle`, `dock-focus-lifecycle`,
  `header-menu-lifecycle`, `window-backdrop`, `chart-raster`, `window-chrome`), because a
  measured gap
  is absent from the typings rather than merely hard to find. Every id a page
  row cites must be a registered probe in `apps/playground` and appear in this
  list, so a row cannot cite a probe that does not exist or a probe the record
  does not owe.
- The record's own evidence column is held to that registry too: every
  kebab-case token a §3 row names in backticks must be a probe a playground
  registry declares, unless it is a value the row quotes as its measurement (a
  `textOverflow` value, a key chord, a row marker) and is listed with its
  reason. A mistyped id in the durable record would otherwise send a plan to a
  probe that does not exist, and the page's citations would stay green.
- The five absences the typings alone prove — links (`href`), `fieldset`,
  `onContextMenu`, `onPaste` and the closed `aria-*` set — are held from both
  sides too: a row dropped from this file, a page row dropped from
  `/docs/runtime`, or an `aria-*` absence the inventory names but this file does
  not, fails by name. The application menu is a sixth absence, but it is proven
  by the runtime's pinned **source** (`app_menu.rs`) rather than by a type, so a
  row giving it a `supported` verdict is a claim no API can keep. Reduced-motion
  detection is proven the same way — the installed `index.d.ts` publishes no
  preference query and `WindowOptions` carries no option — so its `not supported`
  verdict and the `@gpuixui/motion` flag it names as the workaround are held to
  the typings and the package source rather than to a probe that could never run.
- The probe measurements themselves are asserted by the suite
  (`apps/playground`), not here: this document records the verdict and points at
  the evidence.
