# COMPONENTS.md — inventory, status, limitations

The inventory is a **target**, not permission to fake unsupported things. A row
may only move to `done` when the component has: code, a test appropriate to its
behaviour, at least one working example, a docs page, and a verified interaction
in the real runtime (or a documented, evidenced limitation).

Status: `todo` · `wip` · `done` · `blocked (reason)` · `unsupported (evidence)`

Every row also records **GPUix support** and, when it is not `yes`, the evidence
and the strongest honest alternative.

## Not provided by GPUix

The owner's explicit ask: **whatever is missing and GPUix does not already
provide** — the rows that need real implementation, not API-shape work over an
existing host element.

Verdicts are against the **published `@gpuix/react` / `@gpuix/native` 0.10.0**
(the version this repo pins), read on 2026-10-17 from
`workspaces/components/node_modules/@gpuix/react/dist/index.d.ts`,
`dist/components/`, `dist/floating.d.ts`, `@gpuix/native/dist/host.d.ts` and
`@gpuix/native/index.d.ts`. They are **not** read from `references/gpuix`, which
is ahead of the published release — the divergence is called out below.

**Primitives only — still needs implementation:** Popovers / Dropdown menus /
Context menus (`floating`'s `FloatingLayer` + `<anchored>` give positioning and
occlusion, not menu semantics); Toasts / notifications (`AnimatePresence` +
`createPortal` + `<anchored>`); Buttons and Dialogs (**present on
`references/gpuix` `main`, absent from published 0.10.0** — no `./button` or
`./dialog` subpath and no `Button` / `Dialog` in `dist/index.d.ts`); `<canvas>`
custom drawing (**unverified** — the README's Supported Elements table marks it
"Custom drawing (planned)").

**Cross-cutting, verified, partial:** AccessKit `role`, `aria-label`,
`aria-description`, `aria-id`, `aria-expanded`, `aria-selected`,
`aria-valuetext`, `aria-level`; native `tabIndex` / `autoFocus` and renderer
`focusElement` / `focusNext` / `focusPrevious` / `focusNextWithin`. There is **no**
`aria-checked`, `aria-valuenow`, `aria-labelledby` or `aria-describedby`.

0.10.0 also reports **no accessible name from a control's text child**, so every
part that draws an interactive role supplies `aria-label` from its plain-text
children (the caller's own `aria-label` wins); a composed label passes one. The
rule lives in `internal/name.ts` and is held across every example by
`src/behaviour/accessibility.test.tsx` (plan `391`).

0.10.0 has **no `aria-disabled`**. Every part whose own state is disabled appends
`Disabled` to its `aria-description`, joined with the caller's text and any
validation or status message. The rule lives in
`internal/state-description.ts` and is held by
`src/behaviour/disabled-description.test.tsx` (plan `516`). A focusable region
with no role (`ContextMenuTrigger`) has no node to describe and records that
gap instead.

**A focus ring needs a focus signal.** Components seed `focused` from
`autoFocus` and follow React `focus`/`blur`; the headless renderer sends neither
for a programmatic move (plans `536`/`540`) and a live window's delivery is
window-state dependent (playground plans `390`/`603`/`605`), so a ring after a
programmatic or pointer focus move appears only when the host sends the event.
Where the binding delivers no signal, a part that owns a ring measures the
renderer's own focused host instead of inventing focus from colour or hover; the
sample is 50 ms while the part is enabled. `FieldInput` (plan `748`),
`SearchInput` (plans `659`/`660`) and `ComboboxTrigger` while the popup is closed
(plan `672`) read it for their ring, the button-shaped parts — `Button`,
`IconButton`, `TabsTrigger`, `AccordionTrigger` and `CollapsibleTrigger` — read it
through the shared `useFocusState` host id (plan `752`), `Carousel` and its
indicator dots, the colour swatches and HEX field, the recorder and its clear
control, a chip's removal control, a mention row and the time-picker clear control
read it too (plan `754`); `BreadcrumbLink`, the Chat composer, the InlineEdit
display, `CommandMenuInput` and `ContextMenuTrigger` read it through the same hook,
and the Tag input, Mention input and Time picker **group** rings take one sample
per group (plan `755`), `InlineEdit`'s commit watcher while an edit is open
(plan `613`) reads it without painting, and a toast
reads it to hold its auto-dismiss clock while its own controls hold native focus
(plan `743`). The
claim is stated on all
36 component pages whose parts can take focus, `ComponentMeta.focusable` marks
them, and `inventory.test.ts` holds the pages to it (plan `608`).

A part that becomes disabled drops its painted focus, because no `blur` arrives
for the native focus it keeps; `internal/focus.ts` owns the rule, a recording
hotkey field also cancels its recording, and
`src/behaviour/disabled-inert.test.tsx` holds Button/IconButton, Tabs,
Accordion, Collapsible, Inline edit and the hotkey recorder to it (plan `680`).
